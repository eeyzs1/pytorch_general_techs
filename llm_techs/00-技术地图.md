# LLM 技术地图：6 层结构 × 10 个类别

> 更新：2026-10 ｜ 定位：本工作区的总索引。先读这篇，再按需下钻。
> 收录标准：**已经进入生产、被头部公司规模化使用**的技术；纯论文标注「前沿」。

---

## 0. 一个统一视角：所有技术都在跟三种稀缺资源搏斗

| 资源 | 瓶颈出现在 | 用户感受 | 主要解法 |
|---|---|---|---|
| **算力 FLOPs** | Prefill（一次读完整个 prompt） | 长 prompt 首字慢、贵 | 前缀缓存、批处理、MoE 稀疏、量化 |
| **显存带宽 HBM** | Decode（逐 token 生成） | 并发上不去、吞吐低 | KV 量化/压缩、GQA/MLA、投机解码、PD 分离 |
| **上下文 tokens** | 长会话 / 长文档 / Agent | 成本线性涨、注意力 O(n²)、中间信息丢失 | RAG、上下文工程、压缩摘要、分层记忆 |

由此推出所有技术的两个母题：

- **复用**：同一份计算 / 显存 / 上下文，服务更多请求
  → 缓存、批处理、共享前缀、KV 池化
- **切分**：把大问题拆成能并行、能分层的小问题
  → TP/PP/EP 并行、PD 分离、offload、蒸馏

> 看到任何新技术，先判断它是「复用」还是「切分」。90% 的情况一句话就能定位。

## 1. 六层结构

```
┌──────────────────────────────────────────────────────────────┐
│ L5  组织治理   网关 · 路由 · 评测 · 可观测 · 安全合规         │
├──────────────────────────────────────────────────────────────┤
│ L4  应用架构   RAG · Agent · 上下文工程 · 记忆                │
├──────────────────────────────────────────────────────────────┤
│ L3  模型接口   Prompt Caching · 结构化输出 · 工具调用 / MCP   │
├──────────────────────────────────────────────────────────────┤
│ L2  集群服务   连续批处理 · PD 分离 · KV 池化 · 缓存亲和路由  │
├──────────────────────────────────────────────────────────────┤
│ L1  推理引擎   PagedAttention · 前缀缓存 · 投机解码 · 量化    │
├──────────────────────────────────────────────────────────────┤
│ L0  硬件内核   HBM · NVLink/RDMA · FlashAttention · FP8 GEMM  │
└──────────────────────────────────────────────────────────────┘
        ▲ 越往下越通用（换模型也适用），越往上越业务（换模型就要改）
```

**为什么用分层而不是按时间线？** 因为技术的生命周期差别极大：FlashAttention 是永久性的内核级改进，而某个 Agent 框架可能两年就没了。分层能让你判断「这个东西值不值得学」——越靠下越保值。

## 3. 逐类展开

### 3.1 推理引擎与内核

**问题**：朴素实现下 GPU 利用率常常只有 15–25%。原因是 decode 阶段每生成一个 token 都要把整个模型权重读一遍，是彻底的 memory-bound；而 prefill 阶段是 compute-bound。两个阶段的资源画像完全相反。

**关键技术**
- **PagedAttention**：把 KV cache 像操作系统分页一样按 block 管理，消除显存碎片，顺带支持前缀共享（copy-on-write）
- **Continuous batching**：不等整批请求结束就替换已完成的槽位，把 batch 填满（Orca 提出，现为标配）
- **Chunked prefill**：把长 prefill 切成小块，和 decode 混批，避免一个长请求卡住所有人
- **FlashAttention / FlashInfer**：IO-aware 注意力核，避免把 N×N 矩阵写回 HBM
- **CUDA Graph / kernel fusion**：减少 kernel launch 开销（小 batch 时收益极大）
- **投机解码**：小模型草拟多个 token，大模型一次并行验证（EAGLE 系列已进 vLLM/SGLang 主线）

**公司实践**：vLLM 与 SGLang 是事实标准，连 Google TPU 都提供了两者的官方推理引擎；TensorRT-LLM 在 NVIDIA 生态内主打极致性能；DeepSeek 自研 DeepGEMM 做 MoE 的 grouped GEMM。

**关键指标**：tokens/s/GPU、TTFT p95、TPOT（每 token 输出时间）、**goodput**（满足 SLO 的请求占比，比吞吐更真实）

**常见误区**：只看吞吐不看 goodput。把 batch size 拉满，吞吐很漂亮，但 p99 延迟炸了，业务上等于不可用。

---

### 3.2 服务编排与集群

**问题**：单机装不下模型或扛不住并发；更麻烦的是 prefill 和 decode 互相干扰——长 prefill 会打断正在 decode 的请求，导致 TPOT 抖动。

**关键技术**
- **PD 分离（Prefill/Decode Disaggregation）**：prefill 与 decode 跑在不同 GPU 池，KV 通过高速互联传输。代表：DistServe、Splitwise、Mooncake（月之暗面）、llm-d
- **KV 传输层**：NIXL、RDMA、NVLink；DeepSeek 用 3FS 做分布式 KV 落地
- **缓存亲和路由（cache-aware routing）**：网关层看得到每个副本持有哪些前缀，把同前缀请求打到同副本（IBM、llm-d 都在做）
- **自动扩缩**：按队列深度 / KV 占用率扩缩，而不是按 CPU

**公司实践**：Moonshot（Mooncake 是其 Kimi 的推理架构）、DeepSeek、Google（GKE Inference Gateway）、IBM/Red Hat（llm-d）、AWS。

**关键指标**：集群 GPU 利用率、排队时延、跨节点 KV 命中率、单位 token 成本

**常见误区**：小规模上 PD 分离反而更贵——KV 传输开销可能超过省下的算力。拐点通常在中大规模（几十卡以上）+ 长 prompt 场景。

---

### 3.3 缓存与上下文复用 ★本工作区主线

**问题**：同一个 system prompt、同一份文档、同一段对话历史，被反复做 prefill。这是 LLM 系统里**最大且最容易拿到的浪费**。

**六层缓存**（详细展开见 [`01-缓存与上下文复用.md`](01-缓存与上下文复用.md)）

| 层 | 缓存什么 | 谁管理 | 收益量级 |
|---|---|---|---|
| L1 | 单请求内的 KV | 推理引擎 | decode 的前提 |
| L2 | 跨请求前缀 KV（同副本） | vLLM APC / SGLang RadixAttention | TTFT ↓ 50–90% |
| L3 | 厂商侧 prompt cache | OpenAI / Anthropic / Google / DeepSeek | 输入成本 ↓ 50–90% |
| L4 | 跨实例 KV 池 | LMCache、llm-d、3FS | 跨副本复用，TTFT ↓ 4× |
| L5 | 语义缓存 | 应用 / 网关 | 整次调用跳过 |
| L6 | 应用结果缓存 | 应用 | embedding / rerank / 工具结果 |

**关键指标**：prefix cache hit rate、cached token 占比、每会话成本、TTFT p50/p95

**常见误区**：把时间戳、用户 ID、request ID 放在 system prompt 开头——整个前缀全部失效，缓存命中率归零。

---

### 3.4 量化与压缩

**问题**：显存装不下、HBM 带宽不够。decode 阶段读一遍权重只是为了算一个 token，权重越小越快。

**关键技术**
- **权重量化**：GPTQ / AWQ（INT4）、SmoothQuant（W8A8）、FP8（Hopper 之后的主流）
- **KV cache 量化**：FP8 KV 已是 vLLM 生产选项；更激进的 INT4 会影响长上下文质量
- **稀疏**：2:4 结构化稀疏、MoE 的稀疏激活（总参数量 ≠ 激活参数量）
- **蒸馏**：大模型教小模型，是企业最常用的「把成本打下来」手段
- **模型路由**：简单请求走小模型，难请求才升级

**公司实践**：几乎所有推理侧都在用量化；NVIDIA 推 FP8/FP4；端侧（高通、苹果）靠 INT4 + 蒸馏。

**关键指标**：显存占用、tokens/s、**质量回归**（量化必须过评测集，不能只看 loss）

**常见误区**：量化后不做任务级评测。困惑度只涨 2%，但 JSON 输出格式崩了、工具调用成功率掉了 10%。

---

### 3.5 训练与后训练

**问题**：单卡装不下；全参训练成本极高；对齐（让模型听话、有用、安全）需要专门流程。

**关键技术**
- **并行**：数据并行（DP）、张量并行（TP）、流水并行（PP）、专家并行（EP，MoE 必备）、序列/上下文并行（长上下文）
- **显存优化**：ZeRO / FSDP（分片优化器状态、梯度、参数）、activation checkpointing
- **精度**：BF16 起步，FP8 训练已在超大集群常态化
- **长上下文扩展**：RoPE scaling、YaRN、Ring Attention
- **后训练**：SFT → LoRA/QLoRA（低成本适配）→ DPO / GRPO / RLVR（推理能力）
- **蒸馏与合成数据**：企业落地最常用的两条路

**公司实践**：模型公司用 Megatron-LM / torchtitan / 自研；应用公司基本只做 LoRA + 蒸馏 + prompt 工程。

**关键指标**：MFU（模型算力利用率）、每 token 训练成本、评测提升幅度

**常见误区**：一上来就全参微调。绝大多数业务场景 LoRA 就够了，且更好维护、更好回滚。

---

### 3.6 检索增强 RAG

**问题**：模型不知道你的私有数据，也不知道昨天发生了什么；上下文窗口再大也塞不下整个知识库。

**关键技术**
- **解析与切块**：按语义/结构切，保留标题层级；切块策略对效果的影响**大于** embedding 选型
- **向量库**：pgvector（够用且省事）、Milvus / Qdrant / Weaviate（规模）、Pinecone（托管）、Vespa（混合检索强）
- **混合检索**：BM25 + dense + RRF 融合，专有名词和代码场景提升明显
- **Rerank**：cross-encoder 精排，top-50 召回 → top-5 送模型
- **查询侧优化**：query 改写、多查询扩展、HyDE
- **GraphRAG / agentic RAG**：多跳推理、模型自己决定检索什么

**公司实践**：几乎所有企业 AI 项目；Azure AI Search、Vertex AI Search、Elastic、MongoDB Atlas 都把混合检索做成默认能力。

**关键指标**：recall@k、nDCG、引用准确率、端到端答案正确率

**常见误区**：只调 embedding 不调切块；盲目加大 top-k（噪声和成本一起涨，且**破坏前缀缓存**）。

---

### 3.7 Agent 与工具协议

**问题**：模型要能查数据库、发邮件、改代码，而不只是聊天。

**关键技术**
- **Function calling / tool use**：模型输出结构化调用，宿主执行后回填结果
- **MCP（Model Context Protocol）**：已成人机工具连接的事实标准。2026-07-28 版把核心改为**无状态请求/响应**，可直接部署在 serverless / 边缘；Apps、Tasks 作为版本化扩展；授权对齐 OAuth 2.0 / OIDC。官方称 SDK 月下载已超 4 亿次
- **结构化输出 / 约束解码**：JSON Schema 强制合法，XGrammar、llguidance、Outlines（vLLM/SGLang 内置）
- **沙箱**：代码执行必须隔离（容器、E2B、gVisor）
- **编排**：LangGraph、OpenAI Agents SDK、Claude Agent SDK
- **权限与审批**：工具级最小权限、危险操作人工确认

**公司实践**：Anthropic / OpenAI / Google / Microsoft 全线支持；Figma、Intuit、Netlify 等已把 MCP server 作为产品接口。

**关键指标**：工具调用成功率、任务完成率、单任务 token 成本、越权操作数

**常见误区**：一次暴露 50 个工具。模型选择困难，且工具定义一变就**整段前缀缓存失效**。

---

### 3.8 上下文工程

**问题**：上下文是**有限且边际收益递减**的资源。研究显示 token 越多，模型对中间信息的召回反而下降（context rot）。长任务跑几十轮后，上下文膨胀、成本飙升、质量下滑。

**关键技术**（Anthropic 已把这三种做成 first-party API）
- **Compaction（压缩重启）**：接近上限时把整段对话摘要成高保真笔记，重新开始。`compact_20260112`
- **Tool-result clearing**：只清掉旧的、可重取的工具结果，保留「调用过」的记录。`clear_tool_uses_20250919`
- **结构化记忆**：模型自己往外部存储写笔记，跨会话恢复。`memory_20250818`
- **子 agent 隔离**：把脏活丢进独立上下文，只把结论带回来
- **渐进式披露**：技能/文档按需加载，而不是全量塞进 system prompt
- **程序化工具调用**：大结果在代码里处理，不进上下文窗口

**公司实践**：Claude Code（compaction + 两套记忆系统）、Cursor、Manus、LangChain Deep Agents。

**关键指标**：每任务 token 数、上下文利用率、成功率随轮次的衰减曲线

**常见误区**：把 compaction 当免费。它是有损的，而且**会破坏前缀缓存**——要挑时机做，别每轮都做。

---

### 3.9 网关、路由与成本治理

**问题**：一家公司往往同时用 3–5 家模型；还要限流、降级、算账、隔离租户。

**关键技术**
- **LLM Gateway**：统一 OpenAI 兼容协议、密钥托管、重试与 fallback
- **模型路由**：按难度/成本/延迟/质量选模型；也有按业务规则硬路由
- **语义缓存**：相似问题复用答案（见 01 篇，注意误命中风险）
- **配额与预算**：按租户/团队/功能维度设 token 预算
- **审计**：谁在什么时候调了什么模型、花了多少

**公司实践**：LiteLLM、OpenRouter、Portkey、Kong AI Gateway、Cloudflare AI Gateway；中大型企业基本都会自建或采购一层。

**关键指标**：单位请求成本、路由准确率、可用性、P95 延迟

**常见误区**：路由只看价格。便宜模型在 10% 的难请求上答错，返工成本远超省下的钱。

---

### 3.10 评测、可观测与安全

**问题**：LLM 输出是非确定性的，改一个 prompt 可能让另外三个场景悄悄退化；同时 prompt injection、数据泄漏是真实攻击面。

**关键技术**
- **离线回归集**：从真实流量采样，固化成 golden set，每次改动必跑
- **LLM-as-judge**：用强模型打分，需人工校准、防位置偏见
- **RAG 评测**：RAGAS / TruLens，分别评检索与生成
- **Tracing**：OpenTelemetry `gen_ai` 语义约定已成通用标准，Langfuse / LangSmith / Braintrust / Datadog 都支持
- **版本管理**：prompt、模型、工具定义都要有版本，能回滚
- **Guardrails**：输入输出过滤、注入检测、PII 脱敏
- **缓存侧信道**：prompt caching 会通过时序泄漏「这段内容是否被缓存过」，多租户场景要隔离

**公司实践**：所有上生产的团队；金融/医疗额外要求审计日志与数据驻留。

**关键指标**：回归通过率、幻觉率、注入拦截率、PII 泄漏事件数

**常见误区**：用同一批 prompt 既调优又评测——等于把测试集背下来了。

## 4. 三条主线（建议按主线学，而不是按类别学）

**主线 A：缓存**
KV cache → 前缀缓存 → 厂商 prompt cache → 跨实例 KV 池 → 语义缓存。
同一思想逐层上移：**「这段计算/数据，别人是不是已经算过了？」**

**主线 B：摊销**
continuous batching → chunked prefill → PD 分离 → Agent 并发 / 子 agent。
同一思想：**「一次资源投入，摊到更多请求上。」**

**主线 C：上下文**
RAG → 长上下文 → 上下文工程（compaction / 子 agent / 文件系统记忆）。
同一思想：**「上下文是内存，不是硬盘；要换页，不要全量常驻。」**

**生产标配**（不自研也必须懂，面试必问）

**前沿 / 试点**（值得关注，但别急着上生产）

## 7. 自测

<details>
<summary>1. 为什么前缀缓存要求「从第 0 个 token 开始完全一致」？</summary>

因为缓存的是**前缀**的 KV，KV 是按位置累积算出来的。第 k 个 token 的 KV 依赖它前面所有 token 的注意力结果。若第 k 位变了，k 之后所有位置的 KV 都要重算。所以缓存命中必须是「从头开始的一段连续相同前缀」，不是「中间某一段相同」。
</details>

<details>
<summary>2. 一个 8B 模型、128k 上下文，KV cache 大概多大？为什么这个数字重要？</summary>

以 Llama-3-8B 为例（32 层、8 个 KV head、head_dim 128、FP16）：
2 × 32 × 8 × 128 × 2 B = 128 KiB/token。
128k 上下文 ≈ 16 GB，和模型权重（16 GB）一样大。
重要在于：长上下文场景下 KV 会**超过模型本身**，这才是 PagedAttention、KV 量化、offload、驱逐策略存在的根本原因。
</details>

<details>
<summary>3. PD 分离在什么情况下不划算？</summary>

规模小、prompt 短、或跨节点带宽不足时。KV 传输的时间和显存开销可能超过它省下的干扰损失。通常要中大规模 + 长 prompt + 高速互联（NVLink/RDMA）才有正收益。
</details>

<details>
<summary>4. context rot 是什么？它和「上下文窗口越大越好」矛盾吗？</summary>

指上下文 token 增多时，模型准确召回其中信息的能力**下降**。不矛盾：窗口是硬上限，有效注意力是软约束。边际收益递减意味着「塞满窗口」往往不如「精选高信号 token」。
</details>

<details>
<summary>5. 判断一个新技术值不值得学的三个问题？</summary>

① 它省的是算力、显存还是上下文？② 它在什么规模下不划算？③ 上线后看哪个指标能验证？
</details>
