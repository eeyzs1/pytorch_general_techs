# 缓存与上下文复用：从 KV cache 到语义缓存

> 本文是 [`00-技术地图.md`](00-技术地图.md) 第 3 类的深潜。
> 一句话结论：**LLM 系统里最大、最容易拿到的浪费，是把同一段 prefill 算了无数遍。**
> 读完这篇看 [`02-高命中率实战.md`](02-高命中率实战.md)：命中率怎么量化、2026 的新技术（PIC/EPIC、HiCache、KV 池化）、落地顺序。

---

## 1. 先算一笔账

一个典型的 Agent 应用：2 万 token 的系统提示 + 工具定义，会话 20 轮，每轮新增 2k token。

| | 输入 token 总量 | 计费（读 0.1×、写 1.25×） | 相对成本 |
|---|---|---|---|
| 无缓存 | Σ(20k + 2k·i) = **780k** | 780k | 100% |
| 有前缀缓存 | 写 58k，读 722k | 58k×1.25 + 722k×0.1 ≈ **145k** | **18.6%** |

**省 81%，而且不改一行 prompt 逻辑。**

这不是理论值。PwC 在 2026 年对 OpenAI / Anthropic / Google 三家旗舰模型的实测：**成本降 41–80%，TTFT 改善 13–31%**；prompt 涨到 5 万 token 时，GPT-5.2 成本降 89%、Claude Sonnet 4.5 降 88%。([Don't Break the Cache, arXiv:2601.06007](https://arxiv.org/html/2601.06007))

## 2. 缓存到底在缓什么：六层模型

```
用户请求
   │
   ├─ L6 应用结果缓存   embedding / rerank / 检索结果 / 工具结果
   │        ↓ miss
   ├─ L5 语义缓存       相似问题直接返回答案（向量库 + 阈值）
   │        ↓ miss
   ├─ L3 厂商 prompt cache  跨请求的前缀 KV（落在厂商侧）
   │        ↓ miss
   ├─ L4 跨实例 KV 池   LMCache / llm-d / 3FS，副本之间共享
   │        ↓ miss
   ├─ L2 前缀缓存       本副本内，按 block 匹配相同前缀
   │        ↓ miss
   └─ L1 KV cache       本次请求内部，decode 阶段复用 prefill 的结果
```

| 层 | 缓存对象 | 存在哪 | 谁管理 | 命中条件 | 量级收益 | 典型失效原因 |
|---|---|---|---|---|---|---|
| L1 | 当前请求的 KV | GPU 显存 | 推理引擎 | 自动 | decode 的前提 | 请求结束即释放 |
| L2 | 跨请求前缀 KV | GPU 显存（可 offload CPU） | vLLM APC / SGLang RadixAttention | 前缀逐字节一致，按 block 对齐 | TTFT ↓ 50–90% | 前缀任意位置改动 |
| L3 | 前缀 KV | 厂商侧 | OpenAI / Anthropic / Google / DeepSeek | 显式断点或自动检测 | 输入价 0.1–0.5× | TTL 过期、前缀改动 |
| L4 | KV block | CPU / SSD / 远端 | LMCache、llm-d、3FS | 前缀 hash + 路由亲和 | 跨副本 TTFT ↓ 4× | 元数据不一致、驱逐 |
| L5 | 问答对 | Redis / 向量库 | 应用 / 网关 | 语义相似度 ≥ 阈值 | 整次调用跳过 | 误命中、时效性 |
| L6 | 中间结果 | 任意 | 应用 | 业务 key | 省一次子调用 | key 设计不当 |

**关键认知：L1–L4 缓的是「KV」，L5–L6 缓的是「答案」。** 前者永远安全（KV 是精确的），后者有正确性风险。这个区别决定了它们该用在哪。

## 3. L1：KV cache 为什么决定一切

### 3.1 一个公式

```
每 token 的 KV 大小 = 2 × n_layers × n_kv_heads × head_dim × dtype_bytes
```

| 模型 | 每 token KV | 128k 上下文 |
|---|---|---|
| Llama-3-8B（32 层 / 8 KV head / 128 dim / FP16） | 128 KiB | **16 GB** |
| Llama-3-70B（80 层 / 8 KV head / 128 dim / FP16） | 320 KiB | **40 GB** |
| DeepSeek MLA 架构 | 压缩数倍至一个数量级 | 显著更小 |

注意第二行：**128k 上下文的 KV，比 8B 模型本身的权重（16 GB）还大。** 这就是为什么长上下文如此昂贵，也是 PagedAttention、KV 量化、offload、驱逐策略存在的全部理由。

### 3.2 PagedAttention 解决了什么

朴素做法是给每个请求预分配「最大长度」的连续显存 → 内部碎片 + 外部碎片，实测浪费 60–80%。

PagedAttention 借用操作系统的虚拟内存思想：
- KV 切成固定大小的 block（如 16 token）
- 逻辑上连续，物理上离散，用 block table 映射
- 相同前缀的 block 可以**共享**（copy-on-write），这是前缀缓存的物理基础

### 3.3 decode 是 memory-bound

生成每个 token 都要把全部权重和全部 KV 从 HBM 读一遍，但只做一次矩阵向量乘。所以：
- 提高 batch size 能摊薄权重读取 → 吞吐上去
- 但 KV 会随 batch 线性膨胀 → 显存先爆

这个矛盾（**吞吐靠 batch，显存怕 batch**）是推理引擎所有调度的出发点。

## 4. L2：前缀缓存（Prefix Caching / RadixAttention）

### 4.1 原理

把 KV block 组织成**前缀树（radix tree）**。新请求进来，沿树逐 block 匹配：

```
已有树：                新请求： "你是助手…[工具定义]…[文档A]…问题2"
root
 └─ "你是助手…"          ← 命中
     └─ "[工具定义]…"    ← 命中
         ├─ "[文档A]…"   ← 命中，直接复用这棵子树的 KV
         │   ├─ "问题1"
         │   └─ "问题2"  ← 本次请求，只算这一小段
         └─ "[文档B]…"
```

命中部分**跳过 prefill**，直接从最后一个命中 block 继续算。省下的是实打实的算力，不是 IO。

### 4.2 三条硬性命中条件

1. **必须从第 0 个 token 开始一致。** 第 k 位变了，k 之后全部作废（KV 是位置相关的累积结果）
2. **按 block 对齐。** 通常 16 token 一个 block，未对齐的尾巴不缓存
3. **同一副本内。** 这是 L2 的天然边界，也是 L4 存在的理由

### 4.3 怎么开

```bash
# vLLM（v1 引擎默认开启，显式声明更保险）
vllm serve meta-llama/Llama-3.1-8B-Instruct \
  --enable-prefix-caching \
  --gpu-memory-utilization 0.85

# 观察指标（Prometheus）
#   vllm:gpu_prefix_cache_hit_rate      前缀命中率
#   vllm:gpu_kv_cache_usage_perc        KV 显存占用
#   vllm:num_requests_waiting           排队数（判断是否该扩容）

# SGLang：RadixAttention 默认开启，调度策略默认 lpm（最长前缀优先）
python -m sglang.launch_server --model-path meta-llama/Llama-3.1-8B-Instruct \
  --schedule-policy lpm
```

`lpm`（Longest Prefix Match）这个细节值得记：调度器**优先跑前缀最长的请求**，因为它们最可能命中缓存，等于把缓存收益纳入调度目标。这是「缓存感知调度」的第一个例子。

## 5. L3：厂商 prompt caching

### 5.1 三家 + 一家的控制模式

| 供应商 | 触发方式 | 最小长度 | 缓存粒度 | TTL | 经济性 |
|---|---|---|---|---|---|
| **OpenAI** | 自动，无需配置 | ~1024 tok | 前缀，按 128 token 递增 | 数分钟（自动清理） | 读约 0.1–0.5×，无写费 |
| **Anthropic** | **显式** `cache_control` 断点（最多 4 个） | 1024（Sonnet/Opus）/ 2048（Haiku） | 到断点为止的前缀 | 5 min，可延长到 1 h | 读 0.1×，写 1.25× |
| **Google Gemini** | 隐式（自动）+ 显式 `cachedContent` | 1024–4096（按模型） | 前缀 | 显式可自定义 | 读约 0.25×；显式按小时收存储费 |
| **DeepSeek** | 自动，落盘缓存 | — | 前缀 | 数小时至天 | 命中约 0.1× |

> 数字随版本变动，**上生产前务必查官方 pricing 页**。但模式差异是稳定的：**OpenAI/DeepSeek 自动且免写费，Anthropic 手动但折扣最深，Google 两种都有**。

### 5.2 三种缓存策略，实测差别很大

同一批 Agent 任务，只改「缓存边界」：

| 策略 | 做法 | 成本 | TTFT |
|---|---|---|---|
| Full context | 全缓存，不管内容 | 好 | **可能变差** |
| System prompt only | 只在系统提示末尾打断点 | 好 | **最稳** |
| Exclude tool results | 系统提示 + 每个工具结果后都打断点 | 好 | 好 |

**反直觉的结论：全量缓存有时 TTFT 更差。** 因为动态的工具结果也被写入缓存，写了却不会再被读到，纯付写入开销。GPT-4o 的 full-context 模式 TTFT 甚至退化 8.8%，而 system-prompt-only 改善 30.9%。

**结论**：缓存不是「开得越多越好」，而是「只缓存会被复用的东西」。

### 5.3 Anthropic 的断点怎么放

```python
messages = [{
    "role": "user",
    "content": [
        # 稳定：系统指令 + 工具 + few-shot
        {"type": "text", "text": SYSTEM_PROMPT,
         "cache_control": {"type": "ephemeral"}},      # ← 断点 1
        # 半稳定：大块资料
        {"type": "text", "text": KNOWLEDGE_BASE,
         "cache_control": {"type": "ephemeral"}},      # ← 断点 2
        # 易变：本轮输入放最后
        {"type": "text", "text": user_query},
    ],
}]
```

规则：**断点打在「稳定内容」的末尾，最多 4 个，从后往前数命中优先级最高。**

## 6. L4：跨实例 KV 复用

### 6.1 缓存孤岛问题

生产上通常是 4 个 vLLM 副本挂在负载均衡后面，每个副本各自建缓存：

```
4 副本 × 10 GB 本地 KV 缓存 = 理论 40 GB
但每个请求只能用到自己落到的那个副本 → 有效容量仍是 10 GB
```

结果：重复计算、缓存命中率被副本数稀释、同机内存还被重复占用。

### 6.2 三种解法

| 方案 | 做法 | 优点 | 代价 |
|---|---|---|---|
| 远端 KV 池 | Redis / S3 / 3FS 统一存 | 容量近乎无限 | 多一个有状态服务，TCP 延迟 |
| **P2P 共享** | 副本之间直接传 KV（NIXL + RDMA） | 无额外服务，延迟低 | 容量受集群 RAM 限制 |
| 缓存亲和路由 | 网关按前缀 hash 把请求打到「有这份缓存」的副本 | 不用搬数据 | 需要网关能看到缓存元数据 |

**实测数据**（LMCache P2P，腾讯 + LMCache 团队，2026-01）：两个副本，10k 上下文 × 50 次查询，第二个副本从对等节点拉 KV：

```
实例 1（冷启动，自己 prefill）:  mean TTFT 2.028s,  轮次总时长 38.3s
实例 2（复用实例 1 的 KV）:      mean TTFT 0.490s,  轮次总时长  7.96s
                                → TTFT 4×，总时长 5×
```

有意思的是工程细节：他们最终选的元数据结构是**前缀树（RegistryTree）**而不是扁平哈希索引——扁平索引查询快（89 μs）但内存 19.7 GB、注销 worker 要 32 秒；树结构查询 8 ms，但内存 5.9 GB、注销 8 ms。**规模化系统里，「能弹性伸缩」比「单次查询快」重要。**

### 6.3 llm-d：把这件事做进 Kubernetes

llm-d 的思路是把「KV 缓存感知」下沉到网关层：Gateway 知道每个 pod 持有哪些前缀，配合 vLLM 的 KV 事件做亲和路由。这样 PD 分离、KV 池化、亲和路由三件事在同一套控制面里。

### 6.4 什么时候值得上 L4

- 副本数 ≥ 4，且流量有明显的前缀集中（同一 system prompt / 同一批文档）
- 单请求上下文 ≥ 8k（传输成本占比可接受）
- 有 RDMA 或高速内网

否则，**先优化 L2/L3 的命中率，收益更大且零成本。**

## 7. L5：语义缓存

### 7.1 原理与适用面

把 query 做 embedding，和缓存里的历史 query 比相似度，超过阈值就返回历史答案——**连模型都不调**。

适用：FAQ、客服、内部知识问答、低风险高重复流量。
不适用：个性化、时效性强、需要精确计算、多轮有状态的对话。

### 7.2 三个必须防的坑

| 坑 | 表现 | 防法 |
|---|---|---|
| **误命中** | 「怎么取消订单」命中「怎么修改订单」 | 阈值 ≥ 0.95 起步，按业务校准；加意图分类做前置门 |
| **多租户串味** | A 公司的问题命中 B 公司的答案 | key 里强制带 tenant_id |
| **时效性** | 缓存了去年的价格 | TTL + 版本号；数据变更时主动失效 |

### 7.3 建议

只在**「低风险 + 高重复 + 答案稳定」**的流量上开，并且必须留审计日志（记录命中哪条、相似度多少），否则出问题无法排查。

工具：GPTCache、Redis LangCache、Portkey，或自己在网关里写 50 行。

## 8. L6：应用结果缓存（最容易被忽略）

| 缓存对象 | key | 收益 |
|---|---|---|
| Embedding | 文本 hash + 模型版本 | 大文档重复入库时不重复计费 |
| Rerank 结果 | query hash + doc ids | 省一次 cross-encoder 调用 |
| 检索结果 | query hash + 索引版本 | 省一次向量库往返 |
| 工具结果 | 工具名 + 参数 hash + TTL | Agent 反复查同一接口 |
| 结构化抽取 | 文档 hash + schema 版本 | 批量处理同一批文档 |

**注意**：工具结果缓存和上下文工程会打架——如果你用 tool-result clearing 清掉了结果，又靠缓存重新取回，逻辑上是自洽的；但如果工具结果本身会变（股价、库存），缓存就是 bug。

## 9. 命中率工程：12 条 checklist

按收益从高到低排：

1. **稳定内容前置，动态内容后置。** 一条规则解决 80% 的问题
2. **绝不在 system prompt 开头放时间戳 / 用户 ID / request ID。** 这是最常见的「缓存杀手」
3. **工具定义固定且顺序稳定。** 动态工具集会整段失效；用 MCP 分层或 code-gen 替代动态 function list
4. **对话历史只追加，不重写。** 任何「重排历史」的操作都会毁掉缓存
5. **compaction 挑时机。** 摘要替换历史 = 缓存全毁，别每轮都做
6. **显式断点放在大块稳定内容之后**（Anthropic 最多 4 个，从后往前用）
7. **多副本一定开缓存亲和路由**，否则命中率被副本数整除
8. **同一租户 / 同一文档的请求尽量同源**（会话粘性）
9. **TTL 对齐业务节奏**：会话内交互要 > 5 min，否则聊到一半缓存过期
10. **前缀要够长**：低于 1k–4k token 的最小阈值，缓存根本不激活
11. **监控「读/写比」**：写入多、读取少 = 缓存在赔钱
12. **不要在热路径做随机 A/B 分流**，随机分流会随机打散前缀

## 10. 度量：怎么证明它真的生效了

### 10.1 三个核心指标

```python
# 1. 前缀命中率（按 token 加权，不是按请求数）
hit_rate = cached_read_tokens / (cached_read_tokens + uncached_prefill_tokens)

# 2. 真实成本节省
saving = 1 - (read_tok * p_read + write_tok * p_write + new_tok * 1.0) \
             / (total_tok * 1.0)

# 3. TTFT 分解（定位瓶颈在哪一段）
ttft = queue_time + prefill_time(cached, uncached) + first_decode_time
```

### 10.2 埋点建议

在**请求级**记录一行结构化日志：

```json
{
  "ts": "...", "tenant": "acme", "route": "claude-sonnet",
  "prefix_hash": "a3f9...", "prompt_tokens": 21240,
  "cached_tokens": 20480, "cache_write_tokens": 0,
  "ttft_ms": 412, "total_ms": 3180, "cost_usd": 0.0021
}
```

有了 `prefix_hash`，你能直接回答「哪些前缀最常被复用」「哪些前缀只出现一次（不值得缓存）」。

### 10.3 看板看什么

- 命中率 **P50 与 P95 分开看**——平均值会被少数超长请求带偏
- **每会话成本**（而不是每请求），Agent 场景更真实
- **缓存 ROI** = 读命中省下的钱 − 写缓存多付的钱；为负说明策略错了

## 11. 反模式清单

| 反模式 | 后果 | 修法 |
|---|---|---|
| system prompt 开头放 `当前时间：2026-10-21 19:51` | 命中率恒为 0 | 移到最末尾，或改用 user message |
| 每次请求重新生成工具列表（按用户权限裁剪、顺序随机） | 前缀抖动，缓存全失效 | 固定全集 + 运行时校验权限；或把工具说明放最后 |
| 多轮中改 system prompt（「你现在是…」） | 整段重算 | 角色切换用新会话，或放进 user message |
| 每轮都做 compaction | 缓存永远建不起来 | 按 token 阈值触发（如 150k），且用「追加式摘要」 |
| 轮询负载均衡 | 4 副本 = 命中率 ÷ 4 | 前缀亲和路由 / 会话粘性 |
| 语义缓存阈值 0.8 | 答非所问且难排查 | ≥ 0.95 + 意图前置 + 审计日志 |
| 缓存检索结果但不设 TTL | 返回过期信息 | 索引版本号进 key |
| 把「缓存命中率」当唯一 KPI | 刷高命中率但成本没降（缓存了没用的东西） | 同时看 ROI 与每会话成本 |

## 12. 一个缓存友好的 prompt 模板

```
┌─ 稳定（永不变）────────────────────────────┐
│ 角色 / 任务 / 输出格式约束                  │
│ 工具定义（固定顺序，固定措辞）              │
│ few-shot 示例                              │
└──────────── cache breakpoint ① ────────────┘
┌─ 半稳定（同会话/同文档内不变）─────────────┐
│ 大块资料：代码库、文档、知识库快照          │
└──────────── cache breakpoint ② ────────────┘
┌─ 增长（只追加）────────────────────────────┐
│ 会话历史（user / assistant / tool 交替）    │
└────────────────────────────────────────────┘
┌─ 易变（每轮都变，永远放最后）──────────────┐
│ 本轮检索结果 / 用户输入 / 当前时间          │
└────────────────────────────────────────────┘
```

配套的工程约束：

```python
def build_prompt(system: str, tools: list, docs: str, history: list, query: str):
    # 1. 稳定段做内容 hash，只有变化时才重建（并可告警）
    stable = system + render_tools(sorted(tools))   # 排序保证顺序稳定
    # 2. 动态值绝不出现在 stable 里
    assert not re.search(r"\d{4}-\d{2}-\d{2}", stable), "时间戳污染了稳定前缀"
    # 3. 易变内容拼在最后
    return stable + docs + render(history) + query
```

## 13. 自测

<details>
<summary>1. 为什么「把时间戳移到 prompt 末尾」能救回命中率？</summary>

缓存匹配的是**从第 0 个 token 开始的连续前缀**。时间戳在开头 → 第 0 个 token 就不同 → 整段作废。移到末尾 → 前面几万 token 全部命中，只有最后几个 token 需要重算。
</details>

<details>
<summary>2. 4 个副本、每个 10 GB 本地 KV 缓存，总容量是 40 GB 吗？</summary>

不是。**有效容量仍是 10 GB**——每个请求只能用到它落到的那台机器的缓存。这是「缓存孤岛」，也是 L4（KV 池化 / P2P / 亲和路由）要解决的问题。
</details>

<details>
<summary>3. 为什么全量缓存有时比只缓存 system prompt 更慢？</summary>

动态内容（工具结果）也被写入缓存，但不会被再次读到——纯付写入开销，没有读取收益。实测 GPT-4o 的 full-context 模式 TTFT 退化 8.8%，而 system-prompt-only 改善 30.9%。
</details>

<details>
<summary>4. 语义缓存和 KV 缓存的本质区别是什么？</summary>

KV 缓存缓的是**精确的计算中间态**，命中即等价，**永远安全**。语义缓存缓的是**答案**，靠相似度近似匹配，**有误命中风险**。所以前者可以默认开，后者只在低风险高重复流量上开。
</details>

<details>
<summary>5. 一个 20 轮会话，system 20k、每轮新增 2k，开了前缀缓存后成本剩多少？</summary>

无缓存总量 = 20×20k + 2k×(0+…+19) = 780k。
开缓存后：写 58k（20k + 19×2k），读 722k。
按读 0.1×、写 1.25× 计：58×1.25 + 722×0.1 = 144.7k 等价 token，**约为原来的 18.6%，省 81%**。
</details>
