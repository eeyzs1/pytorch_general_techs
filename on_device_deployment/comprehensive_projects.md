## 项目一：量化算法对比实验

### 目标
对同一个模型，实现并对比至少 3 种量化方法，撰写量化报告。

### 场景设定
你是某 AI 公司的推理优化工程师。CTO 要求你在下周技术评审会上给出明确的量化方案推荐。需要对同一模型跑通多种量化方法，用数据说话。

### 任务分解

#### Step 1：模型准备（30 min）
- 选择一个预训练语言模型（推荐：Qwen2.5-0.5B 或 GPT-2 small）
- 加载模型并记录基线性能（参数量、模型大小、推理速度、Perplexity）
- 准备 128-256 条校准数据

#### Step 2：实现 3 种量化方法（2-3h）
必须包含：
1. **对称逐张量 INT8 量化**（最基础，作为下界）
2. **逐组 INT4 量化**（group_size=128，中等水平）
3. **AWQ 风格 INT4 量化**（激活感知，参考课程 9.1 的实现）

可选加分：
4. SmoothQuant 风格 W8A8
5. 使用 GPTQ 官方库

#### Step 3：系统化评估（1-2h）
对每种量化方法，测量并记录：

| 指标 | 测量方法 |
|------|---------|
| 模型大小 | 理论压缩比 + 实际文件大小（如导出 GGUF） |
| 逐层权重余弦相似度 | 各层的量化前后余弦相似度，找最敏感的层 |
| Perplexity（WikiText-2 或自定义测试集） | 量化前后的 PPL 变化 |
| 输出 Token 分布一致性 | 同一输入下，量化前后 Top-5/10 token 的重叠率 |
| 推理速度 | Prefill（256/512 tokens）和 Decode（单 token）的延迟 |
| 内存峰值 | 推理时的最大内存占用 |

#### Step 4：撰写量化选型报告（1h）

报告结构：
```
1. 实验环境（硬件、PyTorch版本、模型信息）
2. 方法概述（每种量化方法的原理一句话 + 关键参数）
3. 精度对比（表格 + 逐层余弦相似度折线图）
4. 性能对比（延迟、内存、吞吐的柱状图）
5. 综合分析（精度-性能的帕累托前沿，找最优 trade-off）
6. 推荐方案（针对不同场景的量化推荐）
7. 附录：复现步骤
```

### 交付物
- 一个 Jupyter Notebook（包含完整实验代码和分析）
- 一份量化选型报告（Markdown/PDF）

### 自评检查清单
- [ ] 至少实现了 3 种不同的量化方法
- [ ] 所有量化方法的逐层余弦相似度都 > 0.95
- [ ] 包含精度、速度、内存三个维度的对比
- [ ] 推荐方案有明确的适用场景说明
- [ ] 代码可以完整复现（从头跑到尾不出错）
- [ ] 图表清晰，有轴标签和图例

### 提示
- 如果模型太小（<50M 参数），量化带来的性能差异可能不明显——可以用更大的模型或更多层来放大效果
- 逐层余弦相似度要找最敏感的层：通常第一层和最后一层对量化最敏感
- PPL 不是唯一精度指标——输出 token 分布一致性有时更能反映用户体感

## 项目二：设计一个端侧友好的轻量级架构

### 目标
从零设计一个小型语言模型架构，专门为端侧推理优化，并对比标准架构的性能。

### 场景设定
你的团队在开发一款离线翻译 App，目标硬件是 2 年前的安卓中端机（骁龙 7 Gen1，4GB 可用内存）。你需要设计一个模型架构，在 500M-1B 参数量下，最大化推理速度和翻译质量。

### 任务分解

#### Step 1：基线架构搭建（1-2h）
- 实现一个标准 GPT-2 风格的小型 Transformer（约 500M 参数）
- 包含标准 MHA（8-12 头）、GELU 激活、LayerNorm
- 在 CPU 上测量基线性能

#### Step 2：逐个应用优化策略（3-4h）
按以下顺序逐步优化，每步都记录变化：

**优化 A：GQA 替换 MHA**
- 从 MHA（12 头）改为 GQA（4 组 KV，12 个 Q 头）
- 测量 KV Cache 大小变化和推理速度变化

**优化 B：ReLU² 替换 GELU**
- 标准 GELU 包含 erf 计算（需要查表或近似），端侧 NPU 可能不支持
- ReLU² = ReLU(x)² 同样有非线性，但仅需乘法和比较
- 对比两者的推理速度和精度差异

**优化 C：RMSNorm 替换 LayerNorm**
- LayerNorm 需要计算均值和方差（两次遍历）
- RMSNorm 只需要均方根（一次遍历），计算量减半
- 对比精度损失

**优化 D：Weight Tying**
- 输入 Embedding 和输出 LM Head 共享权重
- 测量参数量节省

**优化 E：（加分项）尝试更深更窄的设计**
- 参考 MobileLLM 的思路，在相同参数量下尝试不同的深度×宽度比例
- 如：16层×256维 vs 8层×512维

#### Step 3：最终架构对比（1-2h）
将优化后的架构与基线进行全维度对比：

| 维度 | 基线架构 | 优化架构 | 变化 |
|------|---------|---------|------|
| 参数量 | | | |
| KV Cache 大小（seq_len=1024） | | | |
| Prefill 延迟（512 tokens） | | | |
| Decode 延迟（单 token） | | | |
| Perplexity（测试集） | | | |
| 端侧内存占用估算 | | | |

#### Step 4：架构设计文档（1-2h）
撰写设计文档，解释每个优化决策的权衡和理由。

### 交付物
- 一个 Jupyter Notebook（包含基线架构和优化架构的完整实现 + 对比实验）
- 一份架构设计文档（说明每个选择的理由）

### 自评检查清单
- [ ] 包含了至少 4 项架构优化（GQA、激活函数、归一化层、权重共享等）
- [ ] 每项优化都有量化的前后对比数据
- [ ] 最终架构的 KV Cache 比基线减少 50% 以上
- [ ] 推理速度有可测量的提升（>15%）
- [ ] 精度损失 < 5%（PPL 或下游任务）
- [ ] 文档中解释了每项优化的"为什么"而不是"做了什么"

## 项目三：硬件选型决策模拟

### 目标
基于课程第 5 章的硬件知识和 benchmark 数据，为一个具体的业务场景做完整的硬件选型分析。

### 场景设定
你是一家 AI 创业公司的技术负责人，正在做一款"智能会议录音笔"产品。产品需求：
- 实时录音转文字 + 要点摘要（运行 1.5B-3B 参数的语言模型）
- 电池续航 ≥ 8 小时（持续使用）
- 设备成本（芯片部分）< $50
- 首 token 延迟 < 500ms
- 离线运行（不依赖网络）

### 任务分解

#### Step 1：候选硬件调研（1-2h）
基于课程第 5 章和第 10 章的知识，列出至少 4 个候选硬件平台：

建议覆盖：
- 高通骁龙系列（如 7 Gen3、8 Gen2）
- 联发科天玑系列
- 瑞芯微 RK3588
- 地平线/华为昇腾边缘芯片
- Apple Silicon（如果产品支持 iOS）

对每个候选硬件，收集：
- 标称 NPU 算力（TOPS）
- 内存带宽
- 可用内存（芯片支持的最大 RAM）
- TDP（热设计功耗）
- 芯片批量采购价格
- SDK 成熟度和 LLM 算子支持度

利用课程 5.3/5.4 的 Roofline 分析工具：

| 生态（SDK+算子支持） | 10% | | | | |
| 成本（芯片价格） | 10% | | | | |

#### Step 4：敏感性分析（30 min）
- 如果续航要求从 8h 放宽到 4h，推荐会变吗？
- 如果模型从 1.5B 升级到 3B，推荐会变吗？

#### Step 5：选型报告（1h）

## 项目四：端到端部署流水线实战

### 目标
从 HuggingFace 模型出发，完成量化 → 导出 → 推理 → 基准测试 → 故障排查的完整链路。

### 场景设定
你需要将一个开源模型部署到端侧设备。模型已经选定，量化方案需要你设计，部署后需要证明精度和性能达标。

### 任务分解

#### Step 1：模型选型与基线建立（1h）
- 从 HuggingFace 选择一个 1B-3B 参数的模型（推荐：Qwen2.5-1.5B 或 SmolLM2-1.7B）
- 加载模型，跑通基线推理
- 记录基线 Perplexity 和推理速度

#### Step 2：量化方案设计（2-3h）
你需要自己决定量化策略，而不是照搬课程代码。至少回答以下问题：
- 用什么量化算法？为什么？（考虑目标硬件的精度支持）
- W 多少 bit？A 多少 bit？为什么？
- group_size 选多少？为什么？
- 需要校准数据吗？多少条？
- 不同层需要不同精度吗？（混合精度）

实现你选择的量化方案并验证精度。

#### Step 3：模型导出（1-2h）
选择一条导出路径并实现：
- **GPU 路径**：导出 GGUF（使用 llama.cpp 的 convert 脚本或自己实现 GGUF 格式写入）
- **ONNX 路径**：导出 ONNX → 用 ONNX Runtime 推理验证
- 如果硬件条件允许，可以两条路径都做

#### Step 4：基准测试（1-2h）
设计并执行完整的基准测试方案：
- Prefill 阶段：测试不同输入长度（128, 256, 512, 1024）的 TTFT
- Decode 阶段：测试 ITL 均值和 P95/P99
- 内存：测试不同 seq_len 下的峰值内存
- 画 TTFT-seq_len 曲线和内存-seq_len 曲线

#### Step 5：故障排查模拟（1-2h）
人为制造 2 个故障并演示排查过程。故障可以从以下选择：
1. **量化精度异常**：故意对某一层用过大的 group_size，导致精度异常，然后演示如何通过逐层余弦相似度定位问题层
2. **内存模拟泄漏**：模拟 KV Cache 没有被正确释放，演示内存增长曲线和排查方法
3. **算子不兼容**：模拟 ONNX 导出时某个自定义算子导致导出失败，演示如何分解算子

#### Step 6：部署报告（2h）
撰写正式的部署报告：

```
1. 项目概述
   - 目标模型、目标硬件、使用场景
2. 量化方案设计
   - 方案选择的逻辑链
   - 量化参数配置及理由
3. 精度验证
   - 逐层余弦相似度
   - PPL 对比
   - 输出一致性
4. 性能基准
   - TTFT 曲线
   - ITL 统计
   - 内存占用
5. 故障排查记录（模拟）
6. 部署检查清单验证
7. 结论与后续优化建议
```

### 交付物
- 一个 Jupyter Notebook（完整流水线代码）
- 部署报告（Markdown/PDF）
- 量化后的模型文件（或模型导出结果截图）

### 自评检查清单
- [ ] 量化方案有明确的选择理由（不是照抄课程）
- [ ] 逐层余弦相似度 > 0.99（至少 90% 的层）
- [ ] PPL 变化 < 5%
- [ ] 包含了 TTFT 和 ITL 的多场景基准测试
- [ ] 模拟了至少 2 个故障并演示了排查过程
- [ ] 报告专业、可复现、结构清晰

## 项目五：多平台部署方案的完整设计与对比

### 目标
针对同一个模型，设计 3 条不同的部署路径（CPU/GPU/NPU），对比它们的优劣势，给出最终推荐。

### 场景设定
你的产品需要在以下 3 类设备上运行同一个 AI 功能：

| 设备类型 | 代表硬件 | 约束 |
|---------|---------|------|
| 旗舰手机 | 骁龙 8 Elite（Hexagon NPU + Adreno GPU） | 可用内存 5GB，需利用 NPU |
| 中端手机 | 骁龙 7 Gen3（仅有 CPU + 小 GPU） | 可用内存 3GB，NPU 不够强 |
| 桌面/笔记本 | Intel i7 + RTX 4060 / Apple M 系列 | 可用内存 8GB+，按需选择 |

你需要为每种设备设计最优部署方案，并给出跨平台的统一推荐。

### 任务分解

#### Step 1：统一模型选择（1h）
选择一个 3B 左右参数的模型（如 Qwen2.5-3B），确保它能在这 3 类设备上都跑起来。

#### Step 2：路径 A — CPU 部署方案（llama.cpp）（2-3h）
- 选择 GGUF 量化格式（Q4_K_M / Q5_K_M / Q8_0 等）
- 使用 llama.cpp 或 llama-cpp-python 做推理
- 测量不同量化格式的精度-速度 trade-off
- 分析：哪些 K-Quant 变体（Q4_K_S vs Q4_K_M）适合什么场景？

#### Step 3：路径 B — GPU 部署方案（2-3h）
选择以下之一：
- **NVIDIA**：TensorRT-LLM 或 vLLM + AWQ 量化
- **Apple Silicon**：MLC-LLM 或 Core ML 转换
- **通用 GPU**：ONNX Runtime + CUDA/ROCm EP

设计并测试 GPU 推理方案的性能。

#### Step 4：路径 C — NPU 部署方案（模拟）（2-3h）
由于大多数人没有 NPU 开发板，本项目用模拟方式完成：
- 调研目标 NPU（如高通 QNN）的算子兼容性列表
- 对模型做算子兼容性检查（哪些算子不支持？需要分解？）
- 设计算子分解方案（不能直接跑的算子怎么拆？）
- 撰写 NPU 部署方案文档（如果真实硬件可用，加分）
- 估算 NPU 推理性能（基于课程 5.1 的参考数据）

#### Step 5：跨平台对比分析（2-3h）

| 维度 | CPU (llama.cpp) | GPU (TensorRT/MLC) | NPU (QNN模拟) |
|------|:---:|:---:|:---:|
| 模型体积 | | | |
| TTFT (512 tokens) | | | |
| ITL | | | |
| 峰值内存 | | | |
| 功耗估算 | | | |
| 开发复杂度 | | | |
| 可维护性 | | | |
| 跨平台兼容性 | | | |

#### Step 6：最终推荐与实施路线图（1-2h）
给产品经理写一份推荐方案：
- 如果只选一条路径，推荐哪条？为什么？
- 如果预算允许做两条路径，优先级怎么排？
- 3 个月的实施路线图（里程碑、风险、依赖）

### 交付物
- 3 个独立的部署方案文档（CPU/GPU/NPU 各一份）
- 一份跨平台对比分析报告
- 一份最终推荐方案（面向非技术决策者）

### 自评检查清单
- [ ] 3 条路径都有可运行或可验证的方案
- [ ] 每个方案都有 quantifiable 的性能数据
- [ ] 跨平台对比表格完整
- [ ] 最终推荐有清晰的优先级和路线图
- [ ] NPU 方案（即使模拟的）有严肃的算子兼容性分析
- [ ] 至少包含一个"遇到问题→排查→解决"的完整记录

## 产业应用案例参考

> 以下案例展示了端侧部署技术在实际产品中的典型应用，帮助理解技术选型与工程取舍。

### 案例一：手机 AI 助手（Apple Intelligence / Samsung Galaxy AI）

| 维度 | Apple Intelligence (iOS 18.2+) | Samsung Galaxy AI (Galaxy S24+) |
|------|-------------------------------|-------------------------------|
| **基础模型** | ~3B 自研模型（云端大模型补充） | Gemini Nano (1.8B) + Gemini Pro（云端） |
| **芯片** | A17 Pro / A18 Pro (ANE + GPU) | 骁龙 8 Gen 3 (Hexagon NPU) |
| **量化** | FP16 + 部分INT8 | INT4 (W4A16) |
| **部署框架** | Core ML + MLX 技术栈 | ExecuTorch + QNN Delegate |
| **端侧功能** | 文本改写/摘要/通知优先级/Genmoji | 实时翻译/摘要/搜索/圈选搜索 |
| **端云协同** | 简单任务端侧，复杂任务路由到 Private Cloud Compute | 端侧优先，超出能力路由到 Gemini Pro 云端 |
| **内存限制** | 端侧模型 <2GB，与系统共享内存 | 端侧模型 ~1.5GB，需与系统应用共存 |
| **隐私设计** | 端侧数据不上云；云端推理用 Secure Enclave 加密 | 端侧处理优先；用户可选择不使用云端 |

**技术启示**：
- 端侧 3B 模型 + 云端大模型的级联架构是手机 AI 的主流方案
- 端侧模型不需要"万能"，只需覆盖高频简单任务（摘要、改写、分类）
- ANE/NPU 的能效比远高于 GPU，持续推理时必须用 NPU 避免电池快速消耗

### 案例二：车载语音交互系统

| 维度 | 方案 |
|------|------|
| **场景需求** | 语音唤醒 → ASR → NLU/LLM → TTS，全链路延迟 <500ms |
| **硬件** | 骁龙 8295 / 车规级 Orin + NPU |
| **模型组合** | KWS(唤醒词) 1M + ASR(Conformer) 80M + LLM(Qwen-1.8B INT4) 1.2GB + TTS(VITS) 50M |
| **总内存** | ~2GB（车机通常有 8-16GB 可用） |
| **关键优化** | 流式 ASR（边听边识别）、LLM 流式输出（首 token <200ms）、TTS 流式合成（不等 LLM 完整输出） |
| **离线要求** | 隧道/地下车库无网络时必须全离线运行 |
| **热管理** | 车载环境温度高（-40°C~85°C），需降频保护，推理性能可能下降 30-50% |

**技术启示**：
- 车载场景对延迟极其敏感，全链路必须流式处理
- 离线能力是刚需，不能依赖云端
- 车规级芯片的算力通常低于同期手机芯片（如 8295 vs 8 Gen 3），需更激进的量化

### 案例三：离线翻译 App

| 维度 | 方案 |
|------|------|
| **场景需求** | 旅行场景的实时对话翻译，无网络可用 |
| **硬件** | 中端手机（骁龙 7 Gen 1 / 天玑 8100） |
| **模型组合** | ASR(Whisper-tiny 39M) + NMT(Qwen-0.5B INT4 350MB) + TTS(轻量声码器 20M) |
| **总内存** | ~500MB（中端手机可接受） |
| **量化策略** | ASR: INT8 / NMT: INT4 / TTS: FP16 |
| **语言对** | 中英/中日/中韩等高频语言对，低频语言对按需下载 |
| **延迟** | 端到端 <1s（短句），用户可接受 |
| **包体积** | 基础包 50MB + 每语言对包 400MB，按需下载 |

**技术启示**：
- 0.5B 级别的小模型在 INT4 量化下可满足旅行翻译的基本需求
- 按需下载语言包是控制 App 体积的关键策略
- 翻译质量不如云端大模型，但离线可用性是核心卖点

### 案例四：端侧代码补全

| 维度 | 方案 |
|------|------|
| **场景需求** | IDE 内实时代码补全，延迟 <100ms/建议 |
| **硬件** | 开发者笔记本（M2 Pro / RTX 4060） |
| **模型** | DeepSeek-Coder-1.3B INT4（~700MB）或 Qwen2.5-Coder-1.5B INT4 |
| **部署框架** | MLX (macOS) / llama.cpp (跨平台) / Ollama |
| **上下文策略** | 滑动窗口取光标前后 512 token，FIM（Fill-in-the-Middle）格式 |
| **延迟优化** | KV Cache 复用（同一文件的上下文不重复计算）、推测解码 |
| **vs 云端 Copilot** | 延迟更低（无网络延迟）、隐私更好（代码不上传）、但模型能力有限 |

**技术启示**：
- 1-1.5B 代码模型在 INT4 下已具备实用的补全能力
- FIM（Fill-in-the-Middle）格式对代码补全至关重要，需选择支持 FIM 训练的模型
- KV Cache 复用是降低延迟的关键——每次光标移动只需计算新增 token

### 案例五：智能会议录音笔

| 维度 | 方案 |
|------|------|
| **场景需求** | 实时录音转写 + 摘要 + 待办提取，续航 >8h |
| **硬件** | 专用设备：ARM A55 + 小型 NPU（如瑞芯微 RK3588S） |
| **模型组合** | VAD(语音活动检测) + ASR(Paraformer 70M INT8) + 摘要(Qwen-0.5B INT4) |
| **总内存** | ~600MB |
| **功耗预算** | ASR: 0.5W / 摘要: 2W（仅会议结束后生成）/ 待机: 0.1W |
| **关键优化** | VAD 驱动的间歇式推理（无人说话时 ASR 休眠）、摘要延迟生成（非实时） |
| **续航** | ASR 持续 6h + 摘要 10min ≈ 8h 续航 |

**技术启示**：
- 功耗敏感设备必须区分"实时"和"非实时"任务，摘要等可延迟任务在空闲时执行
- VAD 驱动的间歇推理可节省 40-60% 的 ASR 功耗
- 专用设备的算力远低于手机，需用更小的模型和更激进的量化

### 案例六：AR/VR 实时交互

| 维度 | 方案 |
|------|------|
| **场景需求** | 实时场景理解 + 语音交互 + 虚拟角色对话，端到端延迟 <50ms |
| **硬件** | Meta Quest 3（骁龙 XR2 Gen 2） / Apple Vision Pro (M2) |
| **模型组合** | 场景理解(轻量VLM 200M) + ASR + LLM(1B INT4) + TTS |
| **总内存** | ~2GB（与渲染共享 8-12GB 统一内存） |
| **关键挑战** | 渲染已占用大部分 GPU/NPU 算力，LLM 只能用剩余算力 |
| **调度策略** | 渲染优先（90fps 不可中断），LLM 推理在渲染间隙执行 |
| **延迟优化** | LLM 用推测解码减少前向次数；场景理解用 INT8 降低计算量 |

**技术启示**：
- AR/VR 是最严苛的端侧场景——渲染和 AI 共享同一芯片，算力竞争激烈
- 必须采用"渲染优先、AI 填隙"的调度策略
- 统一内存架构（如 Vision Pro 的 M2）在此场景有天然优势，无需数据拷贝

## 项目六：端侧 Agent 产品最小闭环

### 目标

### 场景设定

做一款离线「口袋助理」MVP：能查电量/设闹钟（可扩展），低电量自动降级，模型文件防篡改，并提供网页试用页。

### 任务分解

1. **选型（Ch13）**：用 `13.1_model_selection.ipynb` 为「中文 + 轻 Agent + ≤2.5GB」选出主模型与降级模型  
2. **服务（Ch7.4/7.5）**：实现优先级队列 + 电量/温度策略；文生图与 LLM 分时（参考内存 pin/unpin）  
3. **Agent（Ch14）**：至少 2 个本地工具 + JSON 约束；失败重试不超过 1 次  
4. **入口（Ch7.6 或 Ch15）**：二选一加深  
   - 浏览器：基于 `browser_demo/index.html` 写清 WebLLM 接入说明与内存上限

5. **安全（Ch17）**：打包「权重 + HMAC 签名 + 设备 license」，演示篡改与换机失败
