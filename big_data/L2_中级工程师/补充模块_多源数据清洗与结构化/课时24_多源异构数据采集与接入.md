## 二、数据源分类与特征

真实企业的数据来源五花八门，按"结构化程度"可分为四大类。先认清每类源的延迟特征和 Schema 稳定性，才能选对采集方式。

### 2.1 四大类数据源

```
数据源分类全景:

┌─────────────────────────────────────────────────────────────┐
│                      企业数据源全景                          │
└─────────────────────────────────────────────────────────────┘
        ┌──────────────┬──────────────┬──────────────┐
        ▼              ▼              ▼              ▼
  ┌───────────┐ ┌───────────┐ ┌───────────┐ ┌───────────┐
  │ 结构化源   │ │半结构化源  │ │非结构化源  │ │  实时源    │
  │           │ │           │ │           │ │           │
  │ MySQL     │ │ REST API  │ │ 聊天记录   │ │ Kafka     │
  │ PostgreSQL│ │ GraphQL   │ │ 邮件.eml  │ │ WebSocket │
  │ Oracle    │ │ JSON 日志 │ │ 富文本/PDF │ │ CDC binlog│
  │ SQLServer │ │ CSV/XML   │ │ 工单附件   │ │ MQTT      │
  └───────────┘ └───────────┘ └───────────┘ └───────────┘
```

### 2.2 各类源特征对比

| 数据源类型 | 典型代表 | 延迟 | Schema稳定性 | 典型采集方式 |
|-----------|---------|------|-------------|-------------|
| 结构化源 | MySQL/PostgreSQL/Oracle | T+1 批或秒级 | 高（DDL受控） | Sqoop/DataX 全量或增量 |
| 半结构化源 | REST API/JSON日志/CSV | 分钟~小时级 | 中（字段可能增减） | API拉取/文件落HDFS/Spark读 |
| 非结构化源 | 邮件.eml/聊天导出/富文本/PDF | 小时~天级 | 低（无固定Schema） | Python解析→结构化→入仓 |
| 实时源 | Kafka/WebSocket/CDC binlog | 毫秒~秒级 | 中（需Schema Registry） | Flink CDC/Kafka Connect |

### 2.3 选型要点

- **结构化源**：源端 DBA 把控严格，Schema 变更走流程，采集最简单，是数仓 ODS 层的主要来源
- **半结构化源**：API 返回的 JSON 字段会随业务迭代增减，日志格式可能临时变更，需要处理 Schema 漂移
- **非结构化源**：本身没有 Schema，采集阶段只能"原样落盘"，结构化工作放到课时25
- **实时源**：延迟低但对下游稳定性要求高，binlog 顺序性和断点续传是工程难点

## 三、采集模式选型

### 3.1 三种采集模式

```
三种采集模式对比:

全量采集 (Full Load):
  源表 ──(全表SELECT)──→ ODS分区(dt=当天)
  特点: 每次拉全表，覆盖目标分区
  适合: 表小(百万级以内)、需要每日快照、源端无更新时间戳

增量采集 (Incremental):
  源表 ──(WHERE id > 上次值)──→ 追加到ODS
  特点: 只拉新增/变更数据
  适合: 表大、有自增主键或更新时间戳、对历史快照无需求

CDC实时采集 (Change Data Capture):
  源表binlog ──(实时流)──→ Kafka ──→ 实时ODS/数仓
  特点: 毫秒~秒级捕获行级变更(INSERT/UPDATE/DELETE)
  适合: 实时报表、对延迟敏感、需要捕获删除操作
```

### 3.2 三种模式优缺点

| 维度 | 全量采集 | 增量采集 | CDC实时采集 |
|------|---------|---------|------------|
| 延迟 | T+1（小时~天） | T+1 或小时级 | 秒级 |
| 源端压力 | 高（全表扫描） | 低（带条件过滤） | 低（读binlog不查表） |
| 实现复杂度 | 低 | 中（需维护水位） | 高（需运维Kafka/Flink） |
| 历史快照 | 有（每日全量） | 无（需合并） | 无（需合并） |
| 删除捕获 | 不支持 | 不支持 | 支持 |
| 数据一致性 | 简单（覆盖分区） | 复杂（需合并去重） | 复杂（需幂等写入） |
| 典型工具 | Sqoop/DataX | Sqoop incremental/DataX | Flink CDC/Debezium |

### 3.3 决策树：什么场景用什么模式

```
采集模式决策树:

                    数据源是关系型DB?
                   /              \
                 是                 否
                 /                   \
            延迟要求?              数据源类型?
           /        \             /    |    \
        秒级      T+1          API  文件/日志  消息队列
          |         |           |      |        |
       CDC实时   表数据量?     API拉取  落HDFS   Kafka直连
                  /    \
               <百万    >百万
                |        |
             全量      有更新时间戳?
                       /        \
                     有           无
                     |            |
                  增量采集        全量采集
```

**决策原则**：
1. 实时报表 → CDC实时采集
2. 小表 + 需要每日快照 → 全量采集
3. 大表 + 有更新时间戳 → 增量采集
4. 大表 + 无更新时间戳 → 全量采集（或推动源端补字段）
5. 需要捕获 DELETE 操作 → 只有 CDC 能做到

## 四、Schema 漂移问题与处理

### 4.1 什么是 Schema 漂移

Schema 漂移（Schema Drift）指源端数据结构在采集过程中发生变化，导致下游采集任务失败或数据丢失。常见三类变化：

```
Schema 漂移的三种表现:

源表原始结构:                    漂移后结构:
┌────────────────────┐          ┌────────────────────────┐
│ order_info         │          │ order_info             │
│  - order_id        │          │  - order_id            │
│  - user_id         │   ──→    │  - user_id             │
│  - total_amount    │          │  - total_amount        │
│  - create_time     │          │  - create_time         │
│                    │          │  - channel      (新增) │ ← 漂移1: 加字段
└────────────────────┘          │  - total_amount(STRING)│ ← 漂移2: 改类型
                                │  (删除 payment_amount) │ ← 漂移3: 删字段
                                └────────────────────────┘
```

| 漂移类型 | 危害 | 举例 |
|---------|------|------|
| 新增字段 | 下游表无对应列，新数据丢失 | 源表加 `channel` 字段，ODS表读不到 |
| 类型变更 | 解析失败或精度丢失 | `total_amount` 从 DECIMAL 改 STRING |
| 字段删除 | 下游依赖该字段的任务报错 | 删除 `payment_amount`，DWD 宽表 JOIN 失败 |

### 4.2 三种应对策略

```
Schema 漂移应对策略对比:

策略1: Fail Fast（快速失败）
  - 检测到Schema变化立即报错，人工介入
  - 适合: 关键业务表，不容忍静默丢数据
  - 工具: Great Expectations Schema检查 / Spark 显式Schema

策略2: 容错吸收（Schema Evolution）
  - 自动吸收新增字段，类型变更按规则转换
  - 适合: 探索性数据、日志类、Schema频繁迭代
  - 工具: Spark mergeSchema / Parquet schema evolution

策略3: Schema Registry（集中管控）
  - 源端变更走注册中心，下游按版本订阅
  - 适合: Kafka流式场景、多团队协作
  - 工具: Confluent Schema Registry / AWS Glue Schema Registry
```

| 策略 | 实现难度 | 适用场景 | 缺点 |
|------|---------|---------|------|
| Fail Fast | 低 | 核心业务表、强一致性要求 | 频繁报错，需人工介入 |
| 容错吸收 | 中 | 日志、JSON、Schema迭代快 | 新字段可能长期无人感知 |
| Schema Registry | 高 | Kafka流式、多团队 | 需要源端配合注册，改造成本高 |

### 4.3 代码示例：Spark 处理 JSON 新增字段

```python
"""
schema_drift_spark.py
演示 Spark 读取 JSON 时处理 Schema 漂移的三种方式
"""
from pyspark.sql import SparkSession
from pyspark.sql.functions import col
from pyspark.sql.types import StructType, StructField, LongType, StringType, DoubleType

spark = SparkSession.builder \
    .appName("SchemaDriftDemo") \
    .getOrCreate()

# 假设 /data/json/orders/ 下有新旧两种结构的JSON文件
# 旧文件: {"order_id":1, "user_id":100, "total_amount":99.5}
# 新文件: {"order_id":2, "user_id":200, "total_amount":88.0, "channel":"APP"}

# ===== 方式1: Fail Fast —— 显式定义Schema，多余字段忽略，缺失字段报错 =====
strict_schema = StructType([
    StructField("order_id", LongType(), False),
    StructField("user_id", LongType(), False),
    StructField("total_amount", DoubleType(), False),
])

df_strict = spark.read \
    .schema(strict_schema) \
    .json("/data/json/orders/")
# 注意: 显式Schema下，新增的channel字段会被直接丢弃，不报错
# 若旧字段缺失则该列为null，可结合质量检查发现
df_strict.printSchema()
df_strict.show()

# ===== 方式2: 容错吸收 —— mergeSchema自动合并新旧字段 =====
df_merge = spark.read \
    .option("mergeSchema", "true") \
    .json("/data/json/orders/")
# mergeSchema=true 会把所有文件中出现过的字段合并到统一Schema
# 旧文件没有channel字段，对应行为null；新文件有channel字段，正常读取
df_merge.printSchema()
df_merge.show()

# 检测Schema漂移: 对比本次Schema与基线Schema
baseline_columns = {"order_id", "user_id", "total_amount"}
current_columns = set(df_merge.columns)
new_columns = current_columns - baseline_columns
dropped_columns = baseline_columns - current_columns

if new_columns:
    print(f"[警告] 检测到新增字段: {new_columns}")
if dropped_columns:
    print(f"[警告] 检测到字段缺失: {dropped_columns}")

# ===== 方式3: 容错吸收 + 脏数据隔离 —— columnNameOfCorruptRecord =====
# 对于类型不一致的脏记录，单独存到一列便于排查
df_tolerant = spark.read \
    .option("mergeSchema", "true") \
    .option("mode", "PERMISSIVE") \
    .option("columnNameOfCorruptRecord", "_corrupt_record") \
    .json("/data/json/orders/")

# 解析失败的整行会被写入 _corrupt_record 列，方便后续排查
corrupt_count = df_tolerant.filter(col("_corrupt_record").isNotNull()).count()
print(f"脏数据记录数: {corrupt_count}")

spark.stop()
```

### 4.4 Schema Registry 简述（Kafka 场景）

```
Confluent Schema Registry 工作流:

生产者 ──(序列化数据+SchemaID)──→ Kafka Topic ──→ 消费者
   │                                              │
   │  1.生产者先向Registry注册Schema               │  4.消费者按SchemaID从Registry拉Schema
   │  2.Registry校验兼容性(BACKWARD/FORWARD)       │  5.按Schema反序列化数据
   │  3.返回SchemaID                              │
   ▼                                              ▼
┌──────────────────┐
│ Schema Registry  │
│  - schema_1: v1  │  ← 旧版本
│  - schema_2: v2  │  ← 新增channel字段(BACKWARD兼容)
└──────────────────┘

兼容性规则:
  BACKWARD: 新Schema能读旧数据(新增字段必须有默认值)
  FORWARD:  旧Schema能读新数据(删除字段必须有默认值)
  FULL:     同时满足BACKWARD和FORWARD
```

Schema Registry 通常在 Kafka 流式采集链路中使用，离线批量采集场景用 Spark `mergeSchema` + 质量检查即可满足绝大多数需求。

## 五、采集工具实战

### 5.1 Sqoop（DB → 数仓，全量 + 增量）

Sqoop 是 Hadoop 生态经典的 DB↔HDFS 互导工具，项目4 已用它做 MySQL 全量导入 ODS。本节补充增量模式。

> 参考 [项目4 离线数仓构建](../../L1_初级工程师/第11-14周_项目实战/项目4_离线数仓构建.md) 中的 Sqoop 全量用法保持一致。

#### 5.1.1 全量采集（与项目4一致）

```bash
# 全量导入 user_info 到 HDFS（与项目4 ods_etl.py 中的用法一致）
sqoop import \
    --connect jdbc:mysql://mysql:3306/ecommerce \
    --username root \
    --password root123 \
    --table user_info \
    --target-dir /data/ods/user_info/2024-01-15/ \
    --delete-target-dir \
    --num-mappers 4 \
    --fields-terminated-by ',' \
    --null-string '\\N' \
    --null-non-string '\\N'
```

#### 5.1.2 增量采集（append 模式）

适用于有自增主键、且只追加不更新的表（如日志表、订单明细）。

```bash
# 增量导入 order_detail，按自增主键 id 追加
sqoop import \
    --connect jdbc:mysql://mysql:3306/ecommerce \
    --username root \
    --password root123 \
    --table order_detail \
    --target-dir /data/ods/order_detail/ \
    --incremental append \
    --check-column detail_id \
    --last-value 100000 \
    --num-mappers 4 \
    --fields-terminated-by ','
# --incremental append: 追加模式，只拉 check-column > last-value 的记录
# --check-column:       用于判断增量的列（必须是自增且不回退）
# --last-value:         上次采集到的最大值，需在调度系统持久化保存
```

#### 5.1.3 增量采集（lastmodified 模式）

适用于有 `updated_at` 时间戳、会发生 UPDATE 的表（如用户信息、订单主表）。

```bash
# 按 updated_at 时间戳增量拉取变更记录
sqoop import \
    --connect jdbc:mysql://mysql:3306/ecommerce \
    --username root \
    --password root123 \
    --table order_info \
    --target-dir /data/ods/order_info_inc/2024-01-15/ \
    --incremental lastmodified \
    --check-column updated_at \
    --last-value '2024-01-14 00:00:00' \
    --append \
    --num-mappers 4 \
    --fields-terminated-by ','
# --incremental lastmodified: 按时间戳增量，能捕获INSERT和UPDATE
# --append: 增量数据追加到目标目录，不覆盖历史
# 注意: lastmodified模式无法捕获DELETE操作，需CDC才能做到
```

#### 5.1.4 用 Sqoop job 持久化水位

```bash
# 创建Sqoop job，自动保存last-value，避免手动维护水位
sqoop job --create inc_order_detail \
    -- import \
    --connect jdbc:mysql://mysql:3306/ecommerce \
    --username root \
    --password root123 \
    --table order_detail \
    --target-dir /data/ods/order_detail/ \
    --incremental append \
    --check-column detail_id \
    --last-value 0 \
    --num-mappers 4

# 执行job（Sqoop会自动从 metastore 读取并更新 last-value）
sqoop job --exec inc_order_detail

# 查看当前水位
sqoop job --show inc_order_detail
```

### 5.2 DataX（异构 DB 互导）

DataX 是阿里开源的异构数据源互导工具，相比 Sqoop 不依赖 Hadoop 集群，适合单机或无 HDFS 环境下的 DB↔DB 互导。

#### 5.2.1 核心概念

```
DataX 架构:

┌─────────────────────────────────────────┐
│              DataX Job                  │
│  ┌───────────────────────────────────┐  │
│  │          Job (JSON配置)           │  │
│  │  ┌─────────┐     ┌─────────────┐  │  │
│  │  │ Reader  │ ──→ │   Writer    │  │  │
│  │  │(读插件) │     │  (写插件)    │  │  │
│  │  └─────────┘     └─────────────┘  │  │
│  └───────────────────────────────────┘  │
│          │                              │
│     切分Task                             │
│  ┌───────┼───────┐                      │
│  ▼       ▼       ▼                      │
│ Task1  Task2  TaskN   (并行执行)        │
└─────────────────────────────────────────┘

常用插件:
  Reader: mysqlreader / postgresqlreader / hdfsreader / txtfilereader / httpreader
  Writer: mysqlwriter / hdfswriter / txtfilewriter / oraclescriptwriter
```

#### 5.2.3 DataX vs Sqoop 选型

| 维度 | Sqoop | DataX |
|------|-------|-------|
| 依赖 | 依赖Hadoop/HDFS | 单机可跑，无Hadoop依赖 |
| 数据源 | DB↔HDFS 为主 | 支持异构DB/文件/HTTP互导 |

| 部署 | 需Hadoop集群 | 解压即用 |
| 适用 | 已有Hadoop生态 | 无Hadoop或跨DB同步 |

### 5.3 Flink CDC（实时增量）

Flink CDC 内嵌 Debezium，直接读取 MySQL binlog，无需额外部署 Kafka Connect，一条 SQL 即可接入实时流。

#### 5.3.1 Flink CDC 工作流

```
Flink CDC 实时采集链路:

MySQL binlog ──(Debezium内嵌)──→ Flink Table ──→ 下游Sink
                                     │
                                     ├── 写入 Kafka (供多消费)
                                     ├── 写入 Iceberg/Hudi (实时湖仓)
                                     └── 写入 ClickHouse (实时报表)

特点:
  - 无需独立部署 Kafka Connect/Debezium
  - 一条SQL定义Source，支持DDL同步
  - 支持断点续传（binlog位点持久化到Flink checkpoint）
  - 支持UPDATE/DELETE捕获（需配置changelog模式）
```

#### 5.3.2 Flink SQL 定义 CDC Source

```sql
-- 在 Flink SQL Client 中执行
-- 创建 CDC Source 表，对接 MySQL order_info
CREATE TABLE cdc_order_info (
    order_id BIGINT,
    user_id BIGINT,
```

```python
"""
email_collector.py
通过 IMAP 协议拉取邮箱中的工单邮件，保存为 .eml 文件并记录元信息
"""
import imaplib
import email
from email.header import decode_header
import os
from datetime import datetime, timedelta

# 邮箱配置（以QQ邮箱为例，其他邮箱需替换IMAP服务器）
IMAP_SERVER = "imap.qq.com"
IMAP_PORT = 993
EMAIL_ACCOUNT = "support@example.com"
EMAIL_PASSWORD = "授权码而非登录密码"  # 各邮箱需开启IMAP并生成授权码

# 本地落盘目录
RAW_DIR = "/data/raw/email"
META_LOG = "/data/raw/email/_meta.log"


def decode_mime_header(value):
    """解码邮件头（Subject/From等可能带编码）"""
    if value is None:
        return ""
    parts = decode_header(value)
    result = []
    for text, charset in parts:
        if isinstance(text, bytes):
            result.append(text.decode(charset or "utf-8", errors="replace"))
        else:
            result.append(text)
    return "".join(result)


def collect_emails(since_date):
    """拉取指定日期以后的邮件，原样保存为.eml"""
    os.makedirs(RAW_DIR, exist_ok=True)
    collected = 0

    # 连接IMAP服务器
    mail = imaplib.IMAP4_SSL(IMAP_SERVER, IMAP_PORT)
    mail.login(EMAIL_ACCOUNT, EMAIL_PASSWORD)
    mail.select("INBOX")

    # 按日期搜索邮件
    # IMAP日期格式: 15-Jan-2024
    date_str = since_date.strftime("%d-%b-%Y")
    status, data = mail.search(None, f'(SINCE {date_str})')
    if status != "OK":
        print(f"[错误] 搜索邮件失败: {data}")
        return 0

    mail_ids = data[0].split()
    print(f"[信息] 自 {date_str} 起共找到 {len(mail_ids)} 封邮件")

    for mail_id in mail_ids:
        # 拉取完整邮件内容（RFC822格式）
        status, msg_data = mail.fetch(mail_id, "(RFC822)")
        if status != "OK":
            continue

        raw_email = msg_data[0][1]
        msg = email.message_from_bytes(raw_email)

        # 解析元信息
        subject = decode_mime_header(msg.get("Subject"))
        sender = decode_mime_header(msg.get("From"))
        date = msg.get("Date")
        message_id = msg.get("Message-ID", "")

        # 原样保存.eml文件（保留完整原始内容，便于后续解析）
        safe_id = message_id.strip("<>").replace("/", "_") or f"mail_{mail_id.decode()}"
        eml_path = os.path.join(RAW_DIR, f"{safe_id}.eml")
        with open(eml_path, "wb") as f:
            f.write(raw_email)

        # 记录元信息到日志（供后续结构化提取用）
        with open(META_LOG, "a", encoding="utf-8") as f:
            f.write(f"{safe_id}\t{date}\t{sender}\t{subject}\t{eml_path}\n")

        collected += 1

    mail.logout()
    print(f"[完成] 共保存 {collected} 封邮件到 {RAW_DIR}")
    return collected


if __name__ == "__main__":
    # 拉取最近7天的邮件
    since = datetime.now() - timedelta(days=7)
    collect_emails(since)
```

#### 5.5.2 解析 .eml 文件提取结构化字段

```python
"""
eml_parser.py
解析已落盘的 .eml 文件，提取正文、附件、发件人等结构化字段
输出为 JSONL 供后续入仓
"""
import email
from email.header import decode_header
from email.utils import parsedate_to_datetime
import os
import json
import re

RAW_DIR = "/data/raw/email"
OUT_PATH = "/data/structured/email_tickets.jsonl"


def get_email_body(msg):
    """提取邮件正文，优先返回纯文本，其次HTML"""
    text_body = ""
    html_body = ""
    attachments = []

    if msg.is_multipart():
        for part in msg.walk():
            content_disposition = str(part.get("Content-Disposition", ""))
            content_type = part.get_content_type()

            if "attachment" in content_disposition:
                # 附件：记录文件名和大小，正文不存二进制
                filename = decode_mime_header(part.get_filename())
                payload = part.get_payload(decode=True)
                attachments.append({
                    "filename": filename,
                    "size": len(payload) if payload else 0,
                })
            elif content_type == "text/plain":
                payload = part.get_payload(decode=True)
                charset = part.get_content_charset() or "utf-8"
                text_body = payload.decode(charset, errors="replace")
            elif content_type == "text/html":
                payload = part.get_payload(decode=True)
                charset = part.get_content_charset() or "utf-8"
                html_body = payload.decode(charset, errors="replace")
    else:
        payload = msg.get_payload(decode=True)
        charset = msg.get_content_charset() or "utf-8"
        text_body = payload.decode(charset, errors="replace")

    return text_body, html_body, attachments


def parse_eml_to_record(eml_path):
    """单个.eml文件解析为一条结构化记录"""
    with open(eml_path, "rb") as f:
        msg = email.message_from_bytes(f.read())

    subject = decode_mime_header(msg.get("Subject"))
    sender = decode_mime_header(msg.get("From"))
    date_str = msg.get("Date")
    try:
        send_time = parsedate_to_datetime(date_str).isoformat() if date_str else ""
    except Exception:
        send_time = date_str or ""

    text_body, html_body, attachments = get_email_body(msg)

    # 简单提取工单号（假设subject格式: [工单T20250715-001] 退款问题）
    ticket_match = re.search(r"\[工单([^\]]+)\]", subject)
    ticket_id = ticket_match.group(1) if ticket_match else ""

    # 提取发件人邮箱
    email_match = re.search(r"[\w.+-]+@[\w-]+\.[\w.-]+", sender)
    sender_email = email_match.group(0) if email_match else ""

    return {
        "ticket_id": ticket_id,
        "subject": subject,
        "sender": sender,
        "sender_email": sender_email,
        "send_time": send_time,
        "text_body": text_body.strip(),
        "html_body": html_body.strip(),
        "attachment_count": len(attachments),
        "attachments": attachments,
        "source_file": eml_path,
    }


def batch_parse():
    """批量解析目录下所有.eml，输出JSONL"""
    os.makedirs(os.path.dirname(OUT_PATH), exist_ok=True)
    count = 0
    with open(OUT_PATH, "w", encoding="utf-8") as out:
        for filename in os.listdir(RAW_DIR):
            if not filename.endswith(".eml"):
                continue
            eml_path = os.path.join(RAW_DIR, filename)
            try:
                record = parse_eml_to_record(eml_path)
                out.write(json.dumps(record, ensure_ascii=False) + "\n")
                count += 1
            except Exception as e:
                print(f"[警告] 解析失败 {filename}: {e}")
    print(f"[完成] 共解析 {count} 封邮件，输出到 {OUT_PATH}")


if __name__ == "__main__":
    batch_parse()
```

#### 5.5.3 聊天记录导出文件的格式与解析思路

各聊天工具的导出格式不同，需针对处理。采集阶段的重点是"原样落盘 + 记录来源元信息"，结构化提取放课时25。

```
常见聊天导出格式:

1. 微信（个人/企业微信）导出:
   - 个人微信: 第三方工具导出为 HTML/TXT（无官方导出API）
     格式示例: "张三  2024-01-15 10:30:25\n你好，请问退款怎么操作？"
   - 企业微信: 提供 会话存档 API（需企业开通且合规审批）
     格式: 通过回调获取结构化JSON消息体

2. 钉钉:
   - 提供 机器人/群消息 API，可主动拉取
   - 导出为 JSON，字段: msgId/senderId/sendTime/content/msgType

3. 通用处理思路:
   原始导出文件 ──(正则/解析器)──→ 消息序列 ──(字段化)──→ 结构化表
     │                              │              │
     │ 落HDFS /data/raw/chat/       │ 提取发送人    │ msg_id/sender/
     │ 按日期分区                    │ 提取时间      │ send_time/content/
     │                              │ 提取正文      │ channel/session_id
```

```python
"""
chat_export_parser.py
解析微信/企业微信导出的 TXT 聊天记录，输出为结构化 JSONL
适用于 "昵称  时间\n消息内容" 格式的导出文件
"""
import os
import re
import json
from datetime import datetime

RAW_FILE = "/data/raw/chat/wechat_export_2024-01-15.txt"
OUT_PATH = "/data/structured/chat_messages.jsonl"

# 匹配行: "昵称  2024-01-15 10:30:25"
MSG_HEADER_PATTERN = re.compile(
    r"^(.+?)\s{2,}(\d{4}-\d{2}-\d{2}\s+\d{2}:\d{2}:\d{2})$"
)


def parse_chat_export(raw_path, channel="wechat"):
    """解析聊天导出TXT，输出结构化消息列表"""
    messages = []
    current_sender = ""
    current_time = ""
    current_lines = []

    with open(raw_path, "r", encoding="utf-8") as f:
        for line in f:
            line = line.rstrip("\n")
            match = MSG_HEADER_PATTERN.match(line)
            if match:
                # 命中新消息头，先把上一条消息收尾
                if current_sender:
                    messages.append({
                        "channel": channel,
                        "sender": current_sender,
                        "send_time": current_time,
                        "content": "\n".join(current_lines).strip(),
                        "session_id": os.path.basename(raw_path).replace(".txt", ""),
                    })
                current_sender = match.group(1).strip()
                current_time = match.group(2)
                current_lines = []
            else:
                # 消息正文行
                if current_sender:
                    current_lines.append(line)

    # 收尾最后一条
    if current_sender:
        messages.append({
            "channel": channel,
            "sender": current_sender,
            "send_time": current_time,
            "content": "\n".join(current_lines).strip(),
            "session_id": os.path.basename(raw_path).replace(".txt", ""),
        })

    return messages


def main():
    os.makedirs(os.path.dirname(OUT_PATH), exist_ok=True)
    if not os.path.exists(RAW_FILE):
        print(f"[跳过] 原始文件不存在: {RAW_FILE}")
        return

    messages = parse_chat_export(RAW_FILE, channel="wechat")
    with open(OUT_PATH, "w", encoding="utf-8") as out:
        for msg in messages:
            out.write(json.dumps(msg, ensure_ascii=False) + "\n")
    print(f"[完成] 解析 {len(messages)} 条消息，输出到 {OUT_PATH}")


if __name__ == "__main__":
    main()
```

> 提醒：微信/企业微信/钉钉的导出能力受各平台合规限制，企业内部接入前需走数据合规审批。本节代码仅用于解析"已合规获取"的导出文件。

### 练习2：处理 Schema 漂移的代码练习（30min）

**场景**：ODS 层的 `app_feedback` 表，源端 MySQL 在 2024-01-15 新增了 `feedback_score` 字段（INT），但 Hive ODS 表没有该字段。

**任务**：用 Spark 完成以下三件事：
1. 读取 `/data/ods/app_feedback/` 下所有 JSON 文件，自动合并新旧字段
2. 检测出新增字段并打印告警
3. 把新增字段补到 Hive ODS 表中（ALTER TABLE ADD COLUMNS）

**参考代码**：

```python
"""
practice_schema_drift.py
练习: 检测并处理 Schema 漂移
"""
from pyspark.sql import SparkSession
from pyspark.sql.functions import col

spark = SparkSession.builder \
    .appName("SchemaDriftPractice") \
    .enableHiveSupport() \
    .getOrCreate()

# 1. 读取所有JSON文件，mergeSchema自动吸收新增字段
df = spark.read \
    .option("mergeSchema", "true") \
    .json("/data/ods/app_feedback/")

print("当前Schema:")
df.printSchema()

# 2. 检测新增字段（与Hive ODS表基线对比）
baseline_columns = set(spark.table("ods.ods_app_feedback").columns)
current_columns = set(df.columns)
new_columns = current_columns - baseline_columns
dropped_columns = baseline_columns - current_columns

if new_columns:
    print(f"[告警] 检测到新增字段: {new_columns}")
if dropped_columns:
    print(f"[告警] 检测到字段缺失: {dropped_columns}")

# 3. 补字段到Hive ODS表（仅当有新增字段时）
if new_columns:
    # 推断新增字段类型
    alter_sql_parts = []
    for col_name in new_columns:
        col_type = df.schema[col_name].dataType.simpleString()
        alter_sql_parts.append(f"`{col_name}` {col_type} COMMENT '新增字段-待补充注释'")
    alter_sql = f"ALTER TABLE ods.ods_app_feedback ADD COLUMNS ({', '.join(alter_sql_parts)})"
    print(f"[执行DDL] {alter_sql}")
    spark.sql(alter_sql)
    print("[完成] ODS表已补充新字段，后续分区将携带新字段写入")
else:
    print("[信息] 未检测到Schema漂移")

# 4. 写入当日分区（含新字段）
df.write \
    .mode("overwrite") \
    .insertInto("ods.ods_app_feedback", overwrite=True)

spark.stop()
```

## 七、小结

本课时从数据源分类出发，讲清了三类采集模式的选型、Schema 漂移的应对策略，并实战了五种主流采集工具。核心结论：**结构化源用 Sqoop/DataX 批量采，实时源用 Flink CDC/Kafka Connect 流式采，非结构化源用 Python 原样落盘再结构化**。

| 数据源类型 | 推荐采集工具 | 推荐采集模式 | Schema漂移应对 |
|-----------|-------------|-------------|---------------|
| 结构化DB（小表） | Sqoop / DataX | 全量 | Fail Fast + 显式Schema |
| 结构化DB（大表） | Sqoop incremental | 增量（append/lastmodified） | 质量检查监控 |
| 结构化DB（实时） | Flink CDC | CDC实时 | Schema Registry |
| 半结构化（API/JSON） | Python + Spark | 全量/增量 | mergeSchema容错吸收 |
| 半结构化（CSV/XML） | DataX / Spark | 全量 | 显式Schema + 质量检查 |
| 非结构化（邮件/聊天） | Python IMAP/解析器 | 全量落盘 | 原样保存，结构化放课时25 |
| 实时消息（Kafka） | Kafka Connect / Flink | 流式 | Schema Registry |
