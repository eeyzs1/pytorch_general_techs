# 补充模块：多源数据清洗与结构化

> **所属阶段**：L2 中级工程师 | **模块类型**：补充模块 | **总时长**：约 55h | **难度**：★★★★☆ | **前置**：L1 Spark SQL、L2 课时23 数据质量

---

## 一、为什么需要这个模块

### 真实痛点

现有教程的 [课时23_数据质量与元数据管理](../补充模块_数据治理实操/课时23_数据质量与元数据管理.md) 解决的是"数据符合不符合规则"（完整性、唯一性等**结构化校验**），但**没有解决**下面这类问题：

> 数据来自多个渠道——聊天客服记录、APP 提交表单、邮件工单、第三方 API。同一个用户在不同渠道用不同身份（手机号/邮箱/微信OpenID/设备ID），同一个地区名写成"北京"/"北京市"/"BJ"/"Beijing"，同一个商品名在不同平台有不同 SKU 编码。这些数据**采集进来没法直接用**，必须经过清洗、对齐、标准化才能入仓分析。

本模块就是补齐这条"**多源异构数据 → 可分析的结构化数据**"的完整链路。

### 与现有模块的边界

| 模块 | 解决的问题 | 不解决的问题 |
|------|-----------|-------------|
| 课时23 数据质量 | 结构化数据的规则校验（完整性/唯一性等） | 数据怎么从脏变干净 |
| 课时22 湖仓实战 | Schema 演化、表格式选型 | 数据进湖仓前怎么清洗 |
| **本模块** | **多源采集 → 非结构化解析 → 清洗 → 实体对齐 → 结构化入仓** | — |

本模块是课时23 的**前置工序**：先清洗对齐，再谈质量校验。

## 二、学完能做什么

1. **设计多源数据采集方案**：DB/API/日志/聊天/文件/消息队列的接入模式选型，处理 Schema 漂移
2. **把非结构化数据转成结构化表**：聊天记录、JSON 表单、富文本、日志的字段化提取
3. **系统化清洗脏数据**：缺失值/异常值/重复/格式不统一/编码问题/逻辑矛盾六类问题的处理范式
4. **打通跨渠道用户身份（ID Mapping）**：手机号 ↔ 邮箱 ↔ 设备ID ↔ 微信OpenID 的归一
5. **标准化枚举值**："北京/北京市/BJ" → "Beijing" 的字典映射与模糊匹配
6. **文本实体消歧**：商品名、公司名、地址的模糊匹配与去重（SimHash/MinHash/编辑距离）
7. **理解企业主数据管理（MDM）**：Golden Record 构建流程、架构师视角的治理体系
8. **编排清洗流水线**：Airflow DAG + 质量校验 + dbt test 的端到端工程化

## 六、第一性原理锚点

> 本模块对应 [大数据第一性原理](../../大数据第一性原理.md) 中的**矛盾8：Schema 灵活性 vs 查询性能**。多源数据天然 Schema 混乱，清洗的本质是"在灵活性与可分析性之间找到折中点"——既不能强求所有源统一 Schema（丧失灵活性），也不能放任混乱（丧失查询性能）。
