## 二、清洗流水线整体架构

### 2.1 从采集到入仓的 DAG 全景

前几个课时分别解决了"数据怎么进来（课时24）""怎么字段化（课时25）""怎么去脏（课时26）""怎么对齐标准化（课时27/28）"。本课时把这些步骤**编排成一条流水线**，并在入仓前加一道**质量校验闸门**。

```
清洗流水线 DAG:

                  ┌──────────────┐
                  │  调度触发      │  Airflow 每日 02:00
                  └──────┬───────┘
                         │
            ┌────────────┼────────────┐
            ▼            ▼            ▼
   ┌──────────────┐ ┌──────────┐ ┌──────────────┐
   │ 采集Task      │ │ 采集Task  │ │ 采集Task      │   多渠道并行
   │ APP表单(MySQL)│ │ 客服聊天  │ │ 邮件工单(API) │   课时24
   └──────┬───────┘ └─────┬────┘ └──────┬───────┘
          └───────────────┼─────────────┘
                          │
                          ▼
                ┌──────────────────┐
                │  清洗Task         │   缺失/异常/重复/格式
                │  (Spark/pandas)  │   课时26
                └────────┬─────────┘
                         │
                         ▼
                ┌──────────────────┐
                │  对齐Task         │   ID Mapping + 枚举标准化
                │  (GraphFrame)    │   课时27
                └────────┬─────────┘
                         │
                         ▼
                ┌──────────────────┐
                │  质量校验Task      │   Great Expectations / dbt test
                │  (GE Checkpoint) │   课时23
                └────────┬─────────┘
                    通过 │ ┌── 失败 → 告警 + 阻断入仓
                         ▼ │
                ┌──────────────────┐
                │  入仓Task         │   ODS / DWD 分区写入
                │  (Hive/Iceberg)  │
                └────────┬─────────┘
                         │
                         ▼
                ┌──────────────────┐
                │  通知Task         │   日报 + 量级监控
                └──────────────────┘
```

### 2.2 每个环节的输入输出

| 环节 | 输入 | 处理动作 | 输出 | 对应课时 |
|------|------|---------|------|---------|
| 采集 | MySQL/API/日志文件 | Sqoop/CDC/Filebeat 拉取 | staging 层原始数据 | 课时24 |
| 清洗 | staging 原始数据 | 缺失填充、异常剔除、去重、格式归一 | clean 临时表 | 课时26 |
| 对齐 | clean 临时表 | ID Mapping、枚举字典标准化、文本消歧 | aligned 结构化表 | 课时27/28 |
| 质量校验 | aligned 结构化表 | GE Checkpoint / dbt test 规则校验 | 校验报告 + 通过/失败信号 | 课时23 |
| 入仓 | 校验通过的 aligned 表 | 写入 ODS/DWD 分区 | 数仓正式表 | 课时22 |

> **关键设计**：质量校验是**闸门（Gate）**，不是事后审计。校验失败时阻断入仓，避免脏数据污染下游报表。

## 三、Airflow 编排清洗 DAG

### 3.1 DAG 设计原则

清洗 DAG 比普通 ETL DAG 多两个要求：**可重跑**和**可回溯**。因为清洗逻辑会反复迭代（字典更新、规则补充），必须能安全地重跑历史日期。

| 原则 | 含义 | 落地手段 |
|------|------|---------|
| 幂等性 | 同一日期重跑 N 次，结果一致 | 用 `INSERT OVERWRITE PARTITION`，按 `dt` 覆盖；不在清洗中做"追加" |
| 失败重试 | 瞬时故障（网络、资源）自动恢复 | `retries=3` + 指数退避 `retry_delay` |
| 数据回溯 | 清洗逻辑变更后重跑历史 | 脚本参数化日期（`{{ ds }}`）+ `catchup=True` + 版本化脚本目录 |
| 分区隔离 | 不同日期的数据互不干扰 | 所有中间表、目标表都按 `dt` 分区 |
| 校验前置 | 脏数据不进仓 | 质量校验 Task 作为入仓 Task 的上游，校验失败则阻断 |

### 3.2 清洗 DAG 代码示例（TaskFlow API）

下面用 Airflow 2.x 的 **TaskFlow API**（`@dag` / `@task` 装饰器）实现完整框架。TaskFlow 的优势是用 Python 函数天然表达任务，XCom 自动传递返回值，比传统 Operator 写法更简洁。风格与 [项目6](../../L1_初级工程师/第11-14周_项目实战/项目6_Airflow工作流编排.md) 保持一致：完整可部署的结构，但连接配置用占位符。

```python
"""
dag_cleaning_pipeline.py — 多源数据清洗流水线 DAG（TaskFlow API 版）

调度说明:
  - 每天凌晨 02:00 执行
  - 失败自动重试 3 次，指数退避
  - SLA: 06:00 前必须完成
  - 清洗逻辑版本化，支持历史回溯

依赖: airflow >= 2.5
"""

from datetime import datetime, timedelta
import pendulum

from airflow.decorators import dag, task
from airflow.utils.trigger_rule import TriggerRule


# ========== 告警回调 ==========
def alert_on_failure(context):
    """任务失败时推送企业微信/钉钉告警"""
    import requests

    ti = context["task_instance"]
    dag_id = context["dag"].dag_id
    task_id = ti.task_id
    ds = context["ds"]
    exception = context.get("exception")

    # 企业微信群机器人 webhook（钉钉同理，换 payload 结构即可）
    webhook_url = "https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=YOUR_KEY"
    payload = {
        "msgtype": "markdown",
        "markdown": {
            "content": (
                f"**清洗流水线告警**\n"
                f"> DAG: {dag_id}\n"
                f"> Task: {task_id}\n"
                f"> 数据日期: {ds}\n"
                f"> 重试次数: {ti.try_number}\n"
                f"> 错误: {exception}\n"
                f"> 请及时排查"
            )
        },
    }
    try:
        requests.post(webhook_url, json=payload, timeout=5)
    except Exception as e:
        # 告警本身失败不能影响主流程日志
        print(f"[alert] 告警发送失败: {e}")


# ========== DAG 默认参数 ==========
default_args = {
    "owner": "data_cleaning",
    "depends_on_past": False,        # 不依赖上一次运行（回溯时不会被历史失败卡住）
    "retries": 3,                    # 失败重试 3 次
    "retry_delay": timedelta(minutes=2),      # 首次重试间隔
    "retry_exponential_backoff": True,        # 指数退避
    "max_retry_delay": timedelta(minutes=30), # 退避上限
    "execution_timeout": timedelta(hours=2),  # 单任务超时
    "on_failure_callback": alert_on_failure,  # 失败回调
}


# ========== DAG 定义 ==========
@dag(
    dag_id="cleaning_pipeline",
    description="多源数据清洗流水线：采集→清洗→对齐→质量校验→入仓",
    default_args=default_args,
    schedule="0 2 * * *",            # 每天凌晨 02:00
    start_date=datetime(2024, 1, 1, tzinfo=pendulum.timezone("Asia/Shanghai")),
    catchup=True,                    # 允许回填（支持历史重跑）
    max_active_runs=1,               # 同一时间只允许 1 个 DAG 实例（避免并发写同分区）
    tags=["cleaning", "multi-source", "daily"],
)
def cleaning_pipeline():
    """清洗流水线 DAG 主体"""

    # ---------- 阶段1: 采集（多渠道并行） ----------
    @task
    def collect_app_form(ds: str) -> str:
        """采集 APP 表单数据（MySQL 源）"""
        # 实际用 SqoopOperator / PythonOperator 调用 Sqoop
        # 这里返回采集到的临时表名，通过 XCom 传给下游
        print(f"[采集] APP表单 数据日期={ds}")
        return f"staging.app_form_{ds.replace('-', '')}"

    @task
    def collect_chat_log(ds: str) -> str:
        """采集客服聊天记录（日志源）"""
        print(f"[采集] 客服聊天 数据日期={ds}")
        return f"staging.chat_log_{ds.replace('-', '')}"

    @task
    def collect_email_ticket(ds: str) -> str:
        """采集邮件工单（API 源）"""
        print(f"[采集] 邮件工单 数据日期={ds}")
        return f"staging.email_ticket_{ds.replace('-', '')}"

    # ---------- 阶段2: 清洗（去脏/格式化） ----------
    @task
    def clean_data(source_tables: list, ds: str) -> str:
        """
        对各渠道原始数据做清洗：
        - 缺失值处理（核心字段非空）
        - 异常值剔除（金额范围、枚举值）
        - 去重（按业务主键）
        - 格式归一（手机号、时间格式）
        实际用 SparkSubmitOperator 调用清洗脚本，脚本按 --date 参数执行
        """
        print(f"[清洗] 输入源={source_tables} 数据日期={ds}")
        # Spark 提交示例（伪代码）：
        # spark-submit /opt/jobs/clean/clean_v1.2.py --date {ds}
        print("[清洗] 完成缺失填充/异常剔除/去重/格式归一")
        return f"tmp.clean_{ds.replace('-', '')}"

    # ---------- 阶段3: 对齐（ID Mapping + 标准化） ----------
    @task
    def align_entities(clean_table: str, ds: str) -> str:
        """
        实体对齐与标准化（课时27/28）：
        - ID Mapping：手机号/邮箱/OpenID/设备ID 联通分量归一
        - 枚举标准化：地区/职业 字典映射 + 模糊匹配
        - 文本消歧：商品名 SimHash 去重
        """
        print(f"[对齐] 输入={clean_table} 数据日期={ds}")
        # spark-submit /opt/jobs/align/align_v1.1.py --date {ds}
        print("[对齐] 完成 ID Mapping + 枚举标准化")
        return f"tmp.aligned_{ds.replace('-', '')}"

    # ---------- 阶段4: 质量校验（闸门） ----------
    @task
    def run_quality_check(aligned_table: str, ds: str) -> bool:
        """
        质量校验闸门：调用 Great Expectations Checkpoint
        返回 True 表示通过，False 表示失败（会抛异常阻断下游）
        """
        import great_expectations as gx

        print(f"[校验] 校验表={aligned_table} 数据日期={ds}")
        context = gx.get_context()
        checkpoint = context.get_checkpoint("aligned_feedback_checkpoint")
        result = checkpoint.run()

        if not result["success"]:
            # 抛异常 → 触发重试 → 最终失败触发告警 + 阻断入仓
            raise ValueError(f"质量校验失败: 日期={ds}, 表={aligned_table}")
        print("[校验] 质量校验通过")
        return True

    # ---------- 阶段5: 入仓 ----------
    @task
    def load_to_warehouse(aligned_table: str, ds: str, check_passed: bool) -> str:
        """将校验通过的数据写入 ODS/DWD 分区（INSERT OVERWRITE 保证幂等）"""
        # check_passed 由上游 XCom 传入；trigger_rule=all_success 时只有校验通过才会执行
        print(f"[入仓] aligned={aligned_table} 数据日期={ds} 校验={check_passed}")
        # INSERT OVERWRITE TABLE ods.ods_user_feedback PARTITION (dt='{ds}') ...
        print("[入仓] 写入 ods.ods_user_feedback 分区完成")
        return f"ods.ods_user_feedback@dt={ds}"

    # ---------- 阶段6: 通知 ----------
    @task
    def send_daily_report(warehouse_table: str, ds: str):
        """发送清洗日报（清洗量、清洗率、质量趋势）"""
        print(f"[通知] 日报: 入仓表={warehouse_table} 日期={ds}")
        # 实际用 EmailOperator 或推送企业微信

    # ========== 依赖编排 ==========
    ds = "{{ ds }}"  # 数据日期（占位，TaskFlow 中由 Airflow 模板渲染）

    # 采集并行
    app_tbl = collect_app_form(ds)
    chat_tbl = collect_chat_log(ds)
    email_tbl = collect_email_ticket(ds)

    # 清洗依赖全部采集完成（list 收集多个 XCom）
    clean_tbl = clean_data([app_tbl, chat_tbl, email_tbl], ds)

    # 对齐 → 校验 → 入仓 → 通知 串行
    aligned_tbl = align_entities(clean_tbl, ds)
    check_ok = run_quality_check(aligned_tbl, ds)
    wh_tbl = load_to_warehouse(aligned_tbl, ds, check_ok)
    send_daily_report(wh_tbl, ds)


# 实例化 DAG（TaskFlow 必须调用一次）
dag = cleaning_pipeline()
```

> **代码说明**：
> - `@task` 装饰的函数返回值会自动通过 XCom 传递给下游，无需手写 `xcom_push/xcom_pull`。
> - `collect_app_form` 等返回字符串（表名），下游 `clean_data` 接收 list，Airflow 会自动把多个上游 Task 的 XCom 收集成列表。
> - `max_active_runs=1` 防止同一天并发写同一分区。
> - 真实部署时，把 `print` 换成实际的 Spark/Sqoop/Hive 调用即可。

### 3.3 依赖关系与触发规则

#### 3.3.1 上下游依赖的三种写法

```python
# 写法1: 位运算符（推荐，最直观）
collect() >> clean() >> align() >> validate() >> load()

# 写法2: 链式
[collect_a(), collect_b(), collect_c()] >> clean()

# 写法3: set_downstream（传统写法）
clean().set_downstream(align())
```

#### 3.3.2 分支执行与失败兜底

清洗流水线常遇到"校验失败要继续走兜底分支"的需求。用 `TriggerRule` 控制下游何时触发：

```python
from airflow.utils.trigger_rule import TriggerRule

@task
def quarantine_bad_data(aligned_table: str, ds: str):
    """兜底：把校验失败的数据写入隔离表，供人工排查"""
    print(f"[隔离] 把 {aligned_table} 写入 quaran.bad_records 分区 dt={ds}")

@task(trigger_rule=TriggerRule.ALL_DONE)
def notify_regardless(ds: str):
    """无论上游成功失败都执行（确保告警一定发出）"""
    print(f"[通知] 数据日期={ds} 流水线结束（含失败分支）")

# 编排：校验失败时不入仓，而是进隔离表
aligned = align_entities(clean_tbl, ds)
check_ok = run_quality_check(aligned, ds)

# check_ok 成功 → 入仓
load_to_warehouse(aligned, ds, check_ok)

# check_ok 失败 → 隔离（用 trigger_rule 控制只在失败时跑）
quarantine = quarantine_bad_data(aligned, ds)
# 注意：分支选择更推荐用 BranchPythonOperator，这里简化展示兜底思路
```

| TriggerRule | 触发条件 | 典型用途 |
|-------------|---------|---------|
| `all_success`（默认） | 所有上游成功 | 正常串行链路 |
| `all_done` | 所有上游结束（无论成败） | 必须执行的收尾通知 |
| `one_failed` | 任一上游失败 | 失败兜底分支 |
| `none_failed` | 没有上游失败 | 防御性下游 |
| `none_skipped` | 没有上游被跳过 | 严格要求全部执行 |

## 四、清洗后质量校验

### 4.1 校验时机：清洗后立即校验 vs 入仓前校验

| 时机 | 位置 | 优点 | 缺点 | 适用 |
|------|------|------|------|------|
| 清洗后立即校验 | 清洗 Task 内部 | 早发现早重试，减少下游无效计算 | 与清洗逻辑耦合 | 单表清洗 |
| 入仓前校验 | 对齐后、入仓前（推荐） | 校验的是最终结构化结果，最接近下游可用形态 | 校验失败时上游已算完 | 流水线闸门 |
| 入仓后校验 | 入仓后定期跑 | 不阻断流程，适合非关键表 | 脏数据已进仓，需回滚 | 弱一致场景 |

> **推荐策略**：**入仓前校验为主**（阻断脏数据），**入仓后巡检为辅**（监控已入仓数据的趋势异常，如行数突降）。本课时聚焦入仓前校验。

### 4.2 Great Expectations 集成

[课时23](../补充模块_数据治理实操/课时23_数据质量与元数据管理.md) 已介绍 GE 的 Expectation Suite / Checkpoint 概念。这里把 GE 嵌入 Airflow Task，并区分"阻断"与"告警"两种失败处理。

#### 4.2.1 定义 Expectation Suite（复用课时23）

```python
"""
为对齐后的结构化表定义质量规则
表: tmp.aligned_user_feedback
字段: global_user_id, channel, region_std, feedback_text, create_time
"""
import great_expectations as gx

context = gx.get_context()
suite = context.add_expectation_suite("aligned_feedback_suite")
s = context.get_expectation_suite("aligned_feedback_suite")

# 主键非空且唯一（完整性 + 唯一性）
s.add_expectation(gx.expectations.ExpectColumnValuesToNotBeNull(column="feedback_id"))
s.add_expectation(gx.expectations.ExpectColumnValuesToBeUnique(column="feedback_id"))

# 对齐后的全局用户ID必须非空（验证 ID Mapping 覆盖率）
s.add_expectation(
    gx.expectations.ExpectColumnValuesToNotBeNull(column="global_user_id", mostly=0.98)
)

# 渠道枚举值校验（有效性）
s.add_expectation(
    gx.expectations.ExpectColumnValuesToBeInSet(
        column="channel", value_set=["APP", "CHAT", "EMAIL", "API"]
    )
)

# 标准化后的地区值必须在字典内（验证标准化覆盖率）
s.add_expectation(
    gx.expectations.ExpectColumnValuesToNotBeNull(column="region_std", mostly=0.95)
)

# 行数不为零且波动合理（及时性 + 完整性）
s.add_expectation(gx.expectations.ExpectTableRowCountToBeBetween(min_value=100, max_value=5000000))

context.add_or_update_expectation_suite(expectation_suite=s)
```

#### 4.2.2 在 Airflow Task 中调用 GE，区分阻断与告警

```python
"""
quality_check_task.py
校验失败的处理策略：
  - 阻断（Block）：核心规则失败 → 抛异常 → 阻断入仓 → 触发重试/告警
  - 告警（Alert）：非核心规则失败 → 记录但不阻断 → 仅发告警
"""

# 规则分级配置
RULE_SEVERITY = {
    "feedback_id 非空": "block",
    "feedback_id 唯一": "block",
    "global_user_id 覆盖率": "alert",   # 覆盖率 98% 未达标可告警但不阻断
    "channel 枚举值": "block",
    "region_std 覆盖率": "alert",
    "行数范围": "block",
}


@task
def run_ge_checkpoint_with_severity(aligned_table: str, ds: str) -> bool:
    """分级处理校验结果"""
    import great_expectations as gx

    context = gx.get_context()
    checkpoint = context.get_checkpoint("aligned_feedback_checkpoint")
    result = checkpoint.run()

    # 解析每条规则的通过情况
    run_results = result["run_results"]
    block_failures = []
    alert_failures = []

    for run_result in run_results.values():
        expectation_config = run_result["expectation_result"]["expectation_config"]
        rule_name = expectation_config["expectation_type"]
        success = run_result["expectation_result"]["success"]
        if not success:
            severity = RULE_SEVERITY.get(rule_name, "alert")
            if severity == "block":
                block_failures.append(rule_name)
            else:
                alert_failures.append(rule_name)

    # 告警级失败：只记录，不阻断
    if alert_failures:
        print(f"[告警] 非阻断规则失败: {alert_failures}")
        # 推送告警但不抛异常
        # send_alert(f"软告警: {alert_failures}")

    # 阻断级失败：抛异常，阻断入仓
    if block_failures:
        raise ValueError(f"阻断级质量校验失败: {block_failures}, 日期={ds}")

    print("[校验] 全部阻断规则通过，准许入仓")
    return True
```

| 失败类型 | 处理方式 | 适用规则 |
|---------|---------|---------|
| 阻断（Block） | 抛异常 → 重试 → 最终失败告警 + 不入仓 | 主键非空/唯一、枚举值、行数为零 |
| 告警（Alert） | 记录 + 推送告警，允许入仓 | 覆盖率低于阈值（如 ID Mapping 98%）、软指标 |

### 4.3 dbt test（现代数据栈方式）

如果用 dbt 管理转换层（DWD/DWS），质量校验可以用 `dbt test` 声明式实现。dbt test 的优势是规则写在 `schema.yml` 里，与模型定义放一起，版本化管理天然集成。

#### 4.3.1 schema.yml 定义测试

```yaml
# models/staging/stg_user_feedback.yml
version: 2

models:
  - name: stg_user_feedback
    description: "清洗对齐后的用户反馈表（每日分区）"
    columns:
      - name: feedback_id
        description: "反馈记录主键"
        tests:
          - unique
          - not_null

      - name: global_user_id
        description: "ID Mapping 后的全局用户ID"
        tests:
          - not_null:
              # 覆盖率要求 98%，允许 2% 未对齐
              config:
                severity: warn
          - relationships:
              # 外键一致性：必须在用户主数据表中存在
              to: ref('dim_user')
              field: global_user_id

      - name: channel
        description: "数据来源渠道"
        tests:
          - not_null
          - accepted_values:
              values: ["APP", "CHAT", "EMAIL", "API"]

      - name: region_std
        description: "标准化后的地区值"
        tests:
          - not_null:
              config:
                severity: warn   # 告警级，不阻断

      - name: create_time
        description: "反馈提交时间"
        tests:
          - not_null

    # 表级测试
    tests:
      - dbt_utils.expression_is_true:
          # 业务规则：完成时间必须晚于创建时间
          expression: "finish_time is null or finish_time >= create_time"
      - dbt_utils.recency:
          # 及时性：最新数据时间不超过 2 天
          field: create_time
          datepart: day
          interval: 2
```

#### 4.3.2 常用 dbt test 速查

| 测试名 | 作用 | 等价 GE 规则 |
|--------|------|-------------|
| `not_null` | 列值非空 | `ExpectColumnValuesToNotBeNull` |
| `unique` | 列值唯一 | `ExpectColumnValuesToBeUnique` |
| `accepted_values` | 值在枚举集合内 | `ExpectColumnValuesToBeInSet` |
| `relationships` | 外键引用完整性（值在另一表存在） | `ExpectColumnValuesToBeInSet`（动态） |
| `dbt_utils.expression_is_true` | 自定义 SQL 表达式为真 | `ExpectColumnPairValues...` |
| `dbt_utils.recency` | 数据新鲜度（最近时间） | 时效性检查 |

#### 4.3.3 在 Airflow 中调度 dbt test

```python
from airflow.decorators import task

@task
def run_dbt_test(ds: str) -> bool:
    """调用 dbt test 执行质量校验，失败则阻断入仓"""
    import subprocess

    # 只测试当日分区对应的模型
    cmd = [
        "dbt", "test",
        "--select", "stg_user_feedback",
        "--vars", f"{{run_date: '{ds}'}}",
    ]
    print(f"[dbt test] 执行: {' '.join(cmd)}")
    result = subprocess.run(cmd, capture_output=True, text=True)

    # dbt test 退出码非 0 表示有 error 级测试失败
    if result.returncode != 0:
        print(result.stdout)
        # warn 级失败不阻断（dbt 仍返回 0），error 级失败返回非 0
        raise ValueError(f"dbt test 失败，阻断入仓: 日期={ds}")
    print("[dbt test] 校验通过")
    return True
```

> **GE vs dbt test 选型**：GE 适合在数仓外做"准入校验"（清洗后、入仓前）；dbt test 适合在数仓内做"转换后校验"（DWD→DWS）。两者可共存：GE 守入仓闸门，dbt test 守转换质量。

## 五、失败处理与运维

### 5.1 重试策略

清洗任务常因资源抢占、临时网络抖动失败，自动重试是必备能力。

```python
default_args = {
    "retries": 3,                            # 重试次数
    "retry_delay": timedelta(minutes=2),     # 首次重试间隔
    "retry_exponential_backoff": True,       # 开启指数退避
    "max_retry_delay": timedelta(minutes=30),# 退避上限，避免越退越久
}
```

**指数退避时序**（首次间隔 2 分钟，上限 30 分钟）：

```
失败 → 等 2min → 重试1 → 失败 → 等 4min → 重试2 → 失败 → 等 8min → 重试3 → 最终失败告警
```

> **注意**：`depends_on_past=False` 是回溯的关键。如果设为 `True`，回填历史日期时会被历史某天的失败卡住，导致整个回填中断。

### 5.3 数据回溯（Backfill）

清洗逻辑修改后（如字典升级、规则补充），需要重跑历史数据。回溯的两个前提：**版本化清洗脚本** + **参数化日期**。

#### 5.3.1 版本化脚本目录

```
/opt/jobs/clean/
  ├── clean_v1.0.py    # 初版
  ├── clean_v1.1.py    # 修复：手机号格式遗漏 +86
  ├── clean_v1.2.py    # 当前版本：新增地区字典 v2.0
  └── current -> clean_v1.2.py   # 软链接指向当前版本
```

DAG 中调用版本化脚本，回溯时可指定旧版本重跑：

```python
@task
def clean_data(source_tables, ds, script_version: str = "current"):
    """参数化清洗脚本版本，回溯时可指定历史版本"""
    script = f"/opt/jobs/clean/{script_version}.py"
    # spark-submit {script} --date {ds}
    print(f"[清洗] 版本={script_version} 日期={ds}")
```

#### 5.3.2 触发回溯

```bash
# 方式1: Airflow CLI 回填近 7 天
airflow dags backfill \
    --start-date 2024-07-08 \
    --end-date 2024-07-14 \
    cleaning_pipeline

# 方式2: 重跑单日（清状态后重新触发）
airflow tasks clear --start-date 2024-07-10 --end-date 2024-07-10 cleaning_pipeline
airflow dags trigger cleaning_pipeline -e 2024-07-10
```

> **回溯安全检查清单**：
> 1. 确认目标表按 `dt` 分区且用 `INSERT OVERWRITE`（幂等）
> 2. 确认 `max_active_runs=1`，避免回填与当日正常跑并发冲突
> 3. 确认 `depends_on_past=False`，避免历史失败卡住回填
> 4. 回溯前通知下游报表使用者，避免数据口径突变

## 八、小结

| 流水线环节 | 推荐工具 | 失败处理策略 |
|-----------|---------|-------------|
| 采集 | Sqoop / Flink CDC / Filebeat | 重试 3 次 + 指数退避；源端故障告警 |
| 清洗 | Spark DataFrame / pandas | 幂等重写分区；脚本版本化 |
| 对齐 | GraphFrame / rapidfuzz | ID Mapping 覆盖率告警（不阻断） |
| 质量校验 | Great Expectations / dbt test | 阻断级失败抛异常阻断入仓；告警级仅通知 |
| 入仓 | Hive / Iceberg（INSERT OVERWRITE） | 入仓前必须有上游校验通过信号 |
| 告警 | on_failure_callback + 企微/钉钉 webhook | 失败 + SLA 超时双重告警 |
| 回溯 | Airflow backfill + 版本化脚本 | 参数化日期 + depends_on_past=False |

**核心工程原则**：
1. **校验是闸门不是审计**：质量校验放在入仓前，失败即阻断，不让脏数据进仓
2. **幂等优先**：所有写入用 `INSERT OVERWRITE PARTITION`，保证重跑安全
3. **版本化一切**：清洗脚本、字典、Expectation Suite 都要版本化，回溯才能复现历史
4. **分级告警**：区分阻断级与告警级，避免非核心规则失败拖垮整条流水线
