## Q1: MapReduce 的"物化中间状态"是什么意思？为什么会成为瓶颈？对比 MapReduce（物化每个 Stage）、Spark（内存缓存+惰性求值）、Tez（DAG+避免物化）三者的中间数据管理策略。

### 核心结论

MapReduce 的"物化中间状态"指的是每个 MapReduce Job 的输出（Map 端的 spill 文件、Reduce 端的最终输出）都必须完整地持久化到 HDFS（分布式文件系统）后，下一个 Job 才能读取并启动——即每一步计算的中间结果都被"实体化"为文件系统上的一个稳定数据集。这种设计以牺牲性能换取了极致的容错性和编程模型简单性，但在迭代式和多 Stage 工作流中会因重复的磁盘 I/O、HDFS 3 副本写入开销、Shuffle 网络传输、Job 间调度延迟而成为严重瓶颈。Spark 通过 RDD 的内存缓存 + 血统（Lineage）容错规避了跨 Job 物化；Tez 则以 DAG 执行引擎将多个 Stage 编排进同一个 YARN Application，在 Stage 之间直接走内存或本地 Shuffle，避免落 HDFS。

### 原理剖析

#### MapReduce 的物化设计动机：源自 OSDI 2004 论文

Dean & Ghemawat 在 OSDI 2004 论文 "MapReduce: Simplified Data Processing on Large Clusters" 中明确阐述了物化中间状态的设计动机：

1. **容错优先于性能**。论文第 3 节"Implementation"指出，Map worker 将中间数据写入本地磁盘（而非内存），Reduce worker 通过 HTTP 拉取这些中间数据。Master 节点记录每个 Map 任务的完成位置（机器 ID + 本地磁盘路径），并将该位置信息传递给后续的 Reduce 任务。如果一个 Map worker 失败，Master 会将该任务重新调度到其他节点执行——这要求中间数据要么已持久化、要么可以重算。Google 选择"已持久化到本地磁盘"方案，因为内存中数据会随 worker 失败而丢失，重算 Map 任务的代价相对较低（输入数据通常在 GFS 上有 3 副本）。

2. **Reduce 输出写 GFS（Hadoop 中对应 HDFS）**。论文第 3.4 节指出，Reduce 任务将最终输出写入 GFS。GFS 本身做 3 副本复制，所以每个 Reduce 任务的输出都会被复制 3 份存到不同机架。这种"输出即文件"的设计让 MapReduce 的输出天然可被下一个 Job 当作输入，构成了"链式 Job"的编程模型。

3. **Shuffle 是显式的网络物化**。Map 端输出经过 Partition + Sort + Spill + Merge，最终由 Reduce 端通过 HTTP 拉取（fetch）。这个过程把数据从 Map 节点的本地磁盘搬到了 Reduce 节点的本地磁盘，是一次完整的"网络物化"。论文 Table 1 显示，Sort 任务的 Shuffle 数据量达 6.5TB（500TB 输入 × 副本/分区），这正是物化的代价。

#### 为什么物化会成为瓶颈

把 MapReduce 的物化成本拆解，可以量化出三类开销：

**（1）磁盘 I/O 放大**。假设一个工作流有 N 个串行 Job，每个 Job 的中间输出为 S 字节。MapReduce 模型下：
- 每个 Map 端：spill 到本地磁盘（写），后续 merge（读+写）。
- Shuffle 阶段：Reduce 端 fetch 后落本地磁盘（写）。
- Reduce 输出：写 HDFS（3 副本 = 3 次写）。
- 下一个 Job 的 InputFormat：从 HDFS 读（3 副本中选 1 个读）。

对于一个 Job，中间数据的磁盘写入次数 ≈ 5~7 次（含 3 副本）。N 个 Job 串行时，磁盘 I/O 总量约为 N×S×7。如果数据本身在 100TB 量级，这放大效应非常惊人。

**（2）HDFS 3 副本写入开销**。HDFS 的 3 副本策略为容错设计，但对中间状态而言是冗余的——中间状态本可以通过重算恢复。MapReduce 把中间状态当成"一等公民"持久化，付出了不必要的 3 副本写带宽和存储成本。

**（3）Job 间调度延迟**。每个 MapReduce Job 都是独立的 YARN Application，需要：
- 向 ResourceManager 申请 Container（秒级延迟）。
- ApplicationMaster 初始化（秒级）。
- 数据本地化（如果是大文件可能分钟级）。

对于一个 10 Stage 的工作流，仅调度延迟就可能累计到分钟级。Google 在论文中也承认，对于迭代式算法（如 PageRank、k-means），每次迭代都启动一个完整 Job 的开销很大。

#### Spark 的 RDD：内存缓存 + 血统容错

Zaharia et al. 在 NSDI 2012 论文 "Resilient Distributed Datasets: A Fault-Tolerant Abstraction for In-Memory Cluster Computing" 中提出了 RDD，核心思想是：

1. **不可变 + 分区的内存数据集**。RDD 是一个只读的、分区的数据集，可以通过 transformations（map、filter、join）派生出新的 RDD。每个 RDD 记录其"血统"（Lineage）——即从原始数据到自己的 transformation 链。

2. **惰性物化**。Transformations 不会立即执行，只构建 DAG。只有 actions（count、collect、save）触发时，DAGScheduler 才会反向推导出需要计算的分区并提交任务。这意味着中间 RDD 不一定要物化到磁盘——只有当用户显式调用 `persist()` 或 `cache()` 时，才会物化到内存或磁盘。

3. **血统容错替代副本容错**。当一个 RDD 的某个分区丢失时，Spark 根据 Lineage 重新计算该分区，而不依赖副本。这是 RDD 相比 MapReduce 的根本性差异：MapReduce 用物化（副本+磁盘）换容错，Spark 用重算（Lineage）换容错。论文 Section 3.3 明确指出："RDDs do not need to be materialized at all times"，这正是避免物化的关键。

4. **缓存策略可选**。`StorageLevel` 提供 MEMORY_ONLY、MEMORY_AND_DISK、DISK_ONLY 等多种级别。对于反复使用的 RDD（如迭代算法中的图数据），用 MEMORY_ONLY 避免磁盘 I/O；对于一次性的大中间结果，可以不缓存，让其按需重算。

#### Tez：DAG 执行引擎，避免跨 Job 物化

Apache Tez 的设计目标是替代 MapReduce 在 Hive/Pig 中的执行引擎角色。其核心设计文档 "Apache Tez: A New Framework for Processing Complex DAGs of Tasks" 指出：

1. **单个 YARN Application 编排整个 DAG**。Tez 把一个 SQL 查询（或 Pig 脚本）编译成一个 DAG，整个 DAG 在一个 Tez Session（一个 YARN Application）中执行。Stage 之间通过内存或本地 Shuffle 传递数据，不再落 HDFS。

2. **Vertex + Edge 抽象**。Tez 用 Vertex 表示一个 Stage（一组并行任务），用 Edge 表示 Vertex 间的数据流向。Edge 的 `EdgeProperty` 可以指定数据传输方式：
   - `ONE_TO_ONE`（如 Map 端的 pipe）
   - `BROADCAST`（如 Broadcast Join）
   - `SCATTER_GATHER`（即 Shuffle）

   这比 MapReduce 的"固定 Map→Reduce"模型灵活得多。

3. **避免物化的核心机制**：Stage 间数据走 In-Memory Shuffle 或 Local Shuffle，而不是 HDFS。只有在需要容错检查点时才物化到 HDFS。Hive on Tez 相比 Hive on MR，典型查询有 2~3 倍加速，主要来自避免物化和减少调度开销。

### 技术映射

| 维度 | MapReduce (Hadoop) | Spark | Tez |
|------|-------------------|-------|-----|
| 中间状态存储 | HDFS（3 副本）+ 本地磁盘 | 内存 / 本地磁盘（可选） | 内存 / 本地 Shuffle |
| 容错机制 | 任务重试 + 副本 | 血统重算 + 可选 checkpoint | 任务重试 + DAG 重新调度 |
| Stage 间调度 | 每个 Job 独立 YARN App | 同一个 SparkContext 内 DAG | 同一个 Tez Session |
| 编程模型 | 固定 Map→Reduce | RDD transformations/actions | DAG API（Vertex/Edge） |
| 典型用户 | 早期 Hadoop 作业 | Spark Core/SQL/MLlib | Hive on Tez、Pig on Tez |
| Shuffle 实现 | HTTP fetch + 本地磁盘 | Netty + 内存/磁盘 | Direct Shuffle / Sort Shuffle |

### 设计权衡

**MapReduce 的物化为何在 2004 年是合理的**：
- 当时 Google 集群故障率较高（论文提到平均每分钟有 1~3 个机器故障），容错是第一优先级。
- GFS 的 3 副本模型已成熟，复用其容错能力成本最低。
- 编程模型简单（用户只需写 map/reduce 函数），降低分布式编程门槛。

**何时仍然选择物化**：
- 工作流是"一次性批处理"而非迭代式（如日志 ETL），物化开销可接受。
- 需要中间结果作为多个下游 Job 的公共输入（物化一次，多次读取）。
- 对调试和审计有强需求（物化的中间状态可被检查和重放）。

**何时避免物化**：
- 迭代式算法（ML 训练、图计算）：Spark 的内存缓存收益巨大。
- 多 Stage 的 SQL 查询：Tez/Spark SQL 的 DAG 执行避免反复落盘。
- 数据敏感的实时性需求：流批一体场景下，物化延迟不可接受。

### 生产经验与踩坑

1. **MapReduce 时代的 "Chain Mapper/Reducer" 模式**。早期 Hadoop 用户为了减少 HDFS 写入，会把多个逻辑塞进一个 Mapper（用 `ChainMapper`），但这违背了 MapReduce 的"每步落盘"模型，导致单个任务逻辑臃肿、难以维护。这是物化瓶颈倒逼出的反模式。

2. **Spark 内存缓存的 OOM 陷阱**。新手常把所有中间 RDD 都 `cache()`，结果 Executor 内存爆炸。正确做法：只缓存被多次引用的 RDD（如迭代算法中的训练数据），其余让其按需重算。监控 `StoragePage` 中的 `Fraction Cached`，低于 100% 说明缓存被驱逐，需要调 `spark.memory.storageFraction` 或换 `MEMORY_AND_DISK`。

3. **Spark Shuffle 仍会物化到磁盘**。当 Shuffle 数据量超过 `spark.shuffle.file.buffer` 和内存上限时，Spark 仍会 spill 到本地磁盘。对于超大 Shuffle（如大表 Join），Spark 的"内存缓存"并不能完全避免物化——这是 Spark 和 Tez 共同的痛点，AQE 和 Z-order 等技术都是为了缓解它。

4. **Tez Session 的资源占用**。Tez Session 常驻会占用 Container，空闲时也不释放。在多租户集群上需要配置 `tez.session.am.dag.submit.timeout.secs` 让 Session 自动退出，否则会浪费资源。

5. **物化并非全是坏事**。在数据湖场景下，物化的中间表（如 ODS→DWD→DWS 的分层）是数据治理的标准实践。物化带来了可重放、可审计、可重用的好处。这与"避免物化以提速"是两个不同维度的问题：前者是数据工程，后者是计算引擎。

## Q2: Spark 的"惰性求值"和 MapReduce 的区别是什么？惰性求值如何使得 Catalyst 优化器能做全局 DAG 优化（如 Filter Pushdown、Column Pruning）？

### 核心结论

MapReduce 是"急切执行"模型——用户提交 Job 后立即调度执行，且每个 Job 独立、无全局视图；而 Spark 的"惰性求值"指 transformations 只构建逻辑执行计划（DAG），直到 action 触发时才真正提交物理执行。这种"延迟提交"让 Spark 拥有了对整个查询的全局视图，Catalyst 优化器得以在逻辑计划和物理计划阶段做跨 Operator 的全局优化——如把 Filter 算子下推到数据源层（Filter Pushdown）、裁剪不需要的列（Column Pruning）、合并相邻的算子（Operator Fusion）、做基于代价的 Join 顺序选择（CBO）。MapReduce 因为没有这种全局视图，每个 Job 内部只能做局部优化，无法跨 Job 重排算子。

### 原理剖析

#### MapReduce 的急切执行模型

MapReduce 的编程接口是 `Job.waitForCompletion(true)`——用户配置好 Job 后调用此方法立即提交。每个 Job 的执行流程是：
1. 客户端将 Job 提交到 JobTracker/ResourceManager。
2. JobTracker 调度 Map 任务，Map 执行完毕后调度 Reduce 任务。
3. Reduce 完成后写 HDFS，Job 结束。

在这个过程中，**用户代码和引擎之间没有"逻辑计划"这个中间层**。用户写的 `map()` 和 `reduce()` 函数是黑盒，引擎无法理解其语义（比如不知道 map 里是否做了过滤）。因此引擎无法做任何跨算子优化——你无法让 MapReduce 引擎自动把"先读全表再过滤"优化成"在读取时过滤"，因为过滤逻辑藏在用户的 map 函数里。

#### Spark 的惰性求值：transformation vs action

Spark 的 API 分为两类：
- **Transformations**（`map`、`filter`、`join`、`groupBy` 等）：返回新的 RDD/DataFrame，但不立即执行，只更新 DAG。
- **Actions**（`count`、`collect`、`save` 等）：触发 DAG 的实际执行。

这种设计的关键在于：当 action 触发时，Spark 拥有了从数据源到最终输出的**完整逻辑计划**。DAGScheduler 可以看到整个 DAG，做 Stage 划分、Pipeline 优化、宽窄依赖分析。而在 DataFrame/Spark SQL 层面，这个"完整逻辑计划"更是以一棵未解析的逻辑树（Unresolved Logical Plan）的形式存在，Catalyst 优化器可以对其进行多次变换。

#### Catalyst 优化器：基于规则 + 基于代价

Armbrust et al. 在 SIGMOD 2015 论文 "Spark SQL: Relational Data Processing in Spark" 中详细描述了 Catalyst 的设计。Catalyst 的核心是一个基于 Scala 函数式编程的树变换框架，优化流程分为四个阶段：

1. **Analysis（分析）**：从 Unresolved Logical Plan 出发，结合 Catalog（表元数据、函数注册表）解析列名、类型、函数签名，生成 Resolved Logical Plan。这一步会做未定义列检查、类型推导。

2. **Logical Optimization（逻辑优化）**：对 Resolved Logical Plan 应用一系列规则（Rule），生成 Optimized Logical Plan。关键的规则包括：
   - **Predicate Pushdown**：把 Filter 算子尽可能下推到靠近数据源的位置。例如 `Filter(join(A, B), A.x > 10)` 优化为 `join(Filter(A, A.x > 10), B)`。这样 Join 的输入数据量减少，Join 代价降低。
   - **Column Pruning**：根据查询最终需要的列，裁剪中间算子不需要的列。例如 `select A.name from A join B on A.id = B.id`，B 表只需要 `id` 列，其他列在扫描时就可以不读。
   - **Constant Folding**：把 `1 + 1` 这样的常量表达式在编译期计算。
   - **Boolean Simplification**：`A and true` → `A`。

3. **Physical Planning（物理计划）**：将 Optimized Logical Plan 转换为多个候选 Physical Plan，选择代价最低的。这里引入 CBO（Cost-Based Optimizer），基于表的统计信息（行数、列基数、直方图）估算每个物理算子的代价。

4. **Code Generation（代码生成）**：Spark 2.0 引入 Whole-Stage Code Generation，把一个 Stage 内的多个算子编译成一个 Java 函数，消除虚函数调用，提升 CPU 效率。

#### 为什么惰性求值是这些优化的前提

以 Filter Pushdown 为例，对比 MapReduce 和 Spark：

**MapReduce 场景**：用户写了一个 Job，`map()` 函数里读取 HDFS 上的 Parquet 文件，然后做过滤。引擎看到的是一个黑盒 `map()` 函数，不知道里面读了哪些列、做了什么过滤。因此：
- 无法把过滤下推到 Parquet 读取层（Parquet 本身支持 Predicate Pushdown，但需要用户显式调用 `ParquetInputFormat.setFilterPredicate`）。
- 无法裁剪列（用户在 map 里读了什么列，引擎不知道）。

**Spark SQL 场景**：用户写 `spark.read.parquet("table").filter("x > 10").select("y")`。Catalyst 看到的是一棵完整的逻辑树：
```
Project[y]
  Filter[x > 10]
    Relation[table, Parquet]
```
优化器可以变换为：
```
Project[y]
  Relation[table, Parquet, pushedFilter=[x > 10], requiredColumns=[y]]
```
这样 Parquet 读取层（`ParquetFileFormat`）会：
- 利用 Parquet 的 Row Group 统计信息（min/max）跳过不满足 `x > 10` 的 Row Group。
- 只反序列化 `y` 列的数据，跳过其他列的读取（Column Pruning 直接落到文件格式层）。

这种"从查询语义到存储格式"的端到端优化，只有在惰性求值提供全局逻辑视图的前提下才能实现。MapReduce 的急切执行模型天然不具备这种能力。

#### Catalyst 的规则系统设计

Catalyst 的 Rule 用 Scala 的 `Tree.transform` 实现，每个 Rule 是一个偏函数 `PartialFunction[LogicalPlan, LogicalPlan]`。优化器把所有 Rule 串成一个 `RuleExecutor`，对逻辑树反复应用直到不动点（Fixed Point）。这种设计的优点是：
- **可扩展**：用户可以自定义 Rule 注入优化器（Spark 2.x 的扩展点 `ExperimentalMethods.extraOptimizations`，Spark 3.x 的 `OptimizerRules`）。
- **可组合**：Rule 之间相互独立，可以任意顺序组合。
- **可调试**：`spark.sql.planChangeLog.level=trace` 可以打印每个 Rule 的变换过程。

代价模型方面，Catalyst 的 `CostModel` 基于以下因素估算：
- 每个算子的输出行数（`stats.rowCount`）。
- 每个算子的输出大小（`stats.sizeInBytes`）。
- Join 的代价 ≈ 左表大小 + 右表大小（HashJoin）或 左表大小 × 右表大小（BroadcastHashJoin 的小表 broadcast 代价）。

Spark 3.0 引入了基于直方图的统计信息（`histogram`），让 CBO 对 Join 估算更准确。AQE（见 Q3）则进一步在运行时用真实统计信息修正 CBO 的估算误差。

### 技术映射

| 优化技术 | MapReduce 是否支持 | Spark Catalyst 支持 | 实现机制 |
|----------|-------------------|---------------------|----------|
| Filter Pushdown | 不支持（用户手动） | 支持 | Catalyst Rule `PushDownPredicates` + 数据源 API `SupportsPushDownFilters` |
| Column Pruning | 不支持 | 支持 | Catalyst Rule `ColumnPruning` + 数据源 API `SupportsPushDownAggregation` |
| Constant Folding | 不支持 | 支持 | Catalyst Rule `ConstantFolding` |
| Join Reorder | 不支持 | 支持（CBO） | Catalyst Rule `CostBasedJoinReorder` |
| Operator Fusion | 不支持 | 支持 | Whole-Stage Code Generation |
| Predicate Pushdown 到文件格式 | 手动 | 自动 | Parquet/ORC 的 Row Group 统计信息 |

### 设计权衡

**惰性求值的代价**：
1. **延迟启动**：用户提交查询后到真正执行有一段优化时间（通常毫秒到秒级），对小查询不友好。Spark 引入了AQE后优化开销更明显。
2. **调试困难**：因为 transformations 不立即执行，用户难以在中间步骤插入调试逻辑。Spark 提供了 `explain()` 和 `queryExecution` 来可视化逻辑/物理计划。
3. **内存占用**：逻辑计划树在内存中常驻，对超长查询（几百个算子）会有压力。

**急切执行的好处**：
1. **简单可预测**：用户写一步执行一步，行为直观。
2. **故障隔离**：每个 Job 独立失败，不影响后续 Job（但这也意味着没有全局优化）。

**何时选择惰性 vs 急切**：
- 复杂 SQL / 多表 Join / 需要全局优化：必须惰性（Spark SQL、Presto）。
- 简单的数据搬运（如 `hadoop distcp`）：急切执行更简单。
- 流处理：介于两者之间，需要"微批"模型（Spark Structured Streaming）。

### 生产经验与踩坑

1. **Filter Pushdown 对 Parquet 的实际效果**。曾遇到一个案例：查询 `select count(*) from huge_table where date = '2024-01-01'`，预期下推后只读一天的数据，但实际扫描了全表。排查发现 `date` 列在 Parquet 文件中没有写 Row Group 级别的 min/max 统计（旧版本 Spark 写入时默认关闭），导致下推失效。解决：重新用 `spark.sql.parquet.filterPushdown=true` 和 `spark.sql.parquet.writeLegacyFormat=false` 写入。

2. **CBO 的统计信息必须及时更新**。CBO 依赖 `ANALYZE TABLE ... COMPUTE STATISTICS`。如果表数据变化大但没重新统计，CBO 的 Join 顺序选择可能完全错误。生产实践中应该把 `ANALYZE TABLE` 纳入数据管道的调度。

3. **Column Pruning 的隐藏陷阱**。某些 UDF 引用了不必要的大对象（如整行），会导致 Column Pruning 失效。改用 `select` 显式列出需要的列，能强制触发裁剪。

4. **Whole-Stage Code Generation 的边界**。当 Stage 内有复杂 UDF 或无法编译的算子（如某些 Python UDF）时，会回退到非 codegen 模式，性能可能下降数倍。通过 `spark.sql.codegen.wholeStage=true` 和 `explain()` 检查是否有 `*(1)` 标记（`*` 表示 codegen）。

5. **AQE 与 CBO 的协同**。Spark 3.0+ 推荐 `spark.sql.adaptive.enabled=true`，但 AQE 和 CBO 并非完全互补——AQE 在 Shuffle 后用真实统计修正，CBO 在 Shuffle 前用估算统计决策。两者估算不准时可能产生次优计划。调试时需要同时看 `AdaptiveSparkPlan` 的各个阶段。

## Q3: Sort-Merge Join、Broadcast Hash Join、Shuffle Hash Join 分别在什么场景下最优？Spark 的 AQE（Adaptive Query Execution）如何在运行时动态切换 Join 策略？

### 核心结论

三种 Join 策略的选择取决于两侧数据的大小关系和分布：**Broadcast Hash Join** 在一侧数据小到能放进单 Executor 内存（默认 ≤10MB，可配到 8GB）时最优，零 Shuffle、性能最高；**Shuffle Hash Join** 在一侧数据较大但分区内能建 Hash 表（中等表）时优于 Sort-Merge，省去排序开销；**Sort-Merge Join** 在两侧都是大表时最稳健，因为它的内存占用可控（流式 merge，不需全量加载），且对倾斜和已排序数据友好。Spark 3.0 的 AQE 在运行时收集 Shuffle 后的真实分区统计，动态调整 Join 策略（如把误判的 Sort-Merge 升级为 Broadcast、合并小分区、拆分倾斜分区），弥补了 CBO 估算不准导致的静态计划次优问题。

### 原理剖析

#### 三种 Join 策略的算法与代价模型

**（1）Broadcast Hash Join（BHJ）**

算法：
1. Driver 从小表（BuildSide）拉取数据到 Driver 内存。
2. Driver 将小表 broadcast 到所有 Executor（通过 TorrentBroadcast，类似 BitTorrent 的分块传输）。
3. 每个 Executor 用小表构建 Hash 表。
4. 大表（ProbeSide）的每个分区在本地用 Hash 表查找匹配，无需 Shuffle。

代价：
- 网络代价：小表大小 × Executor 数（broadcast 是一对多，但 TorrentBroadcast 优化为 O(小表大小 × log(Executor数))）。
- 内存代价：每个 Executor 需要放下小表的 Hash 表。
- 时间代价：主要是 broadcast 传输 + 大表扫描，无 Shuffle、无排序。

适用场景：小表 ≤ `spark.sql.autoBroadcastJoinThreshold`（默认 10MB）。典型场景：维度表 Join 事实表、配置表 Join 业务表。

**（2）Shuffle Hash Join（SHJ）**

算法：
1. 对两侧数据按 Join Key 做 Hash Shuffle（相同 Key 进同一分区）。
2. 每个 Reduce 分区内，用较小一侧构建 Hash 表。
3. 较大一侧在本地 Hash 表中查找。

代价：
- 网络代价：两侧数据都要 Shuffle（按 Join Key Hash 分区）。
- 内存代价：每个 Reduce 分区内要放下较小侧的 Hash 表。
- 时间代价：Shuffle + Hash 构建查找，无排序。

适用场景：一侧是中等大小（比 Broadcast 阈值大，但分区内能建 Hash 表）。Spark 的判断条件（`JoinSelection`）是：`小表每分区大小 × 分区数 < 大表大小 × spark.sql.shuffle.partitions` 且小表能放进 BroadcastExchange 的内存限制。

**（3）Sort-Merge Join（SMJ）**

算法：
1. 对两侧数据按 Join Key 做 Hash Shuffle。
2. 每个分区内对两侧数据按 Join Key 排序。
3. 双指针流式 Merge：左侧和右侧各一个指针，按 Join Key 顺序推进，匹配则输出。

代价：
- 网络代价：两侧都要 Shuffle。
- 磁盘代价：排序可能 spill 到磁盘（外部排序）。
- 内存代价：极小，只需排序缓冲区和 merge 指针，可流式处理任意大小数据。
- 时间代价：Shuffle + 排序（O(n log n)） + Merge（O(n)）。

适用场景：两侧都是大表，无法放进内存。Spark 默认对非 Broadcast 场景优先选 Sort-Merge（因为它的鲁棒性最好）。

#### Volcano 模型与 Iterator 接口

Graefe 在 1994 年的论文 "Volcano: An Extensible and Parallel Dataflow System" 中提出了 Volcano 迭代器模型，奠定了现代数据库查询执行的基础。Volcano 模型的核心是每个算子实现 `open()` / `next()` 接口，数据以"拉"（pull）的方式从上层算子流向下层算子。Join 算子在 Volcano 模型中是一个迭代器：
- `open()`：初始化，对 Sort-Merge Join 而言是排序两侧输入。
- `next()`：返回下一个匹配的元组。

Spark 的物理算子（`SortMergeJoinExec`、`BroadcastHashJoinExec`、`ShuffledHashJoinExec`）本质上也是迭代器模型，只是 Spark 2.0 后用 Whole-Stage Codegen 把迭代器编译成紧凑的字节码，消除虚函数调用。

Volcano 论文中还提出了 `Exchange` 算子，用于在不同并行度间重分布数据——这正是 Spark 中 `ShuffleExchangeExec` 的原型。三种 Join 的 Shuffle 步骤都是通过 Exchange 算子实现的。

#### 为什么 Sort-Merge 是大表 Join 的默认选择

对比 SHJ 和 SMJ，当两侧都很大时：
- SHJ 要求每个分区内较小侧能放进内存建 Hash 表。如果分区内数据倾斜（某分区数据量远超平均），该分区会 OOM。
- SMJ 的排序可以 spill 到磁盘，内存占用恒定（排序缓冲区大小），不会因倾斜而 OOM。

因此 Spark 的 `JoinSelection` 规则：如果不满足 Broadcast 条件，且不满足 Shuffle Hash 的内存条件，就选 Sort-Merge。这是出于鲁棒性考虑的保守选择。

#### AQE：运行时动态切换 Join 策略

Spark 3.0 引入 AQE（Adaptive Query Execution），核心论文和设计文档 "Adaptive Query Execution in Apache Spark 3.0" 描述了三大特性：

**（1）动态切换 Join 策略（Dynamic Switch Join Strategies）**

问题：CBO 在 Shuffle 前估算的统计信息可能不准。例如，一个 Filter 后的表估算结果是 100GB，CBO 选了 Sort-Merge Join；但实际 Filter 后只有 50MB，应该用 Broadcast Hash Join。

AQE 机制：在 Shuffle 完成后（即 Exchange 算子的 `mapOutputStatistics` 收集到真实分区大小），AQE 重新评估 Join 策略。如果发现某侧实际大小 ≤ Broadcast 阈值，就把 Sort-Merge Join 替换为 Broadcast Hash Join。

实现细节：
- `AdaptiveSparkPlanExec` 在每个 Exchange 节点后插入逻辑优化点。
- 收集 `MapOutputStatistics`（每个分区的大小、行数）。
- 调用 `DemoteBroadcastHashJoin` 和 `ConvertSortMergeJoinToBroadcastHashJoin` 规则重新选择物理算子。

**（2）动态合并 Shuffle 分区（Dynamic Coalesce Partitions）**

问题：默认 `spark.sql.shuffle.partitions=200`，但实际数据可能只有 10MB，导致 200 个分区每个只有 50KB，每个分区启动一个 Task 开销巨大（Task 调度开销约 5ms/Task）。

AQE 机制：根据 `spark.sql.adaptive.advisoryPartitionSizeInBytes`（默认 64MB），把多个小分区合并成一个大分区，减少 Task 数量。

**（3）动态处理倾斜（Dynamic Skew Handling）**

问题：某个 Join Key 数据量远超其他 Key，导致该分区的 Task 成为长尾。

AQE 机制：检测到分区大小超过中位数的 `spark.sql.adaptive.skewJoin.skewedPartitionFactor`（默认 5）倍且超过 `skewedPartitionThresholdInBytes`（默认 256MB）时，把该倾斜分区拆分成多个子分区，分别与对侧的对应分区做 Join，最后 Union。这避免了单点长尾。

#### AQE 的运行时决策流程

```
1. 逻辑计划 → Catalyst 优化 → 物理计划（静态，基于 CBO 估算）
2. 提交执行，遇到 Exchange 节点时收集真实统计
3. 真实统计触发重新优化：
   - 重新评估 Join 策略（SMJ → BHJ）
   - 合并小分区
   - 拆分倾斜分区
4. 用优化后的计划继续执行后续算子
```

这种"边执行边优化"的能力，是 Spark 相比传统数据库（一次性编译执行）的独特优势。代价是每个 Exchange 都是一次优化点，引入额外的计划和调度开销。

### 技术映射

| Join 策略 | Spark 物理算子 | 触发条件 | 典型场景 |
|-----------|---------------|----------|----------|
| Broadcast Hash Join | `BroadcastHashJoinExec` | 一侧 ≤ broadcastThreshold | 维度表 Join 事实表 |
| Shuffle Hash Join | `ShuffledHashJoinExec` | 一侧中等，能建 Hash 表 | 中等表 Join 大表 |
| Sort-Merge Join | `SortMergeJoinExec` | 两侧都大，默认 fallback | 事实表 Join 事实表 |
| Broadcast Nested Loop Join | `BroadcastNestedLoopJoinExec` | 非 equi-join（如 `<`） | 范围 Join |
| Cartesian Product Join | `CartesianProductExec` | 无 Join Key 的 cross join | 笛卡尔积 |

AQE 相关配置：
- `spark.sql.adaptive.enabled=true`
- `spark.sql.adaptive.coalescePartitions.enabled=true`
- `spark.sql.adaptive.skewJoin.enabled=true`
- `spark.sql.adaptive.localShuffleReader.enabled=true`

### 设计权衡

**Broadcast Hash Join 的权衡**：
- 优点：零 Shuffle，性能最高。
- 缺点：Driver 内存瓶颈（broadcast 要先到 Driver）。如果小表实际是 5GB，Driver 需要 5GB 内存，容易 OOM。
- 风险：阈值判断基于估算，可能误判小表（估算 100MB，实际 5GB），导致 broadcast 失败回退。

**Shuffle Hash Join 的权衡**：
- 优点：无排序开销，比 Sort-Merge 快。
- 缺点：内存风险，倾斜分区可能 OOM。Spark 默认禁用（`spark.sql.join.preferSortMergeJoin=true`），需要手动开启。
- 适用：明确知道数据均匀分布且较小侧能放内存。

**Sort-Merge Join 的权衡**：
- 优点：内存可控，鲁棒性强。
- 缺点：排序开销（O(n log n)），对已排序数据其实浪费。
- 优化：如果数据源本身按 Join Key 排序（如 Iceberg 的 Sort Order），可以跳过排序步骤。

**AQE 的权衡**：
- 优点：弥补估算误差，自适应真实数据。
- 缺点：优化点引入额外开销；对短查询可能不划算；某些场景下多次重新优化导致计划抖动。
- 边界：AQE 只在 Exchange 边界生效，Exchange 之间的算子无法动态调整。

### 生产经验与踩坑

1. **Broadcast 阈值的调优**。默认 10MB 太保守，生产环境通常调到 100MB~1GB（`spark.sql.autoBroadcastJoinThreshold=1073741824`）。但要注意 Driver 内存至少要是阈值的 2 倍（broadcast 要先到 Driver）。

2. **SHJ 被误选导致 OOM**。开启 `spark.sql.join.preferSortMergeJoin=true`（默认）能避免 SHJ 被误选。如果确实想用 SHJ，要确保数据分布均匀，否则倾斜分区必 OOM。

3. **AQE 合并分区的副作用**。AQE 合并分区后，下游算子的并行度降低，可能影响写入性能（如写 Iceberg 时分区数变少，并发度降低）。需要平衡 `advisoryPartitionSizeInBytes` 和输出文件数。

4. **倾斜处理的边界**。AQE 的倾斜拆分只对 Sort-Merge Join 有效，对 Broadcast Hash Join 无效（因为 BHJ 无 Shuffle）。如果倾斜发生在 BHJ 之前，需要手动用 `salting` 技巧打散。

5. **统计信息缺失导致 AQE 失效**。AQE 依赖 `MapOutputStatistics`，如果 Shuffle 写入失败或被跳过（如全在内存），统计信息缺失，AQE 不会触发。生产中遇到 AQE "不生效" 时，先检查 `spark.sql.adaptive.enabled` 和物理计划中是否有 `Exchange` 节点。

6. **Broadcast 失败的静默回退**。Spark 2.x 中，Broadcast 如果超时会静默回退到 Sort-Merge，没有任何告警，导致性能突降难以排查。Spark 3.x 改进了日志，但仍建议监控 `BroadcastExchangeExec` 的耗时。

## Q4: MapReduce 在 Google 内部已经被 FlumeJava 和 MillWheel 取代，但 Apache Hadoop 生态中的 MapReduce 为什么还存活了这么久？替换 MapReduce 的瓶颈是技术还是生态？

### 核心结论

MapReduce 在 Hadoop 生态中存活至今，**瓶颈主要是生态而非技术**。技术层面，Spark/Tez/Flink 早已在性能和编程模型上全面超越 MapReduce；但 MapReduce 凭借三重护城河长期存续：（1）HDFS 深度绑定的存储-计算耦合模型，迁移成本高；（2）大量遗留系统（Hive on MR、Pig、Cascading、Crunch、Sqoop）和业务脚本依赖 MapReduce API；（3）运维团队和开发者的技能惯性，以及 MapReduce 极致的稳定性与可预测性。Google 内部能用 FlumeJava/MillWheel 快速替换，是因为 Google 自研全栈（GFS + FlumeJava + MillWheel + Dataflow），无第三方生态绑定；而 Hadoop 生态是多厂商博弈的产物，替换需要跨组织协调，技术债务被生态债务放大。

### 原理剖析

#### Google 内部的替换路径：FlumeJava 与 MillWheel

**FlumeJava（PLDI 2010）**

Chambers et al. 在 PLDI 2010 论文 "FlumeJava: Easy, Efficient Data-Parallel Pipelines" 中提出了 FlumeJava，核心思想是用高层抽象替代手写 MapReduce：

1. **PCollection 抽象**：FlumeJava 的核心数据结构是 `PCollection<T>`（并行集合），类似 Spark 的 RDD 但更早。用户操作 PCollection 而非直接写 map/reduce 函数。

2. **Deferred Evaluation（延迟求值）**：FlumeJava 把所有操作记录为一个"管道图"（pipeline graph），直到调用 `Pipeline.run()` 时才编译成一组 MapReduce Job 执行。这与 Spark 的惰性求值如出一辙，但 FlumeJava 比 Spark 早 2 年。

3. **Optimizer**：FlumeJava 有一个优化器，能把多个操作融合成一个 MapReduce Job（Operator Fusion），避免中间状态物化。例如 `PCollection.map(f).filter(p).map(g)` 可以融合成单个 Map 任务的 `map(f).filter(p).map(g)`。

4. **Combiners 与 Mappers 的自动生成**：用户写高层操作（如 `groupByKey` + `combineValues`），FlumeJava 自动生成对应的 MapReduce Combiner 和 Reducer。

FlumeJava 在 Google 内部迅速取代了手写 MapReduce，因为它把开发者从"拼装 MapReduce Job"的低级劳动中解放出来，同时优化器保证了性能不输手写。

**MillWheel（SIGMOD 2013）**

Akidau et al. 在 SIGMOD 2013 论文 "MillWheel: Fault-Tolerant Stream Processing at Internet Scale" 中提出了 MillWheel，解决 MapReduce 无法处理流式数据的问题：

1. **无限数据流**：MillWheel 处理无界数据流，每个 record 有一个时间戳，支持事件时间语义。
2. **持久化状态**：每个算子可以维护持久化状态（keyed state），状态定期 checkpoint 到 Bigtable。
3. **Exactly-Once 语义**：通过幂等写和 checkpoint 实现 exactly-once，即使算子失败重启也不会重复处理。
4. **Watermark**：MillWheel 引入了 watermark 机制，表示"事件时间 X 之前的数据应该都已到达"，用于触发窗口计算。

MillWheel + FlumeJava 后来演化为 Google Cloud Dataflow（2014 年发布），统一了批和流的编程模型。Google 在 2015 年后基本不再使用原生 MapReduce。

#### 为什么 Google 能快速替换

1. **全栈自研**。Google 控制 GFS（存储）、MapReduce/FlumeJava/MillWheel（计算）、Bigtable（状态存储）、Colossus（下一代 GFS）的全栈，替换 MapReduce 不需要跨组织协调。
2. **内部应用强管控**。Google 内部的数据处理任务大多由 SWE 团队直接编写，迁移到 FlumeJava 是"改代码"而非"改系统"。
3. **无第三方厂商博弈**。没有 Cloudera、Hortonworks、AWS 等多方利益，决策链条短。

#### Hadoop 生态的替换困境

**（1）存储-计算耦合的迁移成本**

MapReduce 与 HDFS 是天然绑定：MapReduce 的输入是 HDFS 的 `InputSplit`，输出写 HDFS。Spark 虽然也读 HDFS，但其内存模型和 Shuffle 机制与 MapReduce 完全不同。企业要把 MapReduce 作业迁移到 Spark，需要：
- 重写作业逻辑（MR API → RDD/DataFrame API）。
- 调优 Spark 内存参数（`spark.executor.memory`、`spark.memory.fraction` 等）。
- 验证结果一致性（Spark 的 Shuffle 顺序不保证，对有序输出敏感的作业需特殊处理）。

对于一个有几千个 MapReduce Job 的企业，迁移工作量是巨大的。

**（2）遗留系统的生态锁定**

- **Hive on MapReduce**：早期 Hive 默认执行引擎是 MapReduce，大量企业的数仓 SQL 跑在 Hive on MR 上。虽然 Hive on Tez/Spark 性能更好，但迁移需要重新调优所有 SQL（执行计划不同，可能产生不同结果或性能回归）。
- **Pig Latin**：Pig 的执行引擎默认是 MapReduce，虽然 Pig on Tez 存在，但 Pig 本身在 Spark 出现后逐渐被淘汰，没有动力迁移。
- **Sqoop**：Sqoop 的导入导出基于 MapReduce，虽然 Sqoop on Spark 的替代品（Spark JDBC）存在，但 Sqoop 的增量导入逻辑复杂，难以直接替换。
- **Cascading / Crunch**：这些高层 API 封装了 MapReduce，迁移到 Spark 需要重写所有数据处理逻辑。

**（3）运维惯性与技能债务**

MapReduce 的运维模型极其简单：
- 每个 Job 是独立的 YARN Application，故障影响范围小。
- 日志和监控标准化（History Server）。
- 资源管理简单（Container 级别）。

Spark 的运维复杂度高得多：
- Executor 内存管理（堆内 + 堆外 + 用户内存 + 统一内存管理）。
- Shuffle 文件管理（本地磁盘、可能丢失导致 FetchFailure）。
- Driver 单点故障（需要 HA 配置）。

很多企业的运维团队习惯了 MapReduce 的"傻瓜式"运维，对 Spark 的复杂性有抵触。这种技能债务是技术替换的隐性成本。

**（4）MapReduce 的稳定性优势**

MapReduce 的设计哲学是"宁可慢，也要稳"：
- 每个 Job 独立，无共享状态，故障隔离完美。
- 中间状态物化到 HDFS，重启不会丢失进度。
- 没有内存缓存，不会 OOM 导致整个 Application 挂掉。

对于 SLA 要求极高但性能要求不高的批处理（如银行对账、合规报表），MapReduce 的稳定性比 Spark 的性能更有价值。这是 MapReduce 至今仍在金融、电信等行业使用的重要原因。

#### 技术瓶颈 vs 生态瓶颈的辨析

| 维度 | 技术层面 | 生态层面 |
|------|----------|----------|
| 性能 | Spark 已远超 MR（10~100x） | 性能不是阻碍替换的因素 |
| 编程模型 | Spark/SQL 已远优于 MR API | 遗留代码迁移成本高 |
| 容错 | Spark 血统 + checkpoint 已成熟 | 运维心智模型需要重建 |
| 部署 | Spark on YARN / K8s 已成熟 | 集群升级和双栈运行成本 |
| 人才 | Spark 人才充足 | MR 老运维转型成本 |

结论：技术早已不是瓶颈，生态（遗留系统、技能债务、运维惯性）才是真正的阻碍。这与很多技术债务的本质一致——技术问题可以用技术解决，生态问题需要组织和时间的演化。

### 技术映射

| 替换关系 | Google 内部 | Hadoop 生态 | 现状 |
|----------|-------------|-------------|------|
| MapReduce → 高层批处理 | FlumeJava | Hive/Spark SQL/Pig | Hive on MR 仍有遗留 |
| MapReduce → 流处理 | MillWheel | Flink/Spark Streaming | 流处理已脱离 MR |
| MapReduce → 统一批流 | Dataflow | Flink / Spark Structured Streaming | 趋势但未完全替换 |
| HDFS → 对象存储 | Colossus | S3/OSS/ABS | 新工作负载上对象存储 |

### 设计权衡

**保留 MapReduce 的场景**：
- 遗留系统稳定运行，无性能痛点。
- SLA 极高，对稳定性要求 > 性能。
- 运维团队无 Spark 经验，迁移风险大。
- 作业逻辑简单（如简单的 ETL），MapReduce 足够。

**替换 MapReduce 的场景**：
- 迭代式算法（ML 训练），Spark 内存缓存收益巨大。
- 多 Stage SQL 查询，Spark SQL/Tez 的 DAG 优化显著。
- 流批一体需求，Flink/Spark Structured Streaming 统一栈。
- 新项目，无历史包袱，直接用现代栈。

**渐进式迁移策略**：
- 新作业用 Spark，老作业保留 MapReduce，逐步替换。
- 先迁移性能瓶颈作业（收益最大）。
- 用 Spark 的 `mapPartitions` 等 API 模拟 MapReduce 语义，降低迁移难度。
- 建立双栈监控，对比迁移前后的性能和正确性。

### 生产经验与踩坑

1. **Hive on MR → Hive on Tez 的"静默性能回归"**。某企业迁移后发现部分 SQL 性能反而下降，原因是 Tez 的 Join 顺序优化与 MR 不同，某些复杂 SQL 在 Tez 下产生了次优计划。需要逐个 SQL 调优。

2. **Spark 的 Shuffle 不稳定性**。大表 Join 时 Spark 的 Shuffle 文件可能丢失（Executor 被驱逐或磁盘满），导致 FetchFailure 重试。MapReduce 的 Shuffle 是 HDFS 级别的，不会丢。这是 Spark 在超大规模作业上的痛点。

3. **Sqoop 迁移到 Spark JDBC 的陷阱**。Sqoop 的增量导入基于 `--last-value`，Spark JDBC 需要自己实现增量逻辑，容易出错。很多企业选择保留 Sqoop 用于数据库导入，仅用 Spark 做后续处理。

4. **YARN 调度器的差异**。MapReduce 的每个 Task 是独立 Container，Spark 的 Executor 是长驻 Container。在 Capacity Scheduler 下，Spark 的资源抢占行为与 MapReduce 不同，可能导致队列资源争抢。

5. **"MapReduce 已死"是夸大其词**。截至 2024 年，仍有大量企业在使用 Hive on MR 跑核心数仓。原因不是技术落后，而是迁移成本和风险评估的综合结果。技术选型不应盲目追新，而应基于业务价值。

## Q5: 批处理的"输出不可变性"（Output Immutability）带来了什么好处？数据湖（Delta Lake/Iceberg/Hudi）如何利用这一特性实现 Time Travel？

### 核心结论

批处理的"输出不可变性"指每次批处理运行产生一个完整的、不可修改的输出数据集（通常以时间戳或版本号标识），后续运行产生新版本而非原地更新。这种不可变性带来四大好处：**可重现性**（相同输入重跑得到相同输出，便于调试与审计）、**故障隔离**（失败的批处理不污染历史数据）、**版本可追溯**（任意历史版本可查询）、**并发友好**（读取不受写入影响，无需锁）。数据湖格式（Delta Lake/Iceberg/Hudi）将这一理念落表级 ACID：通过快照（Snapshot）+ 不可变数据文件 + 元数据日志，实现了 Time Travel（按时间或版本号查询历史数据），同时支持 upsert/delete 等"看起来可变"的操作——本质是"写新文件 + 标记旧文件为删除"，底层文件不可变。

### 原理剖析

#### MapReduce 时代的输出不可变性

MapReduce 的设计天然支持输出不可变性：
- 每个 Job 的输出写到一个新的 HDFS 目录（如 `/output/2024-01-01/`）。
- 下一天的 Job 写到 `/output/2024-01-02/`，不覆盖前一天的输出。
- 如果 Job 失败，输出目录是空的或部分写入的，但不会影响之前成功的输出。

这种"每天一个目录"的模式是事实上的不可变输出。好处是：
- 重跑某天的数据只需重新提交 Job，覆盖该目录。
- 调试时可以对比前后两天的输出差异。
- 下游消费者可以按日期读取特定版本。

但 MapReduce 的不可变性是"约定俗成"的，不是引擎强制的。如果用户写代码直接覆盖 HDFS 文件，就没有不可变性。而且 MapReduce 不支持 upsert——如果数据源是 CDC（变更日志），MapReduce 需要全量重算或用复杂的 merge 逻辑。

#### 数据湖格式：把不可变性提升到表级 ACID

传统的 Hadoop 数据湖（Hive on HDFS）有两个痛点：
1. **无 ACID**：并发写入会损坏数据，只能"读时不写、写时不读"。
2. **无 Time Travel**：覆盖写后历史数据丢失，无法回溯。

Delta Lake、Iceberg、Hudi 通过"不可变数据文件 + 元数据日志"的架构解决了这两个问题。Armbrust et al. 在 CIDR 2021 论文 "Lakehouse: A New Generation of Open Platforms that Unify Data Warehousing and Advanced Analytics" 中系统阐述了这一架构。

#### Delta Lake 的实现

Delta Lake 的核心是事务日志（`_delta_log` 目录）：
1. **数据文件不可变**：表数据以 Parquet 文件存储，一旦写入不再修改。
2. **事务日志（Delta Log）**：每次写操作（insert/update/delete/merge）产生一个 JSON 格式的日志文件（`00000000000000000000.json`、`00000000000000000001.json`...），记录"新增了哪些文件"、"删除了哪些文件"。
3. **快照（Snapshot）**：日志的每个版本对应一个表快照。读取版本 N 的表 = 应用日志 0~N 后，活跃文件集合的并集。
4. **Time Travel**：`SELECT * FROM table VERSION AS OF 5` 或 `FOR SYSTEM_TIME AS OF '2024-01-01'` 读取特定快照。

Update/Delete 的实现：
- 找到包含被更新数据的 Parquet 文件。
- 读取这些文件，修改后写新的 Parquet 文件。
- 在日志中标记旧文件为 "removed"，新文件为 "added"。
- 旧文件物理上不删除（直到 `VACUUM` 清理）。

这种"写时复制"（Copy-on-Write）保证了读操作永远看到一致的快照，不受并发写影响。

#### Apache Iceberg 的实现

Iceberg 的设计与 Delta 类似，但元数据分层更清晰：
1. **数据文件（Data Files）**：不可变的 Parquet/ORCAvro 文件。
2. **清单文件（Manifest Files）**：每个 Manifest 记录一组数据文件的路径、分区、统计信息（min/max/row count）。Manifest 本身也是不可变的。
3. **清单列表（Manifest List / Snapshot）**：每个快照引用一组 Manifest Files，定义了该快照的完整数据集。
4. **元数据文件（Metadata File）**：记录当前快照列表、表 schema、分区规则。

Time Travel 通过指定快照 ID 实现：
- `SELECT * FROM table.snapshot_id = 1234567890`
- `SELECT * FROM table FOR SYSTEM_TIME AS OF '2024-01-01 12:00:00'`

Iceberg 的优势：
- **分区演进（Partition Evolution）**：因为分区信息在 Manifest 中记录，可以不改数据文件就改变分区策略。
- **Schema 演进**：列增删改不影响历史数据文件（缺失列返回 null）。
- **Manifest 的统计信息**：读取时可以根据 min/max 跳过整个 Manifest，加速查询。

#### Apache Hudi 的实现

Hudi 有两种表类型，对应不同的不可变策略：

1. **Copy-On-Write（COW）**：
   - 每次 upsert 都重写整个 Parquet 文件（类似 Delta）。
   - 读性能最优（直接读 Parquet），写放大严重。
   - 适合读多写少的场景。

2. **Merge-On-Read（MOR）**：
   - Upsert 先写到行级的 Avro 日志文件（log file）。
   - 读时合并 Parquet 基础文件 + Avro 增量日志。
   - 写性能最优，读有合并开销。
   - 适合写多读少的场景（如 CDC 同步）。

Hudi 的 Time Travel 通过 Timeline 实现：
- Timeline 记录所有 `commit`、`deltacommit`、`compaction` 等操作。
- 每个 instant 对应一个表状态。
- `SELECT * FROM table AS OF '20240101120000'` 读取该时刻的状态。

#### Lakehouse 论文的核心论点

Armbrust et al. 在 Lakehouse 论文中提出，数据湖（低成本存储 + 开放格式）和数据仓库（ACID + 高性能查询）的优势可以统一：
1. **底层是数据湖**：Parquet/ORC 等开放格式存储在 S3/HDFS。
2. **上层是事务层**：Delta/Iceberg/Hudi 提供 ACID 和 Time Travel。
3. **中间是元数据管理**：事务日志 + 快照机制。

这种架构的关键洞察是：**不可变性是 ACID 和 Time Travel 的共同基础**。因为数据文件不可变，所以：
- 读操作不需要加锁（看到的快照不会变）。
- 写操作只追加新文件 + 更新元数据，互不干扰。
- 历史快照天然保留，Time Travel 是"免费"的。

#### 输出不可变性的好处再梳理

1. **可重现性**：相同输入 + 相同代码 = 相同输出。如果发现某天数据异常，可以用历史快照重放计算，定位问题。这是"数据可审计"的基础。

2. **故障隔离**：批处理失败不会污染已成功的输出。MapReduce 时代靠"新目录"实现，数据湖靠"新快照"实现。失败的写操作只是产生了一个未提交的快照，不影响已提交的快照。

3. **版本可追溯**：Time Travel 让用户可以查询"一周前的数据状态"，用于：
   - 数据质量回溯（某指标什么时候开始异常？）。
   - A/B 测试（用历史数据重跑算法对比）。
   - 合规审计（监管要求保留某时刻的数据快照）。

4. **并发友好**：读操作看到的是某个快照的一致性视图，写操作在后台产生新快照。这种 MVCC 式的并发控制无需锁，适合"读多写少"的数据湖场景。

5. **回滚能力**：如果某次写操作有问题（如数据质量差），可以回滚到上一个快照。Delta 的 `RESTORE TABLE TO VERSION AS OF N`、Iceberg 的 `rollback-to-snapshot` 都是利用不可变性实现的。

### 技术映射

| 特性 | Hive（传统） | Delta Lake | Iceberg | Hudi |
|------|--------------|------------|---------|------|
| ACID | 不支持（需要锁） | 支持 | 支持 | 支持 |
| Time Travel | 不支持 | 支持 | 支持 | 支持 |
| Upsert | 难（需全量重写） | 支持 | 支持 | 支持（MOR 优化） |
| Schema 演进 | 有限 | 支持 | 支持（更强） | 支持 |
| 分区演进 | 不支持 | 有限 | 支持 | 有限 |
| 底层文件 | 不可变 | 不可变 | 不可变 | COW 不可变 / MOR 增量日志 |
| 元数据格式 | Metastore | Delta Log | Manifest List | Timeline |

### 设计权衡

**不可变性的代价**：
1. **存储放大**：每次更新产生新文件，旧文件不立即删除。需要定期 `VACUUM`（Delta）/ `expire_snapshots`（Iceberg）清理。存储成本是可变模型的 2~5 倍（取决于更新频率）。
2. **写放大**：COW 模式下，更新一行需要重写整个文件。MOR 模式缓解了写放大但引入读放大。
3. **小文件问题**：频繁写入产生大量小文件，影响查询性能。需要 Compaction（Hudi）/ `OPTIMIZE`（Delta）/ `rewrite_data_files`（Iceberg）。

**可变性 vs 不可变性的选择**：
- OLTP 场景（高频小事务）：可变性更合适（行级更新）。
- 数据湖场景（批处理 + 分析查询）：不可变性更合适（append-only + 快照）。
- 混合场景：MOR 模式（Hudi）或频繁 Compaction（Delta/Iceberg）。

**Time Travel 的保留策略**：
- 保留所有历史快照成本太高，通常设置保留期（如 7 天 / 30 天）。
- Delta 的 `logRetentionDuration`（默认 30 天）。
- Iceberg 的 `history.expire.max-snapshot-age-ms`。
- 超过保留期的快照被清理，无法 Time Travel。

### 生产经验与踩坑

1. **小文件问题的治理**。Flink 实时写入 Delta/Iceberg 会产生大量小文件（每次 checkpoint 一个文件）。生产中必须配置 Compaction 任务定期合并。Delta 的 `OPTIMIZE`、Iceberg 的 `rewrite_data_files`、Hudi 的 `cluster` 都是治理手段。建议每 10 分钟 ~ 1 小时跑一次 Compaction。

2. **Time Travel 的存储成本**。曾有团队开启 1 年的 Time Travel 保留期，结果存储成本翻 3 倍。需要根据业务需求平衡保留期和成本。合规要求长的可以下沉到冷存储。

3. **Delta 的 `VACUUM` 误删教训**。`VACUUM` 默认保留 7 天的文件，如果误改成 0 天会删掉所有未提交的文件（包括正在写的）。生产中要设置 `spark.databricks.delta.vacuum.parallelDelete.enabled` 和保留期下限。

4. **Iceberg 的分区演进陷阱**。分区演进后，旧数据仍按旧分区存储，新数据按新分区存储。查询时需要扫描两种分区的 Manifest，可能影响性能。建议在低峰期做分区演进，并触发 `rewrite_data_files` 迁移旧数据。

5. **Hudi MOR 的读放大**。MOR 表的读需要合并 Parquet + Avro 日志，如果日志积压太多，查询性能急剧下降。必须定期 Compaction 把日志合并回 Parquet。Compaction 的频率取决于查询延迟要求。

6. **跨表事务的缺失**。Delta/Iceberg/Hudi 都是单表 ACID，不支持跨表事务。如果需要"同时更新两张表"，要么用幂等重试，要么接受最终一致。这是数据湖相比数据库的先天短板。

7. **并发写的冲突处理**。多个作业同时写同一张表时，Delta 用乐观并发控制（Optimistic Concurrency Control），后提交者检测冲突。如果冲突严重（如同时 upsert 同一分区），会频繁重试失败。Iceberg 用类似机制。生产中应避免对同一分区并发写。

## Q6: 书中说"批处理引擎是构建派生数据系统的好工具"，具体的应用模式有哪些？比如 ETL、物化视图维护、机器学习特征工程？

### 核心结论

DDIA 第10章提出"批处理引擎是构建派生数据系统的好工具"，核心在于批处理的三个特性使其特别适合"从原始数据派生衍生视图"：（1）**容错性**——失败可重跑，结果可重现；（2）**可扩展性**——能处理 TB/PB 级数据；（3）**解耦性**——派生数据的生成与原始数据的写入解耦，无需同步事务。具体应用模式可分为五大类：**ETL/ELT 数据搬运与清洗**、**物化视图维护（搜索索引、物化聚合、推荐特征）**、**机器学习特征工程与训练数据生成**、**图关系派生（用户画像、社交关系）**、**跨系统数据同步（数据库到搜索、数据库到缓存）**。Stonebraker 在 2010 年对 MapReduce 的批评虽然指出了其相比并行数据库的不足，但也承认批处理在"非结构化数据处理 + 复杂转换"场景下的不可替代性——这正是派生数据系统的核心需求。

### 原理剖析

#### Stonebraker 的批评与批处理的定位

Stonebraker 等人在 2010 年的论文 "MapReduce and Parallel DBMSs: Friends or Enemies?" 中对 MapReduce 提出了尖锐批评：
- 缺乏 schema（不如并行数据库的强 schema）。
- 缺乏索引（只能全表扫描）。
- 缺乏高级查询语言（不如 SQL 声明式）。
- 性能不如并行数据库（在 TPC-H 基准上）。

但 Stonebraker 也承认，MapReduce 适合的场景是：
- **非结构化/半结构化数据**（日志、文本、JSON）。
- **复杂的转换逻辑**（需要自定义代码，而非 SQL）。
- **一次性的大规模数据处理**（而非反复查询）。

这些正是派生数据系统的典型场景：从原始日志（非结构化）派生出搜索索引、推荐特征、用户画像（结构化衍生视图）。批处理引擎在这类场景下不是数据库的替代，而是数据库的"上游数据工厂"。

#### 派生数据系统的定义与特征

DDIA 第1章和第10章都强调"派生数据"的概念：
- **记录系统（System of Record）**：数据的权威来源（如业务数据库、事务日志）。
- **派生数据（Derived Data）**：从记录系统通过某种转换生成的衍生视图（如搜索索引、缓存、物化视图、推荐模型）。

派生数据系统的特征：
1. **可重算**：派生数据丢失可以从记录系统重算恢复。
2. **最终一致**：派生数据与记录系统之间有延迟，但最终一致。
3. **针对查询优化**：派生数据的结构针对特定查询优化（如搜索索引针对全文检索、物化聚合针对分析查询）。

批处理引擎之所以适合构建派生数据系统，是因为：
- 批处理的"输入→转换→输出"模型天然匹配"记录系统→转换→派生数据"的模式。
- 批处理的容错性保证派生数据的可重算性。
- 批处理的可扩展性保证能处理记录系统的全量数据。

#### 应用模式一：ETL / ELT 数据搬运与清洗

这是批处理最经典的应用。模式：
1. **Extract**：从源系统（数据库、日志、API）抽取数据。
2. **Transform**：清洗、标准化、富化（如 IP 地理编码、用户 ID 关联）。
3. **Load**：加载到目标系统（数据仓库、数据湖）。

Eckerson 在 "Transforming Data into Insights with Analytics" 中描述了数据到洞察的管道：
```
数据源 → ETL → 数据仓库 → BI 分析 → 业务洞察
```

批处理引擎在 ETL 中的作用：
- **Hive on MapReduce**：早期大数据 ETL 的标准工具，SQL 化的 ETL。
- **Spark**：现代 ETL 的主力，支持复杂转换逻辑（UDF + SQL 混合）。
- **Sqoop**：关系数据库到 HDFS 的批量导入。

ELT（Extract-Load-Transform）是 ETL 的变体：先 Load 原始数据到数据湖，再在湖内 Transform。这种模式得益于数据湖的低成本存储和 Spark/Delta 的计算能力，逐渐成为主流。

#### 应用模式二：物化视图维护

物化视图（Materialized View）是预计算的查询结果，加速重复查询。批处理引擎可以定期（如每天/每小时）刷新物化视图：

1. **搜索索引构建**：
   - 输入：产品数据库的全量数据。
   - 转换：提取字段、分词、构建倒排索引。
   - 输出：Elasticsearch / Solr 索引。
   - 典型实现：Hadoop 的 `MapReduce` 作业读数据库，输出 Lucene 索引文件，然后加载到 Elasticsearch。

2. **物化聚合**：
   - 输入：明细事实表（如订单表）。
   - 转换：按维度聚合（如按天 × 城市 × 品类汇总销售额）。
   - 输出：聚合表（如 DWS 层）。
   - 典型实现：Hive/Spark SQL 的 `GROUP BY` + `INSERT OVERWRITE`。

3. **推荐特征预计算**：
   - 输入：用户行为日志。
   - 转换：计算用户兴趣向量、物品相似度矩阵。
   - 输出：特征表 / 模型文件。
   - 典型实现：Spark MLlib 的协同过滤 + 特征工程。

批处理维护物化视图的好处：
- **解耦**：物化视图的刷新不影响业务数据库的写入。
- **批量高效**：全量重算比增量更新更简单可靠。
- **可回溯**：每次刷新产生一个版本，可以对比历史。

#### 应用模式三：机器学习特征工程

ML 特征工程是批处理的重要应用，模式：
1. **特征提取**：从原始日志提取特征（如用户过去 30 天的点击序列）。
2. **特征聚合**：计算统计特征（如点击率、转化率、留存率）。
3. **特征拼接**：把多源特征 join 成训练样本。
4. **训练数据生成**：生成带标签的训练集，输出到模型训练。

Spark MLlib 和特征平台（如 Feast、Tecton）都依赖批处理引擎生成离线特征。典型流程：
```
原始日志 → Spark 批处理 → 特征表（Parquet/Delta）→ 模型训练
```

批处理在特征工程中的优势：
- **窗口聚合**：批处理擅长大规模窗口聚合（如 30 天滑动窗口）。
- **多源 join**：批处理可以 join 用户表、行为表、物品表生成富特征。
- **可重现性**：相同输入产生相同特征，保证实验可复现。

挑战：
- **特征一致性**：离线特征（批处理生成）和在线特征（实时计算）可能不一致，导致训练-服务偏差。解决方案是特征平台统一离线/在线特征定义。

#### 应用模式四：图关系派生

社交网络、推荐系统依赖图关系数据，批处理可以派生：
1. **用户画像**：从行为日志派生用户标签（兴趣、消费能力、生命周期）。
2. **社交关系**：计算好友推荐、二度关系、社区发现。
3. **知识图谱**：从多源数据抽取实体-关系-实体三元组。

GraphX（Spark 的图计算库）和 Giraph（基于 MapReduce 的图计算）都是批处理引擎在图场景的应用。PageRank、Connected Components、Shortest Path 等图算法可以用批处理迭代式计算。

#### 应用模式五：跨系统数据同步

批处理可以定期把数据从记录系统同步到派生系统：
1. **数据库 → 搜索引擎**：批处理读数据库 binlog 或全量，构建搜索索引。
2. **数据库 → 缓存**：批处理预计算热点数据，加载到 Redis。
3. **数据库 → 数据仓库**：批处理 ETL 把业务数据同步到数仓供分析。

这种模式与 CDC（Change Data Capture）互补：
- 批处理：全量同步，延迟高但简单可靠。
- CDC：增量同步，延迟低但复杂。

现代架构通常用批处理做初始全量 + CDC 做增量持续同步。

#### 派生数据系统的一致性模型

批处理生成的派生数据是**最终一致**的：
- 批处理有调度延迟（如每天凌晨跑一次）。
- 派生数据反映的是批处理运行时刻的记录系统状态，不是实时状态。

这种最终一致性对很多场景足够：
- 搜索索引：延迟几小时可接受。
- 物化聚合：T+1 报表是标准实践。
- ML 特征：日级刷新足以支持日级模型重训。

对延迟敏感的场景（如实时推荐、风控）需要流处理（见第11章），批处理和流处理通常是互补的（Lambda 架构 / Kappa 架构）。

### 设计权衡

**批处理派生 vs 流处理派生**：
- 批处理：延迟高（分钟~天），但逻辑简单、容错好、可重算。
- 流处理：延迟低（秒级），但复杂（需处理乱序、迟到、状态管理）。
- 选择：根据延迟需求决定。报表用批处理，实时推荐用流处理，混合场景用 Lambda 架构（批 + 流）。

**全量重算 vs 增量更新**：
- 全量重算：简单可靠，但成本高（每次处理全量数据）。
- 增量更新：成本低，但复杂（需处理 upsert、合并、去重）。
- 选择：数据量小用全量，数据量大用增量。数据湖格式（Delta/Iceberg/Hudi）让增量更新更简单。

**批处理 vs 物化视图（数据库原生）**：
- 数据库物化视图：实时刷新，但局限于单库、规模有限。
- 批处理物化视图：批量刷新，可跨多源、规模大。
- 选择：单库小数据用数据库 MV，跨源大数据用批处理。

**同步派生 vs 异步派生**：
- 同步（事务内更新派生数据）：强一致，但耦合高、性能差。
- 异步（批处理定期派生）：最终一致，但解耦、可扩展。
- 选择：强一致需求用同步（如金融交易），分析需求用异步（如数仓）。

### 生产经验与踩坑

1. **ETL 的"凌晨批处理窗口"瓶颈**。传统 ETL 在凌晨 0~6 点跑批，窗口紧张。如果数据量增长，批处理时间超过窗口，会影响白天报表。解决方案：增量 ETL + 数据湖（避免全量重算）、流式 ETL（Flink 替代部分批处理）。

2. **搜索索引的全量重建 vs 增量更新**。Elasticsearch 的索引重建很重，全量重建可能几小时。生产中通常用"双索引切换"：新建索引 v2，构建完成后原子切换别名从 v1 到 v2。批处理负责全量构建，CDC 负责增量更新。

3. **ML 特征的训练-服务偏差**。批处理生成的离线特征和在线服务的实时特征如果不一致，会导致模型效果下降。坑点：离线用 Spark SQL 的 `approx_count_distinct`，在线用 Redis 的 `HyperLogLog`，两者实现不同导致特征值偏差。解决方案：统一特征定义（特征平台），离线/在线用相同计算逻辑。

4. **物化视图的"过期数据"问题**。物化聚合表如果刷新不及时，业务看到的是过期数据。曾发生报表显示昨天的库存，实际已经卖光。解决方案：在物化视图上标注 `last_refresh_time`，业务据此判断数据新鲜度。

5. **跨系统同步的数据丢失**。Sqoop 从数据库同步到 HDFS 时，如果用 `--columns` 漏了某些列，下游数仓就缺数据。生产中要用 schema 演进机制（如 Avro schema 注册表）保证字段完整性。

6. **Lambda 架构的复杂性**。批处理和流处理并行的 Lambda 架构维护两套代码，容易出现结果不一致。现代趋势是 Kappa 架构（纯流处理）或流批一体（Flink / Spark Structured Streaming），但批处理在"全量重算"场景仍有价值（如历史数据回填）。

7. **数据血缘的重要性**。派生数据系统多了之后，"某张表是从哪些源表派生的"成为治理难题。生产中必须建设数据血缘系统（如 Apache Atlas、DataHub），记录每个批处理作业的输入输出关系。

8. **幂等性的设计**。批处理作业可能因为故障重跑，必须保证幂等：相同输入产生相同输出，且重复运行不产生重复数据。用 `INSERT OVERWRITE`（覆盖写）而非 `INSERT INTO`（追加写），或者在作业开头清理当天的输出目录。
