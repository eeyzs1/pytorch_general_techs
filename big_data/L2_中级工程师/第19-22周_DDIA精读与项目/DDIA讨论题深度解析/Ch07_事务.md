## 预备：隔离级别的"现象学 vs 形式化"两条路径

讨论任何隔离级别问题前，必须厘清两条定义路径，否则讨论会陷入语义混乱：

1. **ANSI SQL-92 现象学定义**：用"不允许出现的异常现象"（P1 脏读、P2 不可重复读、P3 幻读）来定义隔离级别。Berenson et al. (SIGMOD 1995) 在 *A Critique of ANSI SQL Isolation Levels* 中已经证明：原始 ANSI 定义存在歧义，且与主流数据库实际实现不符 —— 例如 Oracle 的 "Serializable" 实际只是 Snapshot Isolation，并不防止写偏斜。
2. **Adya 形式化定义**：Adya, Liskov, O'Neil 在 *Generalized Isolation Level Definitions* (2000) 中用"有向序列化图（DSG, Direct Serialization Graph）"和"冲突环（G0/G1）"、"现象（G-SI/P4）"重新定义了 PL-1/PL-2/PL-2.99/PL-3/PL-SI，使得讨论有了形式化基础。

DDIA 第7章采用的"读未提交 / 读已提交 / 可重复读 / 快照隔离 / 可序列化"映射就是基于这条修正后的路径。后续问题中提到的"写偏斜（A5A）"、"幻读（A3）"等编号都来自 Berenson 论文的附录。

### Q1: 大数据场景下为什么"可序列化"隔离级别很少用？Kafka Streams 和 Flink 如何处理"写偏斜"问题？

#### 核心结论

可序列化（SERIALIZABLE）在 OLTP 单机数据库中也只在小规模冲突场景下可行；大数据场景下"很少用"的根本原因是：(1) 分布式串行化需要全局协调（SSI 的 SIREAD lock 跨节点传播或 2PL 跨分区锁），吞吐随分区数线性下降；(2) 大数据负载以 append-only 事件流为主，写偏斜本身罕见；(3) 流处理引擎通过"按 key 单线程化 + 状态后端"在引擎内部天然规避了写偏斜，对外只暴露 exactly-once 的端到端语义，把可序列化问题转化成了"幂等 + 单调"问题。

#### 原理剖析

**1. Berenson 对 ANSI 隔离级别的批判**

Berenson 等人在 1995 年的论文中给出了两组定义：
- **ANSI Phenomena**：P1（脏读）、P2（不可重复读）、P3（幻读）
- **锁等价定义**：用锁的持有/释放时序来表达相同语义

论文的核心结论是：ANSI 现象学定义过弱，"允许"很多未被列出的异常（如 A5A 写偏斜、A5B 读偏斜、A4 游标丢失更新）。例如 Snapshot Isolation 满足"无 P1/P2/P3"，但仍然允许 **写偏斜（A5A）**：

```
T1: 读 x=10, y=10   (谓词: x+y >= 10)
T2: 读 x=10, y=10   (谓词: x+y >= 10)
T1: 写 y = y - 5    (commit, 快照 = 10)
T2: 写 x = x - 5    (commit, 快照 = 10)
结果: x=5, y=5, 谓词被破坏，但 SI 通过了检测
```

写偏斜的本质：两个事务的读写集合没有"写-写冲突"（write-write conflict），但有"读-写冲突"（read-write anti-dependency）。Berenson 把这种现象编号为 A5A，是 SI 与真 SERIALIZABLE 之间的关键鸿沟。

**2. Adya 的形式化：G-SI 现象**

Adya 在 *Generalized Isolation Level Definitions* 中用 DSG 图把写偏斜形式化为 **G-SI 现象**：DSG 中存在一个环，环中至少包含两条 read-write anti-dependency 边。PL-SI（快照隔离）允许 G-SI，而 PL-3（可序列化）不允许。

这个形式化定义让 SSI 的设计有了清晰的优化目标：**检测 DSG 中的"危险结构"（dangerous structure）** —— 即三个事务构成 `rw-rw-rw` 的环，只要阻止这种结构就足够防止绝大多数写偏斜。

**3. Cahill 的 SSI：让快照隔离"安全可序列化"**

Cahill et al. 在 *Serializable Isolation for Snapshot Databases* (SIGMOD 2008) 中提出 SSI（Serializable Snapshot Isolation），核心思想是：
- 在 SI 基础上引入 **SIREAD lock**（predicate lock 的轻量替代）
- 当事务读取满足某谓词的行时，记录该谓词的 SIREAD lock
- 当其他事务提交写操作命中已有 SIREAD lock 时，把对应事务标记为"危险"（
- 通过 abort 一个事务来打断"危险结构"

SSI 的工程价值：在 PostgreSQL 9.1+ 中实现，相比 SI 性能下降约 9-23%（取决于负载冲突率），是当时最有希望"在工程上可用"的真可序列化方案。

但 SSI 的局限：
- **SIREAD lock 的粒度**：粗则假阳性高（误 abort 多），细则元数据开销大
- **分布式场景下的 SIREAD lock 跨节点传播**：每个分区要维护一份全局 SIREAD lock 表，需要分布式锁服务或 Gossip，性能崩溃
- **冲突率敏感**：写偏斜负载下 abort 率指数上升

**4. 为什么大数据场景"很少用"**

- **负载特征**：大数据写入以 append-only 事件为主（Kafka topic、Hive partition、日志文件），天然不存在"读-写"冲突的修改场景
- **分布式协调成本**：跨分区 SERIALIZABLE 要求全局谓词锁，吞吐随节点数下降；2PL 跨节点死锁检测代价极高
- **OLAP 读多写少**：分析负载的写通常是批量 ETL，并发度低，不需要复杂隔离
- **应用层补偿更可行**：大多数业务通过幂等键、版本号、CRDT 等应用层机制实现"准可序列化"，比依赖数据库 SERIALIZABLE 更可控

#### 技术映射

**Kafka Streams 的处理方式：**

Kafka Streams 的核心设计是把"流处理"变成"按 key 分区的单线程状态机"，从而在引擎层规避了写偏斜：

1. **Task 划分**：每个 topic partition 对应一个 Task，Task 内部串行执行，**天然可序列化**
2. **Keyed State**：每个 key 的状态只被一个 Task 修改，不存在跨 key 的并发写偏斜
3. **State Store + Changelog**：RocksDB 作为本地状态，每次变更写 changelog topic；故障恢复时回放 changelog 重建状态，保证 exactly-once
4. **Interactive Queries**：对外暴露查询时使用 `ReadOnlyKeyValueStore`，不会读到"未提交"的中间状态（基于 changelog 的 commit 边界）

但 Kafka Streams 不能完全消除写偏斜 —— 跨 key 的应用层逻辑仍可能产生写偏斜（如"统计全局余额是否超过限额"），此时需要：
- 把相关 key co-partition 到同一 Task
- 或用 `KTable.aggregate` 配合 Kafka 事务保证原子提交

**Flink 的处理方式：**

Flink 的 Keyed State 同样保证"每 key 单线程处理"，但 Flink 的写偏斜问题主要出现在 **Sink 端**：当 Sink 同时写多个外部系统（如 MySQL + Elasticsearch）时，需要两阶段提交保证原子性。

Flink 的 `TwoPhaseCommitSinkFunction` 通过 checkpoint 边界把"事务"切分成微批次，每个微批次内：
- pre-commit 阶段：开启外部事务，写入数据
- commit 阶段：checkpoint 完成后调用 `invoke(transactionId, COMMIT)`
- abort 阶段：故障恢复时回滚未完成事务

这种方式把"分布式事务"问题转化成了"checkpoint 同步 + 外部系统事务"，避免了 SSI 的谓词锁开销。

#### 设计权衡

| 方案 | 可序列化强度 | 性能开销 | 适用场景 |
|------|------------|---------|---------|
| 数据库 SERIALIZABLE (SSI) | 真 SERIALIZABLE | 9-23% 性能损失 | OLTP 高冲突短事务 |
| 流处理 keyed state | 引擎内可序列化 | 几乎无 | 单 key 状态机 |
| 应用层幂等 + 版本号 | 弱（需应用保证） | 低 | 分布式跨系统 |
| 2PC Sink | 端到端原子 | 高（外部事务） | 多 sink 原子写 |

权衡核心：**真 SERIALIZABLE 的代价与负载冲突率成正比**。冲突率高时 SSI 的 abort 率爆炸，冲突率低时 SI 已经足够。大数据场景下冲突率天然低，所以 SI + 应用层补偿 是更经济的选择。

#### 生产经验与踩坑

1. **PostgreSQL SERIALIZABLE 在高并发写时 abort 风暴**：生产中遇到一个 SaaS 计费系统，开启 SERIALIZABLE 后 QPS 从 5000 降到 800，原因是 SIREAD lock 覆盖大范围索引，导致几乎每个事务都被 abort。最终降级到 Repeatable Read + 应用层版本号。

2. **Kafka Streams 跨 stream 的写偏斜**：曾遇到"用户积分扣减"场景，扣减逻辑跨两个 KTable（余额表 + 流水表），未做 co-partition，导致部分扣减丢失。修复方式：用相同的 key 做 repartition，确保两表在同一 Task 内处理。

3. **Flink Sink 的 2PC 失败处理**：MySQL Sink 在 pre-commit 后、commit 前发生 JobManager 故障，导致事务悬挂。MySQL 默认 `wait_timeout` 8 小时，会一直占着行锁。生产配置建议把外部事务超时设为小于 checkpoint interval 的两倍，避免锁悬挂。

4. **流处理中的"读偏斜"**：Flink 的 async I/O 读取外部数据库时，可能读到不同 checkpoint 的快照，导致状态不一致。修复：要么把外部数据同步到 Flink state，要么对 async 查询做版本号对齐。

### Q2: Delta Lake 怎么在 Parquet 文件上实现 ACID？其事务日志（_delta_log）的设计与数据库 WAL 有何异同？乐观并发控制如何处理写入冲突？

#### 核心结论

Delta Lake 通过"Parquet 不可变数据文件 + JSON/Parquet 事务日志（`_delta_log`）+ 乐观并发控制（OCC）+ 原子提交"实现 ACID：每次写入生成新的 Parquet 文件，并在日志中追加一条 `Add/Remove` 记录；提交时通过原子文件创建（或对象存储的 conditional put）保证原子性。事务日志与数据库 WAL 的本质差异在于粒度 —— WAL 是字节级物理变更，Delta Log 是"文件级逻辑变更"的 manifest，重放语义完全不同；OCC 通过"读快照 → 计算 → 提交时检测冲突 → 按 conflict type 决定 abort/retry"实现高并发，对 blind append 这种无冲突场景几乎零开销。

#### 原理剖析

**1. Lakehouse 论文的核心论点**

Armbrust et al. 在 *Lakehouse: A New Generation of Open Platforms* (CIDR 2021) 中提出 Lakehouse 架构：在低成本对象存储（S3/ADLS/GCS）上同时实现数据湖的开放格式（Parquet）和数据仓库的事务能力。论文给出了三个关键设计支柱：

- **Metadata layer**：把传统数据湖"散落的 Parquet 文件"升级为"带版本控制的 manifest"
- **Transactional metadata**：每次写入都生成一个新版本，支持 time travel 和 rollback
- **Open storage format**：底层仍是 Parquet，不依赖专有格式

Delta Lake、Apache Iceberg、Apache Hudi 是这一架构的三个工业实现，差异主要在 metadata 的物理布局（Delta 用 JSON+Parquet 日志，Iceberg 用 manifest tree，Hudi 用 timeline + 行级 update）。

**2. _delta_log 的物理结构**

Delta Lake 的 `_delta_log` 目录结构：

```
_delta_log/
├── 00000000000000000000.json      # 初始 commit
├── 00000000000000000001.json      # 第二次 commit
├── ...
├── 00000000000000000010.checkpoint.parquet  # 每 10 次 commit 一个 checkpoint
├── 00000000000000000010.json
└── ...
```

每个 JSON commit 文件包含一组 **Action**：

| Action 类型 | 含义 |
|------------|------|
| `add` | 新增一个 Parquet 数据文件（含路径、partition 值、size、stats） |
| `remove` | 标记删除一个数据文件（实际文件不立即删除） |
| `metaData` | 表 schema、partition columns、配置 |
| `protocol` | Delta 协议版本（minReaderVersion/minWriterVersion） |
| `commitInfo` | 提交元信息（时间、操作、用户） |
| `txn` | 应用层事务标识（用于幂等） |

**Checkpoint 机制**：每 `delta.checkpointInterval`（默认 10）次 commit 后，把当前所有 active `add` actions 序列化为一个 Parquet 文件。读取时先找最近的 checkpoint，再回放后续 JSON commit，把启动时间从 O(N) 降到 O(log N) + O(M)（M 为 checkpoint 后的 commit 数）。

**3. 原子提交：从 atomic rename 到 conditional put**

Delta Lake 早期依赖文件系统的 **atomic rename** 实现原子提交：一个 writer 创建临时文件 `_delta_log/00000000000000000010.json.tmp`，然后 `rename` 到目标路径。POSIX 文件系统的 rename 是原子的，所以多个 writer 并发提交时只有一个能成功，其他会因为目标已存在而失败。

但 S3 等对象存储早期不支持原子 rename（S3 是 eventual consistency + 覆盖语义）。Delta Lake 在 S3 上的解决方案：
- 使用 **S3 Conditional Put**（`If-None-Match: *`，2020 AWS 推出）保证创建原子性
- 或者依赖 DynamoDB 作为锁服务（旧版 concurrent writer 支持）

这是 Lakehouse 在对象存储上实现 ACID 的关键工程难点之一。

**4. _delta_log vs 数据库 WAL 的异同**

| 维度 | 数据库 WAL | Delta Lake _delta_log |
|------|-----------|----------------------|
| 粒度 | 字节级物理变更（page 修改） | 文件级逻辑变更（add/remove file） |
| 重放语义 | 重新执行物理变更恢复内存状态 | 重新计算"当前 active 文件集合" |
| 提交单位 | 单条 SQL 或事务 | 一次 batch 写入 |
| 并发模型 | 通常 2PL + 单 writer | OCC + 多 writer |
| 持久性单位 | fsync 后即持久 | rename/put 成功后持久 |
| 检查点 | checkpoint page 到磁盘 | checkpoint active set 到 Parquet |
| 历史保留 | 通常循环覆盖 | 默认保留 30 天（time travel） |
| 跨节点协调 | 通过共享缓冲池/Lock manager | 通过原子文件创建 |

核心差异：**WAL 是"如何把变更写到磁盘"，Delta Log 是"当前表包含哪些文件"**。前者是物理层，后者是逻辑层。这意味着 Delta Lake 不能像数据库那样"事务内多轮读改写"，每次 commit 都是一个完整的 batch。

**5. 乐观并发控制（OCC）的实现**

Delta Lake 的 OCC 流程基于 Kung & Robinson 1981 年的经典 OCC 模型，但简化为 file-level：

```
T1 开始: 
  1. 读取当前版本 V0 的 active file set（read set = {f1, f2}）
  2. 计算变更：新增 f3, 删除 f2
  3. 准备 commit: 写 _delta_log/00000000000000000011.json.tmp

T1 提交时:
  4. 检查 V0 之后是否有其他 commit（V1, V2...）
  5. 若无：rename .tmp → .json，提交成功
  6. 若有：检查 read set 是否与 V1..Vn 的 write set 冲突
    - 冲突规则见下表
    - 不冲突：依然 rename 成功
    - 冲突：abort 或 retry
```

Delta Lake 的 **冲突检测规则**（来自 Delta Protocol Spec）：

| 当前操作 | 冲突操作 | 是否冲突 |
|---------|---------|---------|
| Add file（partition P1） | Add file（partition P2） | 不冲突（disjoint partition） |
| Add file（partition P1） | Remove file（partition P1） | 冲突 |
| Remove file f1 | Remove file f1 | 不冲突（idempotent） |
| Remove file f1 | Add file f1（同路径） | 冲突 |
| Update metadata | 任何 metadata 变更 | 冲突 |
| Append（无 read set） | 任何并发写 | 不冲突（blind append） |
| Optimize（重写文件） | Add file to same partition | 冲突 |

关键设计：**blind append（无前置读）永远不会冲突**。这是大数据 ETL 场景的核心优化 —— 大多数 append-only 写入不需要 read-modify-write，可以无锁并发。

**6. Kung & Robinson OCC 模型的对应**

原论文定义 OCC 的三阶段：
- **Read Phase**：事务读取数据并写入本地 workspace
- **Validation Phase**：提交时检查 read set 是否仍有效
- **Write Phase**：把 workspace 写入共享存储

Delta Lake 的对应：
- Read Phase = 读取 active file set + 计算
- Validation Phase = 检查 V0 之后是否有冲突 commit
- Write Phase = rename .tmp 到 .json

差异：经典 OCC 在 read phase 不持有任何锁，validation 是原子的；Delta Lake 的 validation 借助文件系统的原子 rename 实现，无需独立的 Lock Manager。

#### 技术映射

**Delta Lake 的具体写入流程（以 `INSERT INTO` 为例）：**

```python
# 简化的 Delta Lake 写入流程
def write_to_delta(table_path, data):
    # 1. 读取当前版本
    current_version = read_latest_version(table_path)
    log_version = current_version + 1
    
    # 2. 写入数据文件（不可变）
    data_files = write_parquet_files(table_path, data)
    
    # 3. 构造 commit log
    actions = [AddAction(f) for f in data_files]
    log_content = serialize_to_json(actions)
    
    # 4. 乐观提交：先写临时文件
    tmp_path = f"_delta_log/{log_version:020d}.json.tmp"
    write_file(tmp_path, log_content)
    
    # 5. 原子 rename
    try:
        atomic_rename(tmp_path, f"_delta_log/{log_version:020d}.json")
    except FileExistsError:
        # 冲突：重新读取最新版本，检查 read set 冲突
        new_version = read_latest_version(table_path)
        if has_conflict(read_set, commits_between(current_version, new_version)):
            raise ConcurrentModificationException
        else:
            # 不冲突，递增版本号重试
            log_version = new_version + 1
            retry_commit(tmp_path, log_version)
```

**Spark + Delta 的并发场景：**

- **并发 append 不同分区**：完全无冲突，性能等同裸 Parquet
- **并发 append 相同分区**：仍无冲突（都是 add），最终 merge 即可
- **OPTIMIZE + append 同分区**：冲突，OPTIMIZE 会被 abort 重试
- **DELETE + 并发 append**：DELETE 的 read set 包含被删文件，append 不修改这些文件 → 不冲突
- **UPDATE + 并发 UPDATE 同文件**：冲突，后提交方 abort

#### 设计权衡

**OCC vs 2PL 的选择：**

| 维度 | OCC（Delta Lake） | 2PL（传统数据库） |
|------|-------------------|------------------|
| 冲突率低时性能 | 接近无锁 | 有锁开销 |
| 冲突率高时性能 | abort 风暴 | 阻塞等待 |
| 死锁风险 | 无 | 有（需要 deadlock detection） |
| 分布式协调 | 通过原子文件操作 | 需要 Lock Manager |
| 适合负载 | append-heavy, 低冲突 | read-modify-write, 高冲突 |

Delta Lake 选择 OCC 的根本原因：**对象存储没有原生锁服务，且大数据负载以 append 为主**。如果换成 2PL，需要在 S3 之上架设独立的 Lock Manager，成本和延迟都不可接受。

**JSON 日志 vs Parquet 日志：**

- JSON：易调试、易兼容、小 commit 体积小
- Parquet（checkpoint）：体积小、列存读取快、解析快

Delta Lake 同时使用两者：JSON 处理单个 commit，Parquet 做 checkpoint。这是工程上的折中。

#### 生产经验与踩坑

1. **并发 OPTIMIZE 导致的 abort 风暴**：在生产中遇到多个 Spark job 同时对同一表跑 OPTIMIZE，互相 abort，CPU 浪费严重。解决：用外部调度（Airflow）串行化 OPTIMIZE，或用 `ZORDER BY` 减少 OPTIMIZE 频率。

2. **S3 上 atomic rename 失效问题**：早期 Delta 0.5 在 S3 上偶发"两个 writer 都成功 rename"的 bug，原因是 S3 eventual consistency。升级到 Delta 0.8+ 启用 S3 Multi-Region Access Point + conditional put 后稳定。

3. **小文件问题**：OCC 鼓励小批次提交，但会导致大量小 Parquet 文件。生产中配置 `delta.autoOptimize.optimizeWrite=true` 自动合并小文件，但会增加写入延迟。

4. **Checkpoint 失败导致启动慢**：曾遇到 checkpoint Parquet 损坏（S3 部分写入失败），导致 Spark 启动时无法读 checkpoint，回放了几百个 JSON commit，启动时间从 5 秒到 5 分钟。解决：定期 `delta.logRetentionDuration` 配合校验。

5. **跨表事务的缺失**：Delta Lake 不支持跨表 ACID。如果需要"表 A 写入成功才提交表 B"，要在应用层用幂等键 + 两阶段提交。

### Q3: Kafka 事务和数据库事务有什么本质不同？Kafka 事务的"原子多分区写入"能力在实际生产中解决了什么问题？

#### 核心结论

Kafka 事务与数据库事务的本质差异在于"事务的对象"：数据库事务保护的是"对存储数据的 read-modify-write"，而 Kafka 事务保护的是"多分区写入的可见性边界"，不提供事务内的读取一致性。Kafka 事务的 ACID 是"阉割版"：原子性仅限多分区写入、一致性留给应用层、隔离性只有 read_committed/read_uncommitted 两档、持久性在 commit marker 写入前是"未提交但已落盘"的中间态。其"原子多分区写入"能力解决了流处理中最经典的 consume-process-produce 死循环问题（"读取-处理-写入"的端到端 exactly-once），以及多 sink 原子广播问题。

#### 原理剖析

**1. KIP-98 的设计动机**

Kafka 的 KIP-98 "Exactly Once Delivery and Consumer Transactional Semantics" 是事务特性的起点。设计动机来自 Kafka Streams 的需求：

- Streams 任务从 input topic 消费 → 处理 → 写入 output topic + 更新本地 state（state 背后是 changelog topic）
- 如果不做事务，可能出现："output 已写入但 state changelog 未写入" → 故障恢复后重复处理 → output 重复
- 这就是经典的 **consume-process-produce 死循环**：消费者偏移的提交与生产者的输出必须原子

KIP-98 的核心设计：把"消费偏移提交（写入 __consumer_offsets）+ 多分区生产"统一包装成一个 Kafka 事务，由 **Transaction Coordinator** 协调。

**2. Kafka 事务的架构组件**

- **TransactionalId**：应用层提供的事务 ID（如 "order-processor-1"），用于跨 session 持久化 producer 身份，实现 zombie fencing
- **Producer Epoch**：每次 `initTransactions` 时自增，旧 epoch 的 producer 写入会被拒绝
- **Transaction Coordinator**：Broker 端的协调者，状态存在 `__transaction_state` topic
- **Transaction Log**：`__transaction_state`，内部 topic，记录事务状态（Ongoing/PrepareCommit/PrepareAbort/CompleteCommit/CompleteAbort）
- **Transaction Marker**：写到实际数据分区的高水位标记，指示 consumer 该分区哪些消息是 committed/aborted

**3. 事务提交流程（两阶段提交的简化版）**

```
1. Producer 调用 initTransactions():
   - Coordinator 分配/恢复 ProducerId + 自增 Epoch
   - Zombie fencing: 旧 Epoch 的 producer 被 abort

2. Producer 调用 beginTransaction():
   - Coordinator 把事务状态置为 Ongoing

3. Producer 调用 send(record) 写入多个 partition:
   - 数据正常写入 partition（含 ProducerId+Epoch header）
   - Coordinator 记录该 partition 加入事务

4. Producer 调用 sendOffsetsToTransaction() 提交消费偏移:
   - 把 __consumer_offsets 的 partition 加入事务

5. Producer 调用 commitTransaction():
   - 阶段1: Coordinator 写 TransactionLog 标记 PrepareCommit
   - 阶段2: 向所有相关 partition 写 COMMIT marker
   - 阶段3: Coordinator 写 TransactionLog 标记 CompleteCommit

6. Consumer (isolation.level=read_committed) 读取时:
   - 跳过未 commit 的消息
   - 只返回已写 COMMIT marker 的消息
```

这本质上是 **2PC 的简化版**：用 TransactionLog 替代 prepare log，用 partition marker 替代 resource manager 的 commit RPC。但关键区别：**Kafka 的数据在 send 时就已经写入 partition 并持久化**，commit marker 只是"可见性边界"，不参与"是否持久化"的决策。

**4. 与数据库 ACID 的逐项对比**

| ACID | 数据库事务 | Kafka 事务 |
|------|----------|-----------|
| **Atomicity** | 所有变更全做或全不做 | 多分区写入 + 偏移提交的可见性原子 |
| **Consistency** | 约束、外键、触发器保证 | 无应用一致性保证（应用层责任） |
| **Isolation** | 多档（RU/RC/RR/SI/SER） | 仅 read_committed / read_uncommitted |
| **Durability** | commit 后保证持久（fsync WAL） | commit marker 写入后保证可见 |

关键差异：

- **Durability 语义差异**：数据库的 durability 是"commit 成功后数据不会丢"；Kafka 的 durability 是"数据 send 成功后已落盘，但只有 commit marker 写入后才对 read_committed consumer 可见"。**未 commit 的消息同样持久化在 partition 上**，只是对消费者不可见。这意味着 abort 一个 Kafka 事务不会"删除已写入的数据"，只是写一个 ABORT marker 让 consumer 跳过。

- **Read 语义差异**：数据库事务支持事务内可重复读（同一事务内多次查询看到一致结果），Kafka 事务**完全没有事务内读取** —— producer 不读、consumer 读到的只是"已 committed 的消息流"。这把隔离问题大幅简化，但限制了 Kafka 事务的应用场景。

- **Consistency 差异**：数据库的事务保证约束（外键、唯一性），Kafka 不做任何应用层一致性检查。事务提交后数据可能违反业务约束，由应用层负责。

**5. Zombie Fencing 的设计**

Kafka 事务最巧妙的设计是 **Producer Epoch + Zombie Fencing**：

- 场景：Producer P1 发起事务 T1，网络故障后被 Coordinator 认为 P1 已死；新的 Producer P2（同 TransactionalId）启动并继续工作；此时 P1 网络恢复，继续写 T1 的数据
- 危险：P1 写入的"僵尸数据"会被混入 T1
- 解决：每次 `initTransactions` 时 Epoch 自增；Broker 拒绝任何 Epoch 小于当前值的写入请求

这是大数据系统中少见的"严格的 fencing token 设计"，比很多分布式系统更可靠。Spanner 的 Paxos group 也有类似 epoch 机制。

#### 技术映射

**Kafka 事务在生产中解决的核心问题：**

**场景1：Consume-Process-Produce 的 exactly-once**

```
Kafka Source (input-topic) → Flink/Streams 处理 → Kafka Sink (output-topic)
                       ↓ (offset 提交)
                __consumer_offsets
```

不用事务的问题：
- 若先提交 offset 再写 output：output 写入失败 → 重启后从新 offset 开始 → 数据丢失
- 若先写 output 再提交 offset：output 写入成功但 offset 提交失败 → 重启后重新处理 → output 重复

用 Kafka 事务：把"写 output"和"提交 offset"放在同一事务中，原子提交。Streams 和 Flink Kafka Connector 都默认启用此机制。

**场景2：多 sink 原子广播**

```
订单事件 → 处理 → 写 order-events topic
                → 写 audit-log topic
                → 写 alert-events topic
```

三个 topic 必须原子写入，否则审计不一致。Kafka 事务天然支持。

**场景3：与外部 Sink 的端到端 exactly-once**

Kafka 事务本身只覆盖 Kafka 内部。要扩展到外部系统（如 MySQL、HBase），需要：
- Flink 的 `TwoPhaseCommitSinkFunction`（见 Q4）
- Kafka Connector 的 `ExactlyOnceSinkSupport`（Kafka 2.6+）

这本质上是把 Kafka 事务与外部事务做嵌套，由 checkpoint 边界对齐。

**Streams 的配置：**

```properties
# Producer
enable.idempotence=true
transactional.id=order-processor-${task.id}
transaction.timeout.ms=900000  # 必须小于 broker 的 max.transaction.timeout.ms

# Consumer
isolation.level=read_committed
```

#### 设计权衡

**Kafka 事务 vs 数据库事务：**

| 维度 | Kafka 事务 | 数据库事务 |
|------|----------|----------|
| 事务粒度 | 多分区批量 | 单条/多条 SQL |
| 事务时长 | 秒到分钟（受 timeout 限制） | 毫秒到秒 |
| 读取参与 | 否 | 是 |
| 一致性约束 | 无 | 外键/约束 |
| 适用场景 | 流处理端到端 | OLTP |
| 长事务副作用 | 阻塞 log compaction | 锁持有 |

**为什么 Kafka 不实现完整 ACID：**

- **没有 read-modify-write**：Kafka 是 append-only log，无法在事务内"读取并修改"
- **没有约束系统**：增加约束会破坏 Kafka 的简单性
- **没有跨节点锁**：事务内一致性需要 Lock Manager，与 Kafka 的去中心化设计冲突

权衡：**牺牲事务的完整性换取简单性和扩展性**，把一致性责任推给应用层（Streams/Flink）。

#### 生产经验与踩坑

1. **transaction.timeout.ms 配置陷阱**：默认 60 秒，长批次处理（如调用外部 API）容易超时。但调大又会阻塞 log compaction。生产经验：60-300 秒，超过的话拆分事务。

2. **未提交数据占盘问题**：Kafka 事务 abort 的数据**不会从 partition 删除**，只写 ABORT marker。在 read_uncommitted 的 consumer 看来仍然可见。生产中曾因为一个 bug 持续 abort 事务，partition 文件膨胀到 GB 级别。监控 `kafka.server:type=transaction-marker-channel` 指标。

3. **TransactionalId 的设计**：Streams 的 `transactional.id` 默认是 `${application.id}-${taskId}`。重启后 task 重分配会触发 zombie fencing，导致前一阶段的 producer 被 abort。如果 task 频繁迁移，会频繁 abort。建议设置合理的 `task.timeout.ms`。

4. **跨集群事务不可用**：Kafka 事务只在单集群内有效。跨集群 MirrorMaker 不支持事务传播，需要用 Connector 级别的 exactly-once。生产中遇到跨 region 复制时事务语义丢失，最终改用 active/active 模式 + 应用层去重。

5. **read_committed 性能下降**：consumer 启用 read_committed 后，要等事务 commit marker 才能返回数据，延迟增加。长事务会让 consumer 延迟可达数秒。生产监控 `records-lag-max`，超过阈值告警。

6. **与 Schema Registry 的事务一致性**：Schema 注册不是事务的一部分，可能出现"消息已写入但 schema 未注册"或反之。生产中用 schema-first 工作流，强制 CI 阶段注册 schema。

### Q4: Flink 的 Exactly-Once 语义（两阶段提交）与数据库的分布式事务（XA/2PC）有什么关系？为什么 Flink 选择 2PC 而不是 XA？

#### 核心结论

Flink 的 exactly-once 语义本质上是 **2PC 的特化应用**：用 checkpoint barrier 作为 prepare 阶段信号，用 checkpoint 完成作为 commit 阶段信号，把"流处理的状态一致性"问题转化为"两阶段提交"问题。Flink 选择自研的 2PC 而非 XA，是因为 XA 的设计假设（OLTP 跨库事务、长期持有的资源锁、X/Open 协议栈）与流处理的需求（微批次、checkpoint 同步、source 重放）完全错位 —— XA 需要"每个 sink 是 XA-compliant 的 Resource Manager"，而流处理 sink 多样（Kafka/MySQL/ES/HDFS），并非都支持 XA；XA 的 prepare/commit 阻塞调用会破坏流处理的低延迟特性；XA 的 coordinator 故障会导致所有 RM 阻塞，而 Flink 通过 source 重放可以更优雅地恢复。

#### 原理剖析

**1. 2PC 的原始定义（Gray 1978）**

Jim Gray 在 *Notes on Data Base Operating Systems* (1978, 在 RJ2188 报告中) 给出了两阶段提交的经典定义：

- **Phase 1 (Prepare/Voting)**：Coordinator 询问所有 Participant "能否 commit？"，Participant 把变更写入稳定存储并回复 YES/NO
- **Phase 2 (Commit/Decision)**：Coordinator 收到所有 YES 后写 commit log，通知所有 Participant commit；任一 NO 则 abort

Gray 指出 2PC 的核心问题：
- **Blocking**：Coordinator 在 Phase 2 失败时，Participant 处于"不确定状态"，无法自主决定 commit 还是 abort，必须等待 Coordinator 恢复
- **Failure window**：prepare 之后、commit 之前的窗口期内，资源被锁定

Gray 后续（与 Lamport 一起）在 *Consensus on Transaction Commit* 中证明了：任何具有非阻塞原子提交协议的系统等价于解决了共识问题（FaB Paxos、Paxos Commit 等）。这是 2PC 的理论下限。

**2. XA 规范：标准化的 2PC**

XA 是 X/Open DTP 模型定义的分布式事务规范（1991），核心组件：
- **TM (Transaction Manager)**：协调者，如 Atomikos、Narayana
- **RM (Resource Manager)**：参与者，通常是支持 XA 的数据库（MySQL XA、Oracle XA、DB2）
- **XA Protocol**：`xa_start`、`xa_end`、`xa_prepare`、`xa_commit`、`xa_rollback`

XA 的设计目标：让多个独立数据库参与同一分布式事务，ACID 跨库保证。典型场景是银行跨行转账。

XA 的工程缺陷：
- **性能极差**：每个 RM 在 prepare 后持有行锁直到 commit，跨库延迟叠加导致 TPS 下降一个数量级
- **Coordinator 单点**：TM 故障会让所有 RM 处于 in-doubt 状态，需要人工干预
- **资源持有时间长**：典型 OLTP 事务 50ms，XA 事务 500ms+，锁持有时间 10 倍
- **RM 兼容性**：很多系统不支持 XA（Kafka、Elasticsearch、HDFS）

**3. Flink 的 2PC：checkpoint-driven**

Flink 的 `TwoPhaseCommitSinkFunction` 把 2PC 重构为"checkpoint-driven"：

```
1. Checkpoint Barrier 触发:
   - Source 记录当前 offset（持久化到 checkpoint）
   - Barrier 流过 DAG，每个 operator 对齐 barrier 后做 snapshot

2. Sink 收到 Barrier:
   - invoke: beginTransaction()  # 在外部系统开启事务
   - 后续数据继续写入外部系统（在事务内）
   
3. Barrier 到达 Sink, Sink snapshotState:
   - persistTransaction(transaction)  # 把事务句柄持久化到 checkpoint
   - 这相当于 2PC 的 Phase 1 (Prepare)
   
4. JobManager 收到所有 operator 的 ACK:
   - 写 checkpoint 完成标记
   - 通知所有 Sink commitTransaction()
   - 这相当于 2PC 的 Phase 2 (Commit)

5. 故障恢复:
   - 从 checkpoint 恢复 transaction 句柄
   - 对未 commit 的事务调用 rollback
   - 对已 commit 的事务幂等提交（避免悬挂）
```

关键设计点：
- **Checkpoint barrier 替代 prepare RPC**：避免额外网络往返
- **Transaction handle 持久化到 checkpoint**：替代 prepare log
- **Source offset 重放**：替代 rollback（"回滚"= 重新消费）
- **微批次事务**：每个 checkpoint 一个事务，事务时长 = checkpoint interval

**4. Flink 2PC 与经典 2PC 的对应关系**

| 经典 2PC | Flink 实现 |
|---------|----------|
| Coordinator | JobManager + CheckpointCoordinator |
| Participant | Sink operator |
| Prepare RPC | Checkpoint barrier + snapshotState |
| Prepare log | Checkpoint state (在 JobManager/store) |
| Commit RPC | notifyCheckpointComplete callback |
| Abort/Rollback | Source offset 重放 + Sink abort transaction |
| 事务时长 | Checkpoint interval (默认 1-10s) |
| 阻塞风险 | 较低（事务短，超时可配置） |

**5. 为什么 Flink 选择 2PC 而不是 XA**

5 个核心理由：

**(1) XA 需要 RM 兼容性，而流处理 sink 多样**

Flink 的 sink 包括 Kafka、JDBC、Elasticsearch、HDFS、Redis、Cassandra 等。其中只有 JDBC 支持 XA，其他都不支持。要求所有 sink 支持 XA 是不现实的。Flink 自研的 2PC 通过 `TwoPhaseCommitSinkFunction` 抽象，让每个 sink 自己实现 begin/commit/rollback 即可，门槛极低。

**(2) XA 的阻塞特性破坏低延迟**

XA 事务在 prepare 后会持有外部系统的锁（如 MySQL 行锁），直到 commit/abort。如果 checkpoint interval 是 1 分钟，外部锁会持有 1 分钟。Flink 2PC 的事务时长等于 checkpoint interval，且只在 commit 阶段短暂持有锁。

**(3) XA 的 Coordinator 是单点**

XA 的 TM 通常是单机进程（如应用服务器），故障后所有 in-doubt 事务悬挂。Flink 的 JobManager 通过 ZooKeeper/HighAvailability 实现 HA，checkpoint 元数据持久化到 HDFS，避免单点。

**(4) Source 重放天然支持"回滚"**

Flink 的 source 是可重放的（Kafka offset、文件 offset），故障恢复时重新消费即可"回滚"。XA 需要 RM 支持 `xa_rollback`，但流处理的"输入"不是 RM，无法用 XA 协议。Flink 把"重放"作为"回滚"的等价物，巧妙绕开 XA 限制。

**(5) 微批次 vs OLTP 长事务**

Flink 的事务粒度是"每个 checkpoint 一个微批次"，几秒到几分钟。XA 设计为 OLTP 长事务，几十毫秒到几秒。两者的事务时长和吞吐目标完全不同。Flink 2PC 的 batch-commit 模式更适合流处理。

#### 技术映射

**Flink Kafka Producer 的 2PC 实现（简化）：**

```java
public class FlinkKafkaProducer<T> extends TwoPhaseCommitSinkFunction<T, KafkaTransactionState, KafkaTransactionContext> {
    
    @Override
    protected KafkaTransactionState beginTransaction() {
        // 创建 transactional producer，initTransactions()
        Producer producer = new KafkaProducer<>(props);
        producer.initTransactions();
        producer.beginTransaction();
        return new KafkaTransactionState(producer);
    }
    
    @Override
    protected void invoke(KafkaTransactionState txn, T value, Context context) {
        // 在事务内写入数据
        txn.producer.send(record);
    }
    
    @Override
    protected void snapshotState(KafkaTransactionState txn) {
        // Phase 1: prepare（持久化 transaction 句柄到 checkpoint）
        // Kafka 事务的 prepare 在 send 时已发生，此处只需持久化 producer 句柄
        txn.flush();  // 确保数据全部发出
    }
    
    @Override
    protected void notifyCheckpointComplete(long checkpointId) {
        // Phase 2: commit
        txn.producer.commitTransaction();
    }
    
    @Override
    protected void abort(KafkaTransactionState txn) {
        txn.producer.abortTransaction();
    }
}
```

**关键陷阱：recover 后的悬挂事务**

如果 checkpoint 完成但 notifyCheckpointComplete 未执行就故障，恢复后需要"补提交"。Flink 的 `recoverAndCommit` 接口要求事务句柄可序列化、可恢复。Kafka 的事务句柄包含 transactional.id + epoch，可以在新 producer 上恢复。

#### 设计权衡

**Flink 2PC vs XA 的对比表：**

| 维度 | Flink 2PC | XA |
|------|----------|-----|
| Sink 兼容性 | 自定义实现 | 需 XA-compliant |
| Coordinator HA | JobManager HA + HDFS | TM HA（难） |
| 事务时长 | checkpoint interval | OLTP 单事务 |
| 锁持有 | commit 阶段短 | prepare-commit 全程 |
| 回滚机制 | source 重放 | xa_rollback |
| 性能 | 高（微批次） | 低（10x 下降） |
| 适用场景 | 流处理 | OLTP 跨库 |

**何时仍需 XA：**

- 真正的 OLTP 跨库事务（如银行核心系统）：必须用 XA 或 Saga
- 强一致性的微事务：Flink 的 checkpoint interval 难以做到毫秒级
- 已有 XA 基础设施：兼容性考虑

#### 生产经验与踩坑

1. **notifyCheckpointComplete 的延迟**：Flink 的 notifyCheckpointComplete 是异步的，可能延迟到下一个 checkpoint。如果 sink 故障，事务会悬挂。MySQL Sink 配置 `wait_timeout` 必须大于 checkpoint interval × 2，避免事务被强制回滚但 sink 仍以为已提交。

2. **JDBC Sink 的 XA 替代方案**：Flink 的 JDBC Sink 不用 XA，而是用 `union all` 多语句或 idempotent write。生产中用 primary key + upsert 模式，配合 checkpoint 实现 exactly-once。

3. **Sink 不可幂等的坑**：如果 sink 不支持幂等（如打印日志、HTTP POST），即使 2PC 也无法保证 exactly-once。Flink 文档明确要求 sink 必须支持幂等或事务性。

4. **Checkpoint 失败时的"补提交"**：曾遇到 JobManager 故障后恢复，发现 MySQL 中有大量未提交事务。根因：`recoverAndCommit` 实现有 bug，没正确恢复 transaction handle。修复方式：把 transaction handle 完整序列化到 checkpoint state。

5. **大 state 下的 checkpoint 耗时**：state 几十 GB 时，checkpoint 上传到 S3 需要 30 秒+，期间 sink 事务一直 open，外部锁持有时间长。生产优化：增量 checkpoint（RocksDB）、调大 checkpoint interval、用本地 SSD 加速。

### Q5: HBase 的 Check-And-Put 和 INCREMENT 操作提供了有限的事务保证，这在什么场景下够用？什么场景下不够？

#### 核心结论

HBase 的 Check-And-Put (CAS)、INCREMENT、APPEND 提供的是 **单行级原子操作**，源自 Google Bigtable 的 cell-level atomic operations 设计哲学：通过把并发控制下沉到单 RegionServer 的单行锁，实现"无协调的并发安全"。这在计数器、状态机、分布式锁等"单实体操作"场景下足够；但在多行事务、跨表原子更新、复杂隔离级别、二级索引一致性等"多实体协调"场景下完全不够，需要走 Spanner 式的真分布式事务，或者通过行设计（denormalization + co-location）把多实体塞进单行。这一权衡体现了 Bigtable 系"放弃事务换扩展性"的核心设计哲学。

#### 原理剖析

**1. Bigtable 的 cell-level atomic 操作设计**

Google Bigtable 论文（Chang et al., OSDI 2006）第3节明确写道：

> "Bigtable provides a single-row transaction that can be used to perform a series of reads and writes to rows atomically. ... Single-row transactions can be used for atomic read-modify-write sequences on data stored in a single row."

Bigtable 的设计哲学：**单行事务足够覆盖大多数 OLTP 场景**。理由：
- 把相关数据 denormalize 到单行（wide-column 模型）
- 用列族（Column Family）做逻辑分组
- 用 timestamp 做版本控制

HBase 完全继承了这一设计，提供：
- **Put / Get / Delete**：单行级原子（行锁保护）
- **CheckAndPut / CheckAndDelete**：CAS 操作，等价于"if value == expected then put"
- **Increment**：原子自增，等价于"read-modify-write"的原子化
- **Append**：原子追加
- **RowMutations**：单行内多个 Put/Delete 的批量子事务

**2. HBase 单行原子性的实现机制**

HBase 的单行原子性来自三个层面：

**(1) RegionServer 单点协调**

每个 Region 由唯一一个 RegionServer 负责（除故障恢复期）。所有对该 Region 的写入都经过这个 RegionServer，因此可以在 RegionServer 内部用单线程化的 row lock 实现串行化。

**(2) Row Lock**

HBase 的 `RowLock` 是显式锁（虽然新版已弱化为 read-write lock）：
- 写操作获取 row 的 exclusive lock
- 操作完成后释放
- 锁持有期间，其他写操作阻塞

```java
// HBase 客户端 API（旧版）
RowLock lock = table.lockRow(Bytes.toBytes("row1"));
try {
    // 在锁内做多个 Put/Delete
    table.put(new Put(...));
    table.delete(new Delete(...));
} finally {
    table.unlockRow(lock);
}
```

**(3) WAL 保证持久性**

每个写操作在修改 MemStore 前先写 WAL（Write-Ahead Log），RegionServer 故障后回放 WAL 恢复未持久化的数据。WAL 的粒度是"单 Region 一个 WAL"，因此单行操作天然原子。

**3. CheckAndPut 的源码级实现**

CheckAndPut 的语义：

```java
boolean result = table.checkAndPut(
    rowKey,           // 行键
    family,           // 列族
    qualifier,        // 列限定符
    expectedValue,    // 期望值（null 表示"期望不存在"）
    put               // 满足条件时执行的 put
);
```

在 RegionServer 端的执行（HRegion.java 简化）：

```java
public boolean checkAndPut(byte[] row, byte[] family, byte[] qualifier,
                           byte[] expectedValue, Put put) {
    // 1. 获取 row lock
    RowLock rowLock = getRowLock(row);
    try {
        // 2. 读取当前值
        Cell current = get(row, family, qualifier);
        
        // 3. 检查条件
        boolean matches = (expectedValue == null && current == null)
                       || (expectedValue != null 
                           && current != null
                           && Bytes.equals(expectedValue, current.getValue()));
        
        // 4. 条件满足则执行 put（在同一锁内）
        if (matches) {
            doPut(put);  // 写 MemStore + WAL
            return true;
        }
        return false;
    } finally {
        releaseRowLock(rowLock);
    }
}
```

关键点：**check 和 put 在同一 row lock 内完成**，因此是原子的。这等价于"无锁 CAS"在分布式存储上的实现 —— 用 row lock 代替 CPU 的 CAS 指令。

**4. INCREMENT 的原子性**

INCREMENT 操作的语义：原子地把某 cell 的值加 N。源码实现类似 CheckAndPut：

```java
public Result increment(Increment increment) {
    RowLock rowLock = getRowLock(increment.getRow());
    try {
        // 读取当前 long 值
        long currentValue = getLongValue(row, family, qualifier);
        // 加 N
        long newValue = currentValue + increment.getAmount();
        // 写回
        Put put = new Put(row);
        put.addColumn(family, qualifier, Bytes.toBytes(newValue));
        doPut(put);
        return Result.create(put.getFamilyCellMap());
    } finally {
        releaseRowLock(rowLock);
    }
}
```

INCREMENT 是 HBase 中**最常用的原子操作**，用于计数器场景（页面访问量、点赞数、库存）。如果不用 INCREMENT，自己实现"读取 → 加 1 → 写回"，在并发下会丢失更新。

**5. 与 Spanner 的分布式事务对比**

Google Spanner（Paxos et al., OSDI 2012）的对比：

| 维度 | HBase 单行原子 | Spanner 分布式事务 |
|------|---------------|------------------|
| 事务范围 | 单行 | 跨表跨数据中心 |
| 隔离级别 | 单行 serializable | 外部一致性（线性化） |
| 时钟依赖 | 无 | TrueTime（原子钟） |
| 协调机制 | 单 RegionServer | 2PC + Paxos |
| 性能 | 极高（μs 级） | 较低（ms 级） |
| 写延迟 | 同步 | 跨 DC 同步 |
| 适用场景 | 计数器/状态机 | 跨实体一致性 |

Spanner 的设计哲学：**通过 TrueTime 提供全局线性化时钟，用 2PC 跨 group 协调，实现外部一致性**。代价是写延迟 ≥ TrueTime uncertainty（默认 7ms），吞吐受 Paxos quorum 限制。

HBase 的取舍：放弃跨行事务，换取单 RegionServer 内的极高性能。这把"分布式事务问题"推给应用层 —— 如果需要跨行一致性，要么 denormalize，要么用外部协调。

#### 技术映射

**够用的场景：**

**场景1：计数器（页访问量、点赞、库存）**

```java
// 单个 cell 的原子自增
Increment increment = new Increment(Bytes.toBytes("page_view_counter"));
increment.addColumn(Bytes.toBytes("cf"), Bytes.toBytes("homepage"), 1);
table.increment(increment);
```

完全够用：单个 cell 的自增，无并发问题。

**场景2：分布式锁**

```java
// 用 CheckAndPut 实现 lock acquire
Put put = new Put(Bytes.toBytes("lock:resource_1"));
put.addColumn(Bytes.toBytes("cf"), Bytes.toBytes("owner"), Bytes.toBytes("worker-A"));

boolean acquired = table.checkAndPut(
    Bytes.toBytes("lock:resource_1"),
    Bytes.toBytes("cf"),
    Bytes.toBytes("owner"),
    null,  // 期望不存在（锁未持有）
    put
);
```

完全够用：CAS 实现锁的 acquire，加 TTL 实现自动释放。

**场景3：状态机（订单状态转换）**

```java
// 订单状态从 "pending" 转换到 "paid"
Put put = new Put(Bytes.toBytes("order:12345"));
put.addColumn(Bytes.toBytes("cf"), Bytes.toBytes("status"), Bytes.toBytes("paid"));

boolean success = table.checkAndPut(
    Bytes.toBytes("order:12345"),
    Bytes.toBytes("cf"),
    Bytes.toBytes("status"),
    Bytes.toBytes("pending"),
    put
);
```

完全够用：单实体的状态机转换。

**场景4：库存扣减 + 订单创建（部分场景）**

如果库存和订单在同一行（denormalize），可以用 RowMutations：

```java
RowMutations mutations = new RowMutations(Bytes.toBytes("product:SKU_123"));
Mutation decreseStock = new Put(...).addColumn("cf", "stock", stock - 1);
Mutation addOrder = new Put(...).addColumn("cf", "last_order", orderId);
mutations.add(decreseStock);
mutations.add(addOrder);
table.mutateRow(mutations);
```

够用，但设计丑陋（库存和订单强行塞一行）。

**不够用的场景：**

**场景1：多行事务（订单 + 库存在不同行）**

```
T1: 读 stock:SKU_123 = 10
T1: 写 order:12345 status=paid
T1: 写 stock:SKU_123 stock=9
```

HBase 不能保证三个操作原子。可能订单写了但库存没扣。

**场景2：跨表原子更新**

```
订单表插入订单
库存表扣减库存
```

HBase 完全不支持跨表事务。

**场景3：二级索引一致性**

HBase 的二级索引通常用 Coprocessor 维护（写主表时同步写索引表）。如果 Coprocessor 在写主表后、写索引前故障，索引不一致。这是 HBase 二级索引的根本痛点。

**场景4：复杂隔离级别**

HBase 单行原子是"单行 serializable"，但没有"读已提交"或"快照隔离"。如果需要事务内多次读取一致快照，HBase 做不到。

#### 设计权衡

**单行原子 vs 分布式事务的取舍：**

| 维度 | 单行原子（HBase） | 分布式事务（Spanner/TiDB） |
|------|------------------|------------------------|
| 性能 | μs 级 | ms 级 |
| 复杂度 | 低 | 高（需要 2PC/Paxos） |
| 一致性 | 单行 | 跨实体 |
| 扩展性 | 极好（线性扩展） | 受协调限制 |
| 开发门槛 | 低（API 简单） | 高（理解 ACID） |
| 适用场景 | OLTP 简单实体 | 跨实体强一致 |

**应用层的"伪分布式事务"方案：**

1. **Denormalization**：把相关数据塞进单行（如把订单的多个状态字段放一行）
2. **Saga 模式**：把分布式事务拆成一系列本地事务 + 补偿事务
3. **Event sourcing**：写操作变为事件追加，由消费者最终一致地更新多个视图
4. **外部协调器**：用 ZooKeeper/etcd 做协调（性能差，仅用于关键路径）

HBase 的设计哲学：**让 80% 的简单场景变得极其高效，剩下 20% 让应用层解决**。这与 Spanner"全场景强一致"的哲学截然相反。

#### 生产经验与踩坑

1. **CheckAndPut 的性能瓶颈**：高并发 CAS 同一行会导致 row lock 争用，QPS 被锁死。曾遇到一个抢购系统，所有请求 CAS 同一库存行，QPS 卡在 500。解决：把库存拆成多个"slot"行，并发扣减不同 slot。

2. **RegionServer 故障导致的 lock 丢失**：RegionServer 故障后，未释放的 row lock 会丢失（lock 是内存态）。恢复期间可能有"幽灵锁"或"锁丢失"。生产中用 TTL + 客户端重试缓解。

3. **INCREMENT 的 Long 溢出**：8 字节 long 最大约 9.2 × 10^18。生产中遇到计数器溢出，导致负数。修复：业务层做大数处理或定期归零。

4. **二级索引不一致的修复**：Coprocessor 二级索引在故障时可能不一致。生产中定期跑"对账 job"，扫描主表与索引表的差异并修复。最终一致性，不保证实时。

5. **跨表事务的"假事务"陷阱**：有人用客户端代码"先写 A 表再写 B 表，失败时回滚 A 表"。这在网络/进程故障下不可靠（"回滚 A"也可能失败）。HBase 不应该被当作"事务型数据库"使用。

6. **HBase vs TiDB 的选型**：业务需要跨行事务时，宁可选 TiDB/CockroachDB（真分布式 ACID）也不要在 HBase 上模拟。HBase 的强项是"海量稀疏数据的简单读写"，不是事务。

### Q6: MVCC 的"垃圾回收"（Vacuum）在 PostgreSQL 中是一个运维痛点，Delta Lake 的 VACUUM 操作是否也面临类似问题？如何配置？

#### 核心结论

Delta Lake 的 VACUUM 与 PostgreSQL 的 VACUUM 面临**同类问题但不同量级**：两者都是 MVCC 多版本数据的回收机制，但 PostgreSQL 是"tuple 级、持续运行、阻塞敏感"的回收，Delta Lake 是"file 级、按需运行、对查询无阻塞"的回收 —— 后者因粒度粗、对象存储廉价、回收简单，运维负担小一个数量级。但 Delta Lake 仍有自己的痛点：VACUUM 会破坏 time travel 能力（默认 7 天保留期是硬约束）、与并发 OPTIMIZE 冲突、跨表 VACUUM 协调缺失、对象存储的 list 操作慢导致 VACUUM 性能瓶颈。合理配置 `delta.deletedFileRetentionDuration`、`delta.logRetentionDuration`、`delta.enableExpiredLogCleanup` 三个参数是生产运维的关键。HBase 的 TTL + Major Compaction 机制则提供了第三种思路："垃圾回收下沉到 Compaction"，代价是 IO 压力。

#### 原理剖析

**1. PostgreSQL MVCC 的垃圾产生机制**

PostgreSQL 的 MVCC 设计（Hellerstein et al., Theordor et al.）采用"多版本元组"：

- 每次 UPDATE/DELETE 不修改原 tuple，而是插入新 tuple 并标记旧 tuple 为"已死"（dead tuple）
- 每个 tuple 有 `xmin`（创建事务 ID）和 `xmax`（删除事务 ID）
- 事务读取时根据 snapshot 决定可见性
- 死 tuple 在"没有活跃事务还能看到它"之前不能回收

这意味着 PostgreSQL 的 UPDATE 会产生 2 倍的空间占用（旧 tuple + 新 tuple）。在高更新负载下，dead tuple 堆积导致：
- 表膨胀（bloat）
- 查询性能下降（顺序扫描要跳过死 tuple）
- 事务 ID 回卷风险（32-bit XID，约 20 亿事务后回卷）

**2. PostgreSQL VACUUM 的两类**

- **Autovacuum**：后台守护进程，定期触发，参数化配置
- **Manual VACUUM**：`VACUUM`（不锁表，回收空间但不归还 OS）、`VACUUM FULL`（锁表，重建表归还空间）

VACUUM 的工作：
1. 扫描表，识别 dead tuple
2. 标记 dead tuple 的空间为可重用（不归还 OS）
3. 更新 free space map
4. （VACUUM FULL）重建表，物理收缩

PostgreSQL VACUUM 的运维痛点：
- **配置复杂**：`autovacuum_vacuum_threshold`、`autovacuum_vacuum_scale_factor`、`autovacuum_naptime` 等几十个参数
- **触发滞后**：默认 dead tuple 达到 20% 才触发，更新频繁的表会膨胀严重
- **锁竞争**：VACUUM 与查询竞争 I/O，长查询会阻塞 VACUUM
- **XID 回卷风险**：必须定期 VACUUM 防止 XID 回卷导致数据库强制只读
- **VACUUM FULL 阻塞**：归还要锁表，生产环境几乎不可用

**3. Delta Lake 的 VACUUM 机制**

Delta Lake 的"垃圾"产生机制完全不同：

- Delta Lake 的数据是**不可变 Parquet 文件**
- UPDATE/DELETE/MERGE 操作生成新的 Parquet 文件，旧文件标记为 `remove`（在 _delta_log 中）
- 旧文件不会立即物理删除，保留用于 time travel

`VACUUM` 命令的作用：物理删除 `_delta_log` 中已 `remove` 且超过保留期的 Parquet 文件。

```sql
VACUUM my_table RETAIN 168 HOURS;  -- 保留 7 天，删除更老的
```

VACUUM 的工作流程：
1. 读取当前 _delta_log，计算所有 active 文件（被最新版本引用的文件）
2. 列出表目录下所有 Parquet 文件
3. 对比：未被引用且超过保留期的文件 → 删除
4. （可选）dry run 模式预览要删除的文件

**4. Delta Lake VACUUM 与 PostgreSQL VACUUM 的对比**

| 维度 | PostgreSQL VACUUM | Delta Lake VACUUM |
|------|-------------------|-------------------|
| 回收粒度 | tuple（8KB page 内） | file（Parquet 文件，MB-GB） |
| 触发方式 | 自动（autovacuum）+ 手动 | 仅手动（或调度） |
| 运行频率 | 持续运行 | 每周/每月一次 |
| 对查询影响 | 锁竞争 + I/O 竞争 | 几乎无（只删旧文件） |
| 性能瓶颈 | 表扫描 + 索引维护 | 对象存储 list 操作 |
| 失败影响 | XID 回卷、表膨胀 | time travel 失效 |
| 配置复杂度 | 几十个参数 | 3-5 个参数 |
| 跨节点协调 | 单节点（共享缓冲池） | 无（OCC 自然隔离） |

核心差异：**PostgreSQL 的 VACUUM 是"运行时必需"（否则数据库崩溃），Delta Lake 的 VACUUM 是"运维可选"（只是清理空间）**。这是粒度差异带来的运维负担差异。

**5. Delta Lake VACUUM 的特有痛点**

**(1) Time Travel 丧失**

VACUUM 删除的文件不可恢复，对应版本的 time travel 失效。如果保留期设太短，可能误删还在用的版本。生产中遇到过：报表任务依赖 7 天前的快照，VACUUM 后报错。解决：保留期设为业务最长依赖 + buffer。

**(2) 与并发 OPTIMIZE 的冲突**

OPTIMIZE 也会产生 `remove` 旧文件 + `add` 新文件。如果 VACUUM 与 OPTIMIZE 并发，VACUUM 可能删除 OPTIMIZE 还在引用的文件。Delta Lake 通过 OCC 检测，但仍有竞态窗口。

**(3) 对象存储 list 性能**

VACUUM 要列出表目录所有文件。S3/ADLS 的 list 操作是分页的，每页 1000 个 key，表有百万级文件时 list 耗时可达分钟级。这是 VACUUM 的主要瓶颈。

**(4) 跨表 VACUUM 缺失**

Delta Lake 不支持"跨表一致快照"，VACUUM 也是单表操作。如果两个表有时间关联（如表 A 的 t-1 与表 B 的 t-1），VACUUM 不同步可能破坏一致性。

**(5) Dry Run 必要性**

VACUUM 是破坏性操作，建议先 `DRY RUN` 预览要删除的文件。但生产中往往忽略，导致误删。Delta Lake 1.0+ 默认 dry run = true，需要显式 `VACUUM ... RETAIN ...`（不带 DRY RUN）才真正删除。

**6. HBase 的 TTL + Major Compaction 对比**

HBase 的"垃圾回收"机制是另一条路径：

- **TTL**：cell 级别的时间到 live，过期自动标记删除
- **Major Compaction**：把一个 Store 的所有 StoreFile 合并为一个，物理删除标记为 delete 的 cell、过期 TTL 的 cell、超出版本数的 cell
- **Minor Compaction**：合并小文件，不删除标记

HBase Compaction 与 Delta Lake VACUUM 的对比：

| 维度 | HBase Major Compaction | Delta Lake VACUUM |
|------|----------------------|-------------------|
| 回收内容 | cell（标记删除/过期/超版本） | file（不再被引用的 Parquet） |
| 副作用 | 重写数据，IO 密集 | 只删文件，IO 轻 |
| 触发方式 | 自动（默认 7 天周期）或手动 | 手动 |
| 性能影响 | 读写放大严重 | 几乎无 |
| 运维痛点 | Compaction storm、IO 竞争 | list 慢、time travel 丧失 |

HBase 的 Compaction 是真正的"运维痛点"：Major Compaction 期间 IOPS 飙升、查询延迟翻倍，生产中常关闭自动 Major Compaction，改在低峰期手动触发。

#### 技术映射

**Delta Lake 的关键配置参数：**

```sql
-- 1. 数据文件保留期（VACUUM 不删此期内的文件）
ALTER TABLE my_table SET TBLPROPERTIES (
  'delta.deletedFileRetentionDuration' = 'interval 168 hours'  -- 默认 7 天
);

-- 2. 事务日志保留期（影响 time travel 的最长时间）
ALTER TABLE my_table SET TBLPROPERTIES (
  'delta.logRetentionDuration' = 'interval 30 days'  -- 默认 30 天
);

-- 3. 自动清理过期日志
ALTER TABLE my_table SET TBLPROPERTIES (
  'delta.enableExpiredLogCleanup' = 'true'  -- 默认 true
);

-- 4. Checkpoint 间隔（影响启动速度）
ALTER TABLE my_table SET TBLPROPERTIES (
  'delta.checkpointInterval' = '10'  -- 默认 10 次 commit
);

-- 5. VACUUM 执行
VACUUM my_table RETAIN 168 HOURS;  -- 保留 7 天
VACUUM my_table RETAIN 168 HOURS DRY RUN;  -- 预览
```


#### 设计权衡

**VACUUM 频率与 time travel 的取舍：**

| 保留期 | 空间成本 | Time travel 能力 | VACUUM 频率 |
|--------|---------|-----------------|------------|
| 1 天 | 低 | 短 | 频繁 |
| 7 天（默认） | 中 | 中 | 每周 |
| 30 天 | 高 | 长 | 每月 |
| 永不 VACUUM | 极高 | 永久 | 不回收 |

权衡：**保留期 = 业务最长依赖 + 安全 buffer**。常见选择：
- 实时表：1-3 天
- OLAP 表：7 天
- 归档表：30 天或更长

**VACUUM vs OPTIMIZE 的协调：**

VACUUM 删除旧文件，OPTIMIZE 合并小文件。两者有部分重叠目标（节省空间），但操作不同：
- VACUUM：删除不再引用的文件（"垃圾"）
- OPTIMIZE：合并多个小文件为大文件（"整理"）

生产中通常先 OPTIMIZE 再 VACUUM：OPTIMIZE 生成新文件 + 标记旧文件 remove，VACUUM 物理删除被 remove 的旧文件。

**PostgreSQL autovacuum vs Delta 调度 VACUUM：**

PostgreSQL 的 autovacuum 是"被动触发 + 自动运行"，Delta Lake 是"主动调度 + 手动运行"。前者更自动化，但容易失控（如长事务阻塞）；后者更可控，但依赖外部调度（Airflow）。

#### 生产经验与踩坑

1. **误删还在用的文件**：曾遇到 BI 报表依赖 30 天前的快照（time travel `VERSION AS OF 30`），但 VACUUM 默认 7 天，导致报表报错 `FileNotFound`。修复：保留期调到 35 天，并在 BI 工具中固化版本依赖。

2. **S3 list 性能瓶颈**：表有 500 万个 Parquet 文件，VACUUM list 耗时 40 分钟。解决：开启 `spark.delta.vacuum.parallelDelete.enabled`，并行删除；同时定期 OPTIMIZE 减少文件数。

3. **VACUUM 与 OPTIMIZE 死锁**：两个 Spark job 同时跑 OPTIMIZE 和 VACUUM，互相 abort。修复：调度上错开，OPTIMIZE 在凌晨 2 点，VACUUM 在凌晨 4 点。

4. **Checkpoint 损坏导致 VACUUM 失败**：Checkpoint Parquet 部分写入失败，VACUUM 计算不出正确的 active set，拒绝运行。修复：手动修复 checkpoint（用 `_delta_log/_last_checkpoint` 重新生成）。

5. **跨表 VACUUM 不一致**：两表有时间关联，VACUUM 时序不一致导致 A 表 t-1 存在但 B 表 t-1 已删除。修复：跨表 VACUUM 用同一调度任务，串行执行。

6. **PostgreSQL autovacuum 调优血泪**：在 PG 上跑高更新负载，autovacuum 跟不上 dead tuple 增长，表膨胀到 5 倍。调参方向：`autovacuum_vacuum_scale_factor=0.05`（更激进触发）、`autovacuum_naptime=10s`、`maintenance_work_mem=4GB`。Delta Lake 完全没有这类问题。

7. **HBase Compaction Storm**：RegionServer 同时触发多个 Region 的 Major Compaction，IOPS 爆炸。修复：`hbase.regionserver.majorcompaction` 关闭自动，手动在低峰期触发；`hbase.hstore.compaction.max=3` 限制并发数。

## 横向对比：六大组件的事务能力矩阵

为便于横向理解，把本章涉及的六个系统的事务能力做一总表：

| 系统 | 事务粒度 | 隔离级别 | 协调机制 | 持久性单位 | 垃圾回收 |
|------|---------|---------|---------|-----------|---------|
| PostgreSQL | 多行 SQL | RU/RC/RR/SI/SSI(真SER) | 2PL + SSI | WAL fsync | VACUUM (tuple 级) |
| Delta Lake | 文件级 batch | Snapshot Isolation | OCC + atomic rename | 文件持久 | VACUUM (file 级) |
| Kafka | 多分区写入 | read_committed/uncommitted | Transaction Coordinator + 2PC | commit marker | log compaction |
| Flink | checkpoint 微批次 | exactly-once（端到端） | JobManager + 2PC | checkpoint | （无 GC 概念） |
| HBase | 单行 | 单行 serializable | RegionServer row lock | WAL | TTL + Compaction |
| Spanner | 跨 DC 分布式 | 外部一致性 | 2PC + Paxos + TrueTime | Paxos quorum | （无 GC 痛点） |

横向规律：**事务能力越强，性能开销越大；粒度越粗，运维越简单**。大数据系统的共同选择是"弱事务 + 高吞吐 + 应用层补偿"，这与 OLTP 的"强事务 + 低吞吐 + 数据库保证"形成鲜明对比。这正是 DDIA 第7章的核心洞察：**ACID 不是免费的，分布式 ACID 尤其昂贵，工程上的智慧在于识别场景并选择恰当的弱化方案**。

## 章节小结与延伸思考

本章六个问题串起了"事务"在大数据生态中的演化路径：

1. **隔离级别的形式化**（Q1）：从 ANSI 现象学到 Adya 形式化，再到 SSI 工程实现 —— 理论与工程的桥梁
2. **数据湖 ACID**（Q2、Q6）：把数据库的 ACID 搬到对象存储，用 OCC + 文件级日志实现，垃圾回收从 tuple 级简化到 file 级
3. **流处理事务**（Q3、Q4）：Kafka 事务保护多分区可见性，Flink 2PC 保护端到端 exactly-once —— 都是对经典 2PC 的特化
4. **NoSQL 的取舍**（Q5）：HBase 用单行原子换扩展性，Spanner 用 TrueTime 换跨 DC 一致性 —— 设计哲学的两端
