## 1. 问题的起点：并行不是免费的午餐

直觉认为：1 台机器算 100GB 数据要 100 分钟，那 100 台机器并行只要 1 分钟。**这是最大的错觉。**

并行计算引入了三类单机不存在的代价：

1. **通信代价**：数据要跨网络移动（Shuffle），网络带宽是稀缺资源
2. **同步代价**：并行的任务需要同步等待（最慢的任务决定整体速度）
3. **协调代价**：调度器要分配任务、监控进度、处理故障

这三类代价在单机计算中几乎为零，但在分布式计算中可能占据总耗时的 80%+。**理解分布式计算的本质，就是理解这些代价从哪来、如何减少。**

---

## 2. 分布式计算的代价模型

### 2.1 总时间公式

```
总时间 = 计算时间 + 通信时间 + 同步等待时间 + 协调开销

  计算时间    = 数据量 / (单机算力 × 并行度)
  通信时间    = Shuffle 数据量 / 网络带宽
  同步等待    = max(各 Task 耗时) - avg(各 Task 耗时)   ← 数据倾斜的代价
  协调开销    = Task 启动 × Task 数量                    ← 每个Task有固定启动成本
```

### 2.2 为什么增加机器不能线性加速

**Amdahl 定律**：程序的加速比受限于**串行部分**。即使并行部分能无限加速，串行部分（如汇总结果、Shuffle 同步）也会拖住整体。

```
假设任务 90% 可并行，10% 串行:
  1台机器:  100分钟 (90并行 + 10串行)
  10台机器: 19分钟  (9并行 + 10串行)   ← 加速比 5.3x，不是 10x
  100台机器: 11分钟 (1并行 + 10串行)   ← 加速比 9.1x，不是 100x
  ∞台机器:  10分钟  (0并行 + 10串行)   ← 极限就是串行部分
```

**通信开销随机器数增加而增加**：机器越多，Shuffle 时数据跨网络传输的概率越大。100 台机器时，几乎所有 Shuffle 都跨网络；10 台机器时，部分 Shuffle 可能在同机内完成（走内存 Loopback）。

**协调开销随 Task 数增加而增加**：每个 Task 有启动开销（JVM 启动、序列化反序列化、调度延迟）。Task 太多（如百万级小文件），协调开销可能超过计算时间。

**结论**：并行度不是越高越好。存在一个最优并行度，超过它反而变慢。这是矛盾 2 的核心权衡。

## 3. 数据本地性：移动计算比移动数据划算

### 3.1 核心洞察

这是 MapReduce 论文（Google, 2004）最重要的设计原则：

> **把计算任务调度到数据所在的机器上执行，而不是把数据搬到计算节点。**

为什么？因为数据量通常是 GB-TB 级，而计算代码是 KB-MB 级。搬 1TB 数据走网络要几分钟，搬 1MB 代码走网络只要毫秒。

### 3.2 本地性级别

```
NODE_LOCAL  (节点本地):  数据和计算在同一台机器 → 走本地磁盘/内存，最快
RACK_LOCAL  (机架本地):  数据和计算在同一机架   → 走机架内网络，较快
NO_PREF     (无偏好):    数据位置不影响
OFF_SWITCH  (跨机架):    数据和计算在不同机架   → 走核心交换机，最慢
```

**HDFS 的副本放置策略与本地性的配合**：
- HDFS 默认 3 副本：本机架 1 份 + 跨机架 2 份
- 调度器优先选 NODE_LOCAL，其次 RACK_LOCAL，最后才 OFF_SWITCH
- 3 副本意味着同一数据块在 3 个节点都有，调度器有 3 个选择

### 3.3 Spark 的 preferred locations

Spark RDD 的第五大特性就是"优先位置"（preferred locations）——记录每个 Partition 的数据在哪些节点上，调度器据此优先调度。

```python
# HDFS 读取的 RDD，preferred locations = HDFS 块的位置
rdd = sc.textFile("hdfs:///data/large_file.parquet")
print(rdd.preferredLocations(rdd.partitions[0]))
# 输出: ['node1', 'node3', 'node5']  ← HDFS 块的 3 个副本位置
```

**为什么 Spark 比 MapReduce 快（之一）**：Spark 的调度器更智能，会等待一小段时间争取 NODE_LOCAL，而非立即调度到任意节点。这牺牲了一点调度延迟，换取了数据本地性。

**第一性原理挂载**：数据本地性是矛盾 2（并行计算）和矛盾 3（网络代价）的交叉解法。它通过"计算找数据"而非"数据找计算"，把网络传输量从"数据量级"降到"代码量级"。

## 4. Shuffle：最昂贵的操作

### 4.1 什么是 Shuffle

**Shuffle**：当某个操作需要把**相同 Key 的数据汇集到同一节点**时，数据必须跨网络重新分布。

典型触发 Shuffle 的操作：
- `groupByKey`：按 Key 分组
- `reduceByKey`：按 Key 聚合
- `join`：按 Key 关联两表
- `sortBy` / `orderBy`：按 Key 排序
- `distinct`：去重（需要把相同值汇集）

### 4.2 Shuffle 的完整流程

```
Map 端:
  1. Map Task 处理数据，输出 (Key, Value) 对
  2. 按 Key 的 Hash 分区，写入本地磁盘的多个文件（每个 Reduce 分区一个文件）
     ← 必须写盘！不能只在内存，因为数据量可能超内存 + 容错需要

Shuffle 传输:
  3. Reduce Task 从所有 Map Task 的对应文件中拉取属于自己的数据
     ← 跨网络传输！M 个 Map × R 个 Reduce = M×R 个网络连接

Reduce 端:
  4. Reduce Task 接收数据，写入内存缓冲区
  5. 缓冲区满 → 排序 + 溢写磁盘
  6. 所有数据到齐 → 归并排序 → 执行 Reduce 逻辑
```

### 4.3 为什么 Shuffle 贵

| 环节 | 代价 | 说明 |
|------|------|------|
| Map 端写盘 | 磁盘 IO | 数据必须持久化到本地磁盘 |
| 网络传输 | 网络带宽 | 跨节点拉取数据，M×R 连接 |
| Reduce 端排序 | CPU + 内存 + 磁盘 | 归并排序需要排序所有数据 |
| 同步等待 | 时间 | Reduce 必须等所有 Map 完成才能开始 |

**典型比例**：一个 Spark 作业中，Shuffle 通常占总耗时的 **50%-90%**。这就是为什么"所有 Spark 调优的本质都是减少 Shuffle"。

### 4.4 为什么 Shuffle 必须写盘

有人问：能不能 Shuffle 只走内存，不写盘？答案是不能，原因有二：

1. **数据量可能超内存**：Shuffle 的数据量可能是 GB-TB 级，内存放不下。
2. **容错需要**：如果 Reduce Task 失败重试，它需要重新从 Map 端拉取数据。如果 Map 端没写盘，数据已经没了（Map Task 已结束），只能重跑整个 Map Stage。

所以 Shuffle 写盘是**可靠性**和**性能**的权衡——牺牲性能换可靠性。

## 5. 宽依赖 vs 窄依赖：Spark 的核心抽象

### 5.1 定义

```
窄依赖 (Narrow Dependency):
  父 RDD 的每个 Partition → 最多被子 RDD 的一个 Partition 使用
  特点: 不需要 Shuffle，可 Pipeline 流水线执行
  例子: map, filter, flatMap, union

宽依赖 (Wide Dependency / Shuffle Dependency):
  父 RDD 的每个 Partition → 被子 RDD 的多个 Partition 使用
  特点: 需要 Shuffle，是 Stage 的边界
  例子: reduceByKey, groupByKey, join, sortBy
```

### 5.2 为什么窄依赖可以 Pipeline

窄依赖是"一对一"或"多对一"的关系，父 Partition 的数据不需要跨节点移动。所以 Spark 可以把一连串窄依赖操作合并成一个**流水线**（Pipeline），在一个 Task 内顺序执行，不需要中间落盘。

```
rdd.map(f).filter(g).map(h)  ← 三个窄依赖，Pipeline 成一个 Task

执行流程:
  读取一条数据 → map(f) → filter(g) → map(h) → 输出
  （全程在内存中，一条一条流水线处理，不落盘）
```

### 5.3 为什么宽依赖必须等 Shuffle

宽依赖是"多对多"的关系，子 Partition 需要来自所有父 Partition 的数据。这意味着：

1. 所有父 Partition 必须全部计算完成
2. 数据必须跨网络 Shuffle 到正确的子 Partition
3. 只有 Shuffle 完成后，子 Partition 才能开始计算

所以宽依赖是 **Stage 的边界**——DAGScheduler 遇到宽依赖就切一刀，分成两个 Stage。

### 5.4 Stage 划分原理

```
代码:
  rdd.map(f)          # 窄
     .filter(g)       # 窄
     .reduceByKey(h)  # 宽 ← Stage 边界
     .map(i)          # 窄
     .sortBy(j)       # 宽 ← Stage 边界

Stage 划分:
  Stage 0: map(f) → filter(g)     (Pipeline 执行)
     ↓ Shuffle (按 Key Hash 分区)
  Stage 1: reduceByKey(h) → map(i)  (Pipeline 执行)
     ↓ Shuffle (按 Key 排序分区)
  Stage 2: sortBy(j)
```

**第一性原理挂载**：宽窄依赖是矛盾 3（Shuffle 代价）在 Spark 编程模型上的抽象。窄依赖不触发 Shuffle 所以廉价；宽依赖触发 Shuffle 所以昂贵。理解这一点，你就能通过看 DAG 图判断作业的性能瓶颈在哪里——Stage 越多、Shuffle 越多，通常越慢。

## 6. 减少 Shuffle 的工程手段

所有 Spark 调优的本质都是减少 Shuffle。以下是主要手段：

### 6.1 Broadcast Join（广播 Join）

**场景**：大表 JOIN 小表。

**普通 Join（Shuffle Join）**：
```
大表(1TB) ──┐
            ├── Shuffle 按 Key 分区 ──→ 每个分区做 Join
小表(1GB) ──┘

问题: 1TB + 1GB 的数据都要 Shuffle，网络传输 1TB+！
```

**Broadcast Join（无 Shuffle）**：
```
小表(1GB) → 广播到所有 Executor（每个节点一份内存副本）
大表(1TB) → 不动，在每个分区上直接与内存中的小表 Join

结果: 完全没有 Shuffle！代价是每个 Executor 要能放下小表
```

**为什么有效**：把"大表 Shuffle"换成"小表广播"。1GB 小表广播到 100 个节点，总网络传输 100GB；而 Shuffle 1TB 大表，网络传输 1TB。**用 100GB 换 1TB，赚了 10 倍。**

**适用条件**：小表能放进单个 Executor 的内存（通常 < 10GB）。超过则退化成 Shuffle Join。

### 6.2 Combiner / Map 端预聚合

**场景**：`reduceByKey` vs `groupByKey`。

**groupByKey 的灾难**：
```
数据: ("hello", 1), ("hello", 1), ("hello", 1), ... (10亿条)
  → groupByKey: 把所有 "hello" 的值 Shuffle 到一个节点 → [1,1,1,...10亿个]
  → 再求和

问题: Shuffle 传输了 10 亿条数据！网络和内存都被压垮。
```

**reduceByKey 的智慧**：
```
Map 端先预聚合: ("hello", [1,1,1,...]) → ("hello", 10亿)  ← 在本地先加好
  → 只 Shuffle ("hello", 10亿) 一条数据
  → Reduce 端汇总

结果: Shuffle 数据量从 10 亿条降到 1 条！
```

**为什么 reduceByKey 比 groupByKey 好**：reduceByKey 在 Map 端先用相同的 reduce 函数做局部聚合，大幅减少 Shuffle 数据量。groupByKey 不做预聚合，把所有原始数据 Shuffle 到 Reduce 端。

**原则**：能用 `reduceByKey` 就不要用 `groupByKey`。能用 `aggregateByKey` 就不要用 `groupByKey` + `mapValues`。

### 6.3 分区设计：让数据"天然"分布好

**场景**：多次 JOIN 同一 Key。

如果两个 RDD 都按同一 Key 预分区（如 `partitionBy(new HashPartitioner(200))`），且分区数相同，那么 JOIN 时**不需要 Shuffle**——相同 Key 已经在同一分区内。

```python
# 预分区并缓存
users_partitioned = users.partitionBy(200).persist()
orders_partitioned = orders.partitionBy(200).persist()

# 后续多次 JOIN 都不需要 Shuffle
result1 = orders_partitioned.join(users_partitioned)  # 无 Shuffle！
result2 = result1.join(users_partitioned)              # 无 Shuffle！
```

**原理**：Shuffle 的目的是"把相同 Key 汇集到同一分区"。如果数据已经按 Key 分好区了，就不需要 Shuffle。代价是预分区本身需要一次 Shuffle（但只付一次，后续所有 JOIN 都受益）。

## 7. 数据倾斜：Shuffle 的并发症

### 7.1 什么是数据倾斜

**数据倾斜**：Shuffle 后，某个分区/Key 的数据量远大于其他分区，导致某个 Task 运行时间极长，拖慢整个作业。

```
正常情况:
  Task1: 10GB → 10分钟
  Task2: 10GB → 10分钟
  Task3: 10GB → 10分钟
  总时间: 10分钟（并行）

数据倾斜:
  Task1: 1GB  → 1分钟
  Task2: 1GB  → 1分钟
  Task3: 28GB → 28分钟  ← 瓶颈！
  总时间: 28分钟（被最慢的Task拖住）
```

### 7.2 为什么数据倾斜是 Shuffle 问题

数据倾斜只在 Shuffle 时出现——因为 Shuffle 按 Key 分区，如果某个 Key 的数据量特别大（如热门商品 ID、空值），它会被分到同一个分区，造成倾斜。

窄依赖不涉及 Shuffle，所以不会有倾斜问题。

### 7.3 解决方案：加盐

**核心思想**：把大 Key 拆成多个小 Key，分散到不同分区。

```
原始: ("hot_key", 100万条数据) → 全部到一个分区

加盐: ("hot_key_0", 25万)
      ("hot_key_1", 25万)
      ("hot_key_2", 25万)
      ("hot_key_3", 25万)
  → 分散到 4 个分区，每个 25 万条

聚合后再去盐: 4 个分区的结果汇总
```

**适用场景**：明显有少数大 Key 导致倾斜时。代价是增加了 Key 的数量和后续去盐的复杂度。

### 7.4 解决方案：提高并行度

```
原并行度 200:  大 Key 的数据全到一个分区
并行度 1000:   大 Key 的数据可能分散到多个分区（Hash 取模不同）
```

**原理**：提高并行度改变了 Hash 分区的取模数，让原本在同一分区的数据分散到多个分区。代价是其他正常 Key也被分散，可能增加 Task 启动开销。

**适用场景**：轻微倾斜、不想改代码时。效果不如加盐彻底，但最简单。

### 7.5 诊断方法

```
Spark UI → Stages 页面 → 查看 Task 耗时分布
  如果: Task 耗时分布严重不均（某几个 Task 远慢于其他）
  则: 数据倾斜

定位倾斜 Key:
  sampled = rdd.sample(false, 0.1).map(...).countByKey()
  找到 count 远大于其他的 Key
```

## 8. 序列化代价

### 8.1 为什么必须序列化

分布式计算中，数据跨网络传输、跨进程传递、缓存到磁盘，都需要把对象转换成字节流——这就是序列化。

**三个场景必须序列化**：
1. **Shuffle**：数据跨网络传输前序列化，接收后反序列化
2. **缓存**：RDD 缓存到磁盘时序列化
3. **Task 分发**：闭包（closure）从 Driver 发到 Executor 时序列化

### 8.2 Java 序列化 vs Kryo

| 维度 | Java 序列化 | Kryo |
|------|-----------|------|
| 速度 | 慢 | 快 10x |
| 体积 | 大 | 小 3-10x |
| 兼容性 | 所有 Java 对象 | 需注册类 |
| Spark 默认 | 是（兼容性优先） | 否（需手动开启） |

**为什么 Spark 默认用 Java 序列化**：兼容性。Java 序列化能处理任何 Serializable 对象，不需要额外配置。但性能差。

**为什么推荐切换 Kryo**：性能。Kryo 用更紧凑的格式和更快的算法，序列化速度快 10 倍、体积小 3-10 倍。对于 Shuffle 密集的作业，切换 Kryo 能显著提速。

```python
# 开启 Kryo
conf = SparkConf().set("spark.serializer", "org.apache.spark.serializer.KryoSerializer")
conf.set("spark.kryo.registrationRequired", "true")
conf.registerKryoClasses([User.class, Order.class, ...])
```

### 8.3 序列化优化的本质

序列化代价本质上是**矛盾 3（网络代价）的具体表现**。数据要跨网络传输，就必须序列化；序列化越快、体积越小，网络传输越快。所以序列化优化是减少 Shuffle 代价的一个子手段。

## 9. 权衡总结

| 维度 | 选择 | 权衡 |
|------|------|------|
| 并行度 | 高 vs 低 | 高=并行度好但协调开销大；低=协调少但并行度不足 |
| 本地性 | 等待 NODE_LOCAL vs 立即调度 | 等待=少网络传输但增加延迟；立即=快但可能跨网络 |
| Shuffle | 减少vs不可避免 | 减少Shuffle是核心优化手段，但某些操作（如JOIN大表）必须Shuffle |
| 序列化 | Java vs Kryo | Java=兼容但慢；Kryo=快但需注册 |
| 倾斜处理 | 加盐vs提高并行度 | 加盐=彻底但复杂；提高并行度=简单但不彻底 |

**减少 Shuffle 手段对比**：

| 手段 | 原理 | 适用场景 | 代价 |
|------|------|---------|------|
| Broadcast Join | 小表广播，避免 Shuffle | 大表 JOIN 小表 | 内存（放小表） |
| Map 端预聚合 | reduceByKey 本地先聚合 | 聚合类操作 | 无（纯收益） |
| 预分区 | 数据已按 Key 分好区 | 多次 JOIN 同一 Key | 初始 Shuffle 一次 |
| 加盐 | 大 Key 拆小 Key | 数据倾斜 | 后续去盐复杂度 |

- **课时12 MapReduce**：MapReduce 是分布式计算的起点。它的核心设计就是数据本地性（调度到数据所在节点）和 Shuffle（Map→Reduce 必经之路）。理解 MapReduce 的 Shuffle 代价，才能理解 Spark 为什么用内存计算和 DAG 优化它。
- **课时14 RDD 宽窄依赖**：宽窄依赖是矛盾 3 在 Spark 编程模型上的抽象。窄依赖 Pipeline 执行不 Shuffle；宽依赖必须 Shuffle 是 Stage 边界。看 DAG 图判断性能瓶颈是 L1 核心能力。
- **课时15 Spark SQL Catalyst**：Catalyst 优化器的核心目标之一就是减少 Shuffle——谓词下推（先过滤再 Shuffle，减少 Shuffle 数据量）、列裁剪（只 Shuffle 需要的列）、Join 重排（选 Broadcast Join 还是 Shuffle Join）。DataFrame 比 RDD 快，除了 Tungsten 向量化，还因为 Catalyst 能做全局优化。
- **课时16 Spark 调优**：所有调优手段的本质都是减少 Shuffle——Broadcast Join 消除 Shuffle、reduceByKey 预聚合减少 Shuffle 数据量、加盐解决倾斜、调整并行度分散 Shuffle 压力。
- **DDIA Ch10 批处理**：DDIA 对 MapReduce 和分布式批处理有系统讲解。本文是它的课程化精简版。

---

## 11. 一句话总结

> **分布式计算的本质代价是 Shuffle——数据跨网络重新分布，要写盘、传输、排序、同步，通常占作业 80%+ 耗时。所有调优手段的本质都是减少 Shuffle：Broadcast Join 用小表广播消除 Shuffle，reduceByKey 用 Map 端预聚合减少 Shuffle 数据量，预分区让数据"天然"分布好避免重复 Shuffle，加盐解决 Shuffle 导致的数据倾斜。理解了 Shuffle 代价，你就能通过看 DAG 图判断作业瓶颈、通过 Spark UI 的 Task 耗时分布诊断数据倾斜、通过选择正确的算子（reduceByKey 而非 groupByKey）从源头减少代价——这些都是矛盾 2/3 的必然推论，而非经验技巧。**

## 课后思考

1. 为什么 `distinct` 操作比 `dropDuplicates` 慢？它们分别触发几次 Shuffle？（提示：distinct 是全字段去重，dropDuplicates 可以按部分字段去重，但两者 Shuffle 代价相近。关键在于去重逻辑的实现差异）
2. 如果一个 Spark 作业有 5 个 Stage，你能仅通过 Stage 数量判断它慢不慢吗？还需要看什么？（提示：Stage 数多通常意味着 Shuffle 多，但还要看每个 Stage 的数据量、Shuffle 读写量、Task 耗时分布）
