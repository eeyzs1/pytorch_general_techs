# 原理深潜 4：流处理时间语义——为什么实时计算比批处理难一个量级

> **本文定位**：对应第一性原理**矛盾 6（延迟 vs 吞吐）**。课程里课时19（Flink 核心）、课时20（Flink Checkpoint）、课时17（Kafka 作为流源）、DDIA Ch11 都涉及流处理，但散落在各处、停在"是什么"。本文把这些碎片串成一条原理主线，回答一个核心问题：**为什么流处理比批处理难一个量级？为什么需要 Watermark？为什么 Exactly-Once 在流处理中更难？微批和原生流的本质区别是什么？**
>
> **前置阅读**：`大数据第一性原理.md` 第 2 章矛盾 6。

---

## 1. 问题的起点：流处理比批处理难在哪里

批处理的数据是**有限的、已知的、静态的**——你有一堆文件，处理完就结束。流处理的数据是**无限的、持续到达的、可能乱序的**——数据像河水一样流过来，永远不会"结束"。

这个差异带来三个批处理不存在的挑战：

1. **何时算"完"？** 批处理等所有数据到齐才开始；流处理没有"到齐"的概念，必须边到边算。
2. **数据乱序怎么办？** 批处理读文件时数据已落盘，顺序确定；流处理的数据到达顺序≠产生顺序（网络延迟、重试）。
3. **状态如何管理？** 批处理无状态（每次从头算）；流处理有累积状态（窗口聚合、去重、JOIN），状态不能无限增长也不能丢。

**核心洞察**：流处理的全部复杂性，都源于"数据是无限的且可能乱序"这一事实。Watermark、窗口、Checkpoint 都是为了应对这个事实。

## 2. 事件时间 vs 处理时间

### 2.1 两个时间轴

```
事件时间 (Event Time): 数据实际发生的时间
  → 用户点击发生在 12:00:03
  → 订单创建发生在 12:00:05

处理时间 (Processing Time): 数据被系统处理的时间
  → 点击数据 12:00:08 到达 Flink（晚了 5 秒）
  → 订单数据 12:00:06 到达 Flink（晚了 1 秒）
```

### 2.2 为什么两个时间会偏离

**理想世界**：事件产生后立刻被处理，事件时间 ≈ 处理时间。

**现实世界**：数据从产生到被处理，要经过多层传递，每层都有延迟：

```
用户设备 → 网络传输 → 采集层(Kafka) → 计算层(Flink)
  产生       网络延迟    排队延迟         处理延迟
```

延迟来源：
- **网络延迟**：移动网络、跨地域
- **排队延迟**：Kafka 积压、消费组 lag
- **重试延迟**：网络抖动导致重传
- **时钟偏差**：不同设备时钟不同步

**结果**：处理时间可能比事件时间晚几秒到几小时。更糟糕的是，**延迟不均匀**——同一秒产生的两条数据，可能间隔 10 分钟才到达。

### 2.3 用哪个时间？

**用处理时间**：
- 优点：简单，不需要处理乱序
- 缺点：结果不可复现。同一份数据重放两次，结果可能不同（因为处理时间不同）
- 适用场景：监控仪表盘（只关心"现在"的状态）

**用事件时间**：
- 优点：结果正确且可复现。同一份数据重放，结果一致
- 缺点：必须处理乱序（数据可能晚到）
- 适用场景：计费、报表、任何需要准确性的场景

**工程选择**：多数业务场景必须用事件时间。处理时间看似简单，但会导致"12:00-12:01 的窗口统计少了 12:00:03 产生的数据"——因为那条数据 12:01:05 才到。这种错误在计费场景是不可接受的。

## 3. 乱序的本质

### 3.1 乱序不可避免

```
事件时间轴:  12:00:01 → 12:00:02 → 12:00:03 → 12:00:04
到达顺序:    12:00:01 → 12:00:03 → 12:00:02 → 12:00:04
                              ↑ 乱序！12:00:02 比 12:00:03 晚到
```

**为什么不可避免**：
- 数据来自不同设备，网络路径不同
- Kafka 多分区，各分区消费速度不同
- 重试、重放导致旧数据"插队"

### 3.2 不处理乱序的后果

假设用处理时间做 1 分钟窗口：

```
窗口 [12:00, 12:01):
  12:00:01 到达 → 计入窗口 ✓
  12:00:03 到达 → 计入窗口 ✓
  12:01:05 到达（事件时间是 12:00:02）→ 计入 [12:01, 12:02) 窗口 ✗ 错误！
```

**结果**：12:00 窗口的统计数据少了 12:00:02 那条，12:01 窗口多了一条不该有的数据。**两个窗口都错了。**

### 3.3 用事件时间为什么难

用事件时间，数据应该计入事件时间对应的窗口。但问题是：

```
窗口 [12:00, 12:01) 什么时候关闭？
  → 不能在 12:01:00 关闭，因为 12:00:02 的数据可能 12:01:05 才到
  → 那等到什么时候？等 5 秒？10 秒？1 分钟？
  → 等太久 → 实时性差
  → 等太短 → 丢数据
```

这就是**矛盾 6 在流处理中的具体化**：延迟 vs 完整性。等得越久数据越完整但实时性越差；等得越短实时性越好但可能丢数据。**Watermark 就是解决这个矛盾的工程方案。**

## 4. Watermark：用概率换确定性

### 4.1 核心思想

**Watermark**（水位线）是一个时间戳断言：

> **"我已经看到了事件时间 ≤ T 的所有数据（大概率）。可以安全关闭 T 之前的窗口了。"**

形式化定义：`Watermark = 已见最大事件时间 − 允许延迟`

```
当前已见最大事件时间: 12:00:30
允许延迟 (allowed lateness): 5 秒
Watermark = 12:00:30 - 5s = 12:00:25

含义: 事件时间 ≤ 12:00:25 的窗口可以安全关闭
      12:00:25 之后的数据可能还会来，但概率很小
```

### 4.2 为什么这是最优解

**不能无限等**：数据是无限的，永远等"所有数据到齐"意味着窗口永远不关闭，流处理退化成批处理。

**不能不等**：不等就关闭窗口，迟到数据会丢失或错误归窗。

**Watermark 的折中**：用"允许一定延迟"换"窗口能确定性地关闭"。它接受"极少数迟到数据可能被丢"的概率代价，换取实时性。

**关键理解**：Watermark 不是"保证不丢数据"，而是"大概率不丢"。这是工程上可接受的概率保证，而非数学上的绝对保证。

### 4.3 Watermark 设置过小 vs 过大

| 设置 | 效果 | 代价 |
|------|------|------|
| 过小（如 1 秒） | 窗口快速关闭，实时性好 | 大量迟到数据丢失或落入侧输出 |
| 过大（如 1 小时） | 几乎不丢数据 | 窗口迟迟不关闭，实时性丧失 |
| 合适（如 5-30 秒） | 平衡 | 需根据业务延迟分布调优 |

**如何选择**：分析数据延迟分布（P99/P999 延迟），选择覆盖 99%+ 数据的延迟值。金融场景用大 Watermark 保完整性，监控场景用小 Watermark 保实时性。

### 4.4 Watermark 传播：取最小值

多分区（如 Kafka 多 Partition）时，Watermark 取所有分区的**最小值**：

```
Partition 0: Watermark = 12:00:30
Partition 1: Watermark = 12:00:25
Partition 2: Watermark = 12:00:10  ← 最慢的
整体 Watermark = min(...) = 12:00:10

含义: 只有所有分区都过了 12:00:10，才算过了 12:00:10
```

**为什么取最小值**：任何一个分区都可能还有 12:00:10 之前的数据。取最小值保证"所有分区的早期数据都已到齐"。

**问题**：如果某个分区消费慢（如数据倾斜），会拖累整体 Watermark，导致窗口迟迟不关闭。这叫"Watermark 拖累"，是流处理常见的性能问题。

### 4.5 迟到数据的处理

即使设了 Watermark，仍可能有极端迟到数据。处理方式：

1. **丢弃**：默认行为。窗口已关闭，数据丢失。
2. **侧输出（Side Output）**：把迟到数据单独输出到另一个流，后续单独处理。
3. **更新已有结果**：允许迟到数据更新已输出的窗口结果（需要下游支持更新，如 ClickHouse 的 ReplacingMergeTree）。

**第一性原理挂载**：Watermark 是矛盾 6（延迟 vs 完整性）在流处理中的核心解法。它用"概率保证"换"确定性关闭"，是工程上延迟与完整性的最优折中。

## 5. 窗口语义

### 5.1 为什么需要窗口

流数据是无限的，不能对"无限"做聚合（如 SUM、COUNT）。窗口把无限流切成**有限的块**，每块可以独立聚合。

### 5.2 三种窗口

**滚动窗口（Tumbling Window）**：
```
|---窗口1---|---窗口2---|---窗口3---|
12:00-12:01  12:01-12:02  12:02-12:03

特点: 固定大小，不重叠，每条数据只属于一个窗口
适用: 每 1 分钟的 PV/UV 统计
```

**滑动窗口（Sliding Window）**：
```
|--窗口1--|
   |--窗口2--|
      |--窗口3--|
12:00-12:02  12:01-12:03  12:02-12:04

特点: 固定大小，有重叠，每条数据可能属于多个窗口
适用: 最近 5 分钟的滑动平均
```

**会话窗口（Session Window）**：
```
|---会话1---|     |---会话2---|
活动          空闲  活动
   ← gap →

特点: 大小动态，按活动间隔分割，无固定边界
适用: 用户会话分析（用户操作间隔超过 30 分钟算新会话）
```

### 5.3 窗口与 Watermark 的配合

```
窗口 [12:00, 12:01):
  12:00:01 数据到达 → 加入窗口
  12:00:03 数据到达 → 加入窗口
  ...
  Watermark 推进到 12:01:00 → 窗口关闭 → 输出结果
  12:01:05 迟到数据到达（事件时间 12:00:02）→ 丢弃或侧输出
```

**关键**：窗口的关闭不是由"处理时间到了 12:01"决定，而是由"Watermark 推进到 12:01"决定。这就是事件时间语义的核心——用 Watermark 而非处理时间来判断窗口关闭。

## 6. Exactly-Once 为什么在流处理中更难

### 6.1 流处理 EOS 的额外挑战

原理深潜2 讲了 EOS 的一般原理。流处理中，EOS 更难，因为：

1. **流是持续的**：不能像批处理那样"失败了从头重来"——流是无限的
2. **状态是累积的**：窗口聚合、去重、JOIN 的状态会持续增长，不能丢失
3. **输出是持续的**：结果不断输出到下游，不能"回滚已输出的结果"（下游可能已消费）

### 6.2 Flink 的 Checkpoint：Chandy-Lamport 算法

**核心思想**：周期性给整个流处理应用拍"快照"，记录所有算子的状态和输入位置。失败时从最近的快照恢复。

```
Checkpoint 流程:
  1. Checkpoint Coordinator 向 Source 注入 Barrier（屏障）
  2. Barrier 随数据流一起向下游流动
  3. 每个算子收到 Barrier 后:
     a. 暂停处理新数据（或对齐多个输入的 Barrier）
     b. 把当前状态保存到状态后端
     c. 向下游转发 Barrier
  4. 所有算子都完成状态保存 → Checkpoint 成功

恢复流程:
  1. 从最近的 Checkpoint 恢复状态
  2. Source 从 Checkpoint 记录的位移重新消费
  3. 数据重放，状态恢复，继续处理
```

### 6.3 Barrier 对齐

当一个算子有多个输入（如 JOIN 两个流）时，必须做 **Barrier 对齐**：

```
输入A: ... 数据 ... [Barrier N] ... 数据 ...
输入B: ... 数据 ... 数据 ... 数据 ... [Barrier N] ...

对齐过程:
  1. 输入A 先收到 Barrier N → 暂停输入A，缓存后续数据
  2. 输入B 还没收到 Barrier N → 继续处理输入B
  3. 输入B 收到 Barrier N → 保存状态，转发Barrier，恢复输入A

为什么要对齐: 如果不对齐，输入A的Barrier后数据会先被处理，
              导致状态包含了"Barrier之后的数据"，破坏一致性
```

**代价**：Barrier 对齐期间，先到 Barrier 的输入会被缓冲，增加延迟。对于多流 JOIN 场景，Checkpoint 会有额外延迟开销。

### 6.4 端到端 EOS 的三要素

如原理深潜2 所述，流处理 EOS 需要 Source + Checkpoint + Sink 三者配合：

```
Source: 可重放（Kafka 记录位移，失败后重新消费）
  → 保证不丢数据

Checkpoint: 一致性快照（状态 + 位移原子保存）
  → 保证状态一致

Sink: 事务性写入（Checkpoint 成功后才提交下游）
  → 保证不重复
```

**为什么 Sink 最难**：多数下游（如 MySQL、Redis）不支持事务性写入。解决方案：
- **两阶段提交（2PC）**：如 Kafka 事务。先预写，Checkpoint 成功后提交。
- **幂等写入**：如 MySQL 用主键去重。即使重复写，效果等同一次。
- **预写日志**：先写临时表，Checkpoint 后合并到正式表。

**第一性原理挂载**：流处理 EOS 是矛盾 4（容错）在流场景下的极致挑战。Checkpoint 用 Chandy-Lamport 算法解决了"持续流 + 累积状态"的容错问题，Sink 的事务/幂等解决了"持续输出"的不重复问题。代价是巨大的复杂度——Barrier 对齐有延迟、状态后端有存储开销、事务性 Sink 有工程门槛。

## 7. 微批 vs 原生流

### 7.1 两种流处理模型

**微批（Micro-Batch）**：
```
时间轴: |---批1---|---批2---|---批3---|
         处理      处理      处理

机制: 把流数据按时间间隔切成小批次，每批用批处理引擎处理
代表: Spark Structured Streaming（默认 100ms 一批）
延迟: ~100ms - 秒级
```

**原生流（Native Streaming）**：
```
时间轴: 数据→数据→数据→数据→数据→（逐条处理）

机制: 每条数据到达就立即处理
代表: Flink、Kafka Streams
延迟: 毫秒级
```

### 7.2 为什么微批更简单

微批本质上是"频繁的小批处理"，复用了批处理引擎的所有基础设施：
- **无状态管理负担**：每批独立处理，不需要跨批状态管理
- **无 Barrier 对齐**：批与批之间自然分隔，不需要 Checkpoint 对齐
- **容错简单**：某批失败重跑该批即可，不需要复杂快照
- **反压简单**：批处理天然有界，积压时拉长批间隔即可

### 7.3 为什么原生流延迟更低

微批的延迟下限是批间隔（如 100ms）——一批数据必须等批间隔到齐才开始处理。原生流逐条处理，延迟可达毫秒级。

```
微批延迟: 数据到达 → 等批间隔(100ms) → 处理(10ms) → 输出
         总延迟 ≈ 100-200ms

原生流延迟: 数据到达 → 立即处理(5ms) → 输出
           总延迟 ≈ 5-20ms
```

### 7.4 选择依据

| 维度 | 微批 | 原生流 |
|------|------|--------|
| 延迟 | ~100ms-秒级 | 毫秒级 |
| 复杂度 | 低（复用批处理） | 高（状态管理+Checkpoint） |
| 吞吐 | 高（批处理优化） | 中（逐条开销） |
| 状态管理 | 简单 | 复杂（需要状态后端） |
| 容错 | 简单（重跑批次） | 复杂（Checkpoint） |
| 代表 | Spark Structured Streaming | Flink |

**选择原则**：
- 延迟要求 > 1 秒 → 微批足够（简单、稳定、生态好）
- 延迟要求 < 1 秒 → 原生流（Flink）
- 延迟要求 < 100ms → 必须原生流

**趋势**：Spark Structured Streaming 在降低批间隔（已支持连续模式），Flink 在简化 API（SQL 化）。两者在收敛，但底层模型差异仍在。

**第一性原理挂载**：微批 vs 原生流是矛盾 6（延迟 vs 复杂度）的典型权衡。微批用"批间隔"换取简单性和稳定性；原生流用"工程复杂度"换取低延迟。没有对错，只有场景适配。

## 8. 状态管理

### 8.1 为什么流处理必须有状态

批处理是无状态的——每次从头算，不需要记住中间结果。流处理必须有状态，因为：

- **窗口聚合**：需要记住窗口内已积累的部分结果
- **去重**：需要记住已见过的 Key
- **JOIN**：需要记住两侧未匹配的数据
- **Pattern 检测**：需要记住已匹配的部分模式

**状态是流处理的"记忆"**，没有状态，流处理只能做无状态的 map/filter，无法做聚合和关联。

### 8.2 状态的分类

```
托管状态 (Managed State):
  ├── Keyed State: 按 Key 分组的状态（如每个用户的购物车）
  │   ├── ValueState: 单值（如用户最近登录时间）
  │   ├── ListState: 列表（如用户的浏览历史）
  │   ├── MapState: 映射（如商品点击计数）
  │   └── ReducingState: 聚合值（如窗口内 SUM）
  └── Operator State: 算子级状态（如 Kafka 消费位移）
```

### 8.3 状态后端

状态要存在哪里？这是**延迟 vs 容量**的权衡：

| 后端 | 机制 | 延迟 | 容量 | 适用场景 |
|------|------|------|------|---------|
| HeapStateBackend | 内存堆 | 极快 | 受限于内存 | 小状态、测试 |
| RocksDBStateBackend | 本地磁盘+LSM | 较快 | 受限于磁盘 | 大状态、生产 |

**为什么 Flink 选 RocksDB**：RocksDB 是嵌入式 LSM-Tree（见原理深潜1），写快读较慢、支持 TB 级状态。Flink 的状态存在 RocksDB 中，Checkpoint 时把 RocksDB 的 SSTable 增量上传到 HDFS/S3。

**与存储引擎原理的联系**：RocksDB 用 LSM-Tree（矛盾 7 的写优化端）管理状态，因为流处理的状态写入是高频小量写（每次处理一条数据都更新状态），LSM 的追加写特性正合适。

### 8.4 状态 TTL

状态不能无限增长（如去重状态会无限膨胀）。**状态 TTL** 让过期状态自动清理：

```java
// Flink 状态 TTL 配置
StateTtlConfig ttlConfig = StateTtlConfig
    .newBuilder(Time.hours(24))  // 24小时后过期
    .setCleanupType(StateTtlConfig.CleanupType.FULL_CLEANUP)
    .build();
```

**为什么需要 TTL**：无界流的状态会无限增长，最终 OOM。TTL 让"不再需要的状态"（如 24 小时前的去重记录）自动过期，控制状态大小。

## 9. 权衡总结

| 维度 | 选择 | 权衡 |
|------|------|------|
| 时间语义 | 事件时间 vs 处理时间 | 事件时间=正确但需处理乱序；处理时间=简单但不准确 |
| Watermark | 大 vs 小 | 大=完整但延迟高；小=实时但可能丢数据 |
| 窗口 | 滚动/滑动/会话 | 各有适用场景，会话最灵活但最复杂 |
| EOS | At-Least-Once vs Exactly-Once | EOS=不丢不重但复杂；ALO=简单但可能重复 |
| 计算模型 | 微批 vs 原生流 | 微批=简单但延迟高；原生流=低延迟但复杂 |
| 状态后端 | Heap vs RocksDB | Heap=快但小；RocksDB=大但稍慢 |

**时间语义决策树**：
```
业务需要准确性吗?
  → 否: 用处理时间（简单）
  → 是: 用事件时间
       数据乱序严重吗?
         → 否: Watermark 设小（5-10秒）
         → 是: Watermark 设大（30-60秒）+ 侧输出处理极端迟到
```

## 10. 串到课程知识点

- **课时17 Kafka 作为流源**：Kafka 是 Flink 最常用的流源。它的可重放特性（记录位移）是 EOS 的 Source 基础。Kafka 多分区对应 Flink 多并行度，分区数影响 Watermark 传播（取最小值，慢分区拖累）。
- **课时19 Flink 核心**：事件时间、Watermark、窗口是 Flink 的三大核心概念。理解本文的 Watermark 原理，才能正确配置 Flink 作业的时间语义。
- **课时20 Flink Checkpoint**：Chandy-Lamport 算法、Barrier 对齐、状态后端选择。这是矛盾 4（容错）在流处理中的实现。Checkpoint 间隔的权衡：频繁=恢复快但开销大；稀疏=开销小但恢复慢。
- **课时18 Kafka EOS**：Kafka 事务作为 Flink 的 Sink，实现端到端 EOS。两阶段提交：Checkpoint 成功后提交 Kafka 事务。
- **DDIA Ch11 流处理**：DDIA 对流处理有系统讲解。本文是它的课程化精简版，补充了 Flink 的工程实现细节。
- **与原理深潜2 的关系**：原理深潜2 讲了一致性与容错的一般原理（CAP、共识、EOS）；本文是它在流处理场景的深化——Checkpoint 是分布式快照的具体实现，Barrier 对齐是共识协议在数据流上的变体。

## 11. 一句话总结

> **流处理的全部复杂性源于"数据是无限的且可能乱序"。事件时间语义保证了结果正确但引入了乱序问题；Watermark 用"概率保证"换"窗口能确定性地关闭"，是延迟与完整性的最优折中；Checkpoint（Chandy-Lamport）用 Barrier 快照解决了"持续流+累积状态"的容错问题；微批 vs 原生流是延迟与复杂度的典型权衡——微批用批间隔换简单性，原生流用工程复杂度换低延迟。理解了这些，你就能解释为什么 Flink 比 Spark Streaming 延迟低、为什么 Watermark 设不好会丢数据或延迟高、为什么流处理的 EOS 比批处理难得多——这些都是矛盾 6 在流场景下的必然推论。**

## 课后思考

1. 如果你的 Watermark 设为 0（不允许任何延迟），会发生什么？设为 1 小时呢？（提示：0=几乎每条数据都迟到，窗口快速关闭但大量丢失；1小时=窗口1小时后才关闭，实时性丧失）
2. 为什么 Flink 的 Checkpoint 间隔通常设为 1 分钟到 5 分钟，而不是 1 秒？（提示：每次Checkpoint 有 Barrier 对齐开销和状态快照 IO 开销，太频繁会影响吞吐）
3. 用第一性原理 5 步法分析会话窗口：它解决哪个矛盾？做了什么取舍？假设前提是什么？失败模式是什么？（提示：假设前提是"用户活动有明显的间隔模式"；失败模式是间隔设置不当导致会话过多或过少）
4. 为什么 Spark Structured Streaming 的连续模式（Continuous Mode）延迟比微批低，但仍然不如 Flink？（提示：连续模式是"伪原生流"——它减少了批间隔但仍有记录级别的开销；Flink 是真正的逐条处理+异步 Checkpoint）
