## 1. 问题的起点：访问模式决定存储结构

存储引擎的选择，不取决于"数据长什么样"，而取决于**数据怎么被访问**。访问模式分两大类：

| 访问模式 | 特征 | 典型场景 | 偏好的存储结构 |
|---------|------|---------|--------------|
| 事务型（OLTP） | 高频小量读写，按主键点查/范围查，要低延迟 | MySQL 业务库、订单系统 | B+Tree |
| 分析型（OLAP） | 大批量扫描，按列聚合，要高吞吐 | 数仓报表、BI 分析 | 列存 + 向量化 |
| 写密集型 | 海量写入，少量读取 | 日志、IoT、时序 | LSM-Tree |

**为什么没有通吃的结构？** 因为读和写在物理上是矛盾的：

- **要读得快**，数据就得有序、紧凑、有索引——但写入时要维护这个有序结构，就得移动数据、加锁，写就慢。
- **要写得快**，数据就该无序追加（append）——但读时就要在无序数据里翻找，读就慢。

这是一个物理层面的权衡，无法靠工程技巧消除。所有存储引擎都是在"读快"和"写快"之间选一个点。下面三种结构，就是三个不同的选择点。

## 2. B+Tree：读优化的经典

**代表**：MySQL InnoDB、PostgreSQL。

### 2.1 结构与原理

B+Tree 是 B-Tree 家族的变种，一棵平衡多路查找树。数据按主键有序存储在叶子节点，叶子节点间用链表串起来。

```
              [10 | 20 | 30]            ← 内部节点（索引，指引搜索方向）
             /      |      |     \
       [1,3,7] [10,12,15] [20,22] [30,35,40]  ← 叶子节点（存数据，有序+链表）
         ↔        ↔          ↔        ↔
```

**为什么读快**：
- 点查：从根到叶走 O(log N) 次，每次一个磁盘页（16KB），3-4 层就能索引千万级数据——意味着点查只需 3-4 次磁盘 IO。
- 范围查：找到起点叶子后，沿链表顺序扫描，局部性好。

### 2.2 为什么写得慢

B+Tree 要保持有序，每次写入可能触发**页分裂**（一个页满了要拆成两个）和**索引维护**。页分裂要移动数据、更新父节点指针，还要加锁保证并发安全。所以 B+Tree 的写是"原地更新 + 加锁维护"，开销大。

### 2.3 权衡总结

| 维度 | B+Tree |
|------|--------|
| 读 | 极快（点查、范围查都优） |
| 写 | 慢（页分裂+锁） |
| 空间 | 有填充因子浪费（页不满） |
| 适合 | OLTP、事务、强一致点查 |
| 失败模式 | 大量随机写时性能急剧下降；不适合全表扫描分析 |

**第一性原理挂载**：B+Tree 选了矛盾 7 的"读优化"端，代价是写慢。MySQL 适合业务库而不适合数仓分析，根因在此。

### 2.4 数据结构：B+Tree 的节点长什么样

B+Tree 与经典 B-Tree 的关键区别：**数据只存叶子，内部节点只存索引（路由）**。这让内部节点能塞更多 key，树更矮，IO 更少。

```
节点结构（每个节点 = 一个磁盘页，InnoDB 默认 16KB）:

内部节点 (Internal Node):
┌──────────────────────────────────────────┐
│ keys[K-1]    :  10 | 20 | 30             │  ← 用于二分查找路由
│ child_ptrs[K]:  P0| P1| P2| P3           │  ← 指向子节点
│ is_leaf      :  false                    │
└──────────────────────────────────────────┘

叶子节点 (Leaf Node):
┌──────────────────────────────────────────┐
│ keys[K-1]    :  10 | 12 | 15             │  ← 存实际 key
│ values[K-1]  :  v10| v12| v15            │  ← 存实际 value（或行指针）
│ next_leaf    :  ───────────────────►     │  ← 指向下一个叶子（范围查关键）
│ is_leaf      :  true                     │
└──────────────────────────────────────────┘
```

**为什么内部节点不存 value？** 一个 16KB 页，如果存 key+value 可能只能放 100 条；只存 key 可以放 1000+ 条。树每多一层，索引容量 ×1000，3 层就能索引 10 亿条。这是 B+Tree 比 B-Tree 更适合磁盘的根因。

### 2.5 算法：查找、插入、页分裂

#### 查找算法（点查）

```
1. 从根节点开始
2. 在当前节点的 keys 数组里二分查找，定位 key 应该在哪个子区间 child[i]
3. 若是内部节点：读 child[i] 磁盘页，回到步骤 2
4. 若是叶子节点：二分查找 keys，命中则返回 value，未命中则 key 不存在
```

#### 插入算法（含页分裂）

```
1. 查找到目标叶子节点（同查找流程）
2. 把 key-value 插入叶子，保持有序
3. 若叶子已满（keys 数量 ≥ 2t-1，t 为阶数）→ 触发页分裂:
   a. 把叶子从中点拆成两半:左半留原节点，右半建新节点
   b. 把中点 key 复制一份上推到父节点（注意 B+Tree 是"复制"上推，不是"移动"）
   c. 父节点若也满 → 递归分裂，直到根节点
4. 若根节点也分裂 → 新建一个根，树高 +1（这是 B+Tree 长高的唯一方式）
```

**页分裂示意图**（t=3，满节点 5 个 key 时分裂）:

```
分裂前（叶子已满）:            分裂后:
[1,3,7,9,12]                   [1,3,7]   [9,12]
                                 左叶子     右叶子
父节点: [10|20]              父节点: [7|10|20]   ← 7 被复制上推
          |                            |  |
        ...                          ... ...
```

注意：上推的是 **7**（左半最大值），不是 9。B+Tree 分裂时中点 key 会被**复制**到父节点做索引，叶子仍保留完整数据。这跟 B-Tree（中点 key 被移动上推）不同。

### 2.6 Python 实现：B+Tree 原理骨架

这段代码演示 B+Tree 的核心逻辑（查找 + 插入 + 分裂），阶数 t 可调。省略了磁盘持久化（内存模拟页）和并发控制。

```python
from bisect import bisect_left, insort
from dataclasses import dataclass, field
from typing import List, Optional

# B+Tree 阶数:每个节点最多 2t-1 个 key,最少 t-1 个。t=3 即每节点 2~5 个 key。
T = 3

@dataclass
class Node:
    is_leaf: bool = True
    keys: List[int] = field(default_factory=list)
    values: List[object] = field(default_factory=list)   # 叶子用
    children: List['Node'] = field(default_factory=list)  # 内部节点用
    next_leaf: Optional['Node'] = None                    # 叶子链表

class BPlusTree:
    def __init__(self, t: int = T):
        self.t = t
        self.root = Node(is_leaf=True)

    def search(self, key: int):
        """点查:从根到叶二分查找。"""
        node = self.root
        while not node.is_leaf:
            i = bisect_left(node.keys, key)
            # key < node.keys[i] 走 child[i];key >= 走 child[i+1] 处理等于的情况
            if i < len(node.keys) and node.keys[i] == key:
                i += 1
            node = node.children[i]
        i = bisect_left(node.keys, key)
        if i < len(node.keys) and node.keys[i] == key:
            return node.values[i]
        return None

    def insert(self, key: int, value):
        """插入:先处理根节点满的特例,再递归插入。"""
        root = self.root
        if len(root.keys) == 2 * self.t - 1:   # 根满 → 先分裂,树会长高
            new_root = Node(is_leaf=False, children=[root])
            self._split_child(new_root, 0)
            self.root = new_root
        self._insert_non_full(self.root, key, value)

    def _split_child(self, parent: Node, idx: int):
        """分裂 parent.children[idx] 这个满节点。"""
        t = self.t
        full = parent.children[idx]
        new_node = Node(is_leaf=full.is_leaf)

        if full.is_leaf:
            # 叶子分裂:右半搬过去,中点 key 复制上推
            new_node.keys = full.keys[t:]      # [t, 2t-1)
            new_node.values = full.values[t:]
            full.keys = full.keys[:t]          # [0, t)
            full.values = full.values[:t]
            new_node.next_leaf = full.next_leaf
            full.next_leaf = new_node
            up_key = new_node.keys[0]          # 复制上推右半第一个 key
        else:
            # 内部节点分裂:中点 key 移动上推(不保留)
            up_key = full.keys[t - 1]
            new_node.keys = full.keys[t:]      # [t, 2t-1)
            new_node.children = full.children[t:]
            full.keys = full.keys[:t - 1]      # [0, t-1)
            full.children = full.children[:t]

        parent.keys.insert(idx, up_key)
        parent.children.insert(idx + 1, new_node)

    def _insert_non_full(self, node: Node, key: int, value):
        if node.is_leaf:
            i = bisect_left(node.keys, key)
            if i < len(node.keys) and node.keys[i] == key:
                node.values[i] = value          # 覆盖更新
            else:
                node.keys.insert(i, key)
                node.values.insert(i, value)
        else:
            i = bisect_left(node.keys, key)
            if i < len(node.keys) and node.keys[i] == key:
                i += 1
            child = node.children[i]
            if len(child.keys) == 2 * self.t - 1:   # 子节点满 → 先分裂再插
                self._split_child(node, i)
                if key >= node.keys[i]:
                    child = node.children[i + 1]
            self._insert_non_full(child, key, value)

    def range_scan(self, low: int, high: int):
        """范围查:定位起点叶子后,沿 next_leaf 链表扫描。"""
        node = self.root
        while not node.is_leaf:
            i = bisect_left(node.keys, low)
            if i < len(node.keys) and node.keys[i] == low:
                i += 1
            node = node.children[i]
        result = []
        i = bisect_left(node.keys, low)
        while node is not None:
            while i < len(node.keys) and node.keys[i] <= high:
                result.append((node.keys[i], node.values[i]))
                i += 1
            if i < len(node.keys) and node.keys[i] > high:
                break
            node = node.next_leaf
            i = 0
        return result

# ---- 验证 ----
if __name__ == "__main__":
    tree = BPlusTree(t=3)
    for k in [10, 20, 5, 6, 12, 30, 7, 17, 25, 35, 40, 50, 3, 1]:
        tree.insert(k, f"v{k}")
    print("search(12):", tree.search(12))         # v12
    print("range(7,25):", tree.range_scan(7, 25))
    # [(7,'v7'),(10,'v10'),(12,'v12'),(17,'v17'),(20,'v20'),(25,'v25')]
```

运行后能验证：点查 O(log N)、范围查沿叶子链表顺序扫描、插入时自动分裂。

### 2.7 C++ 实现要点：贴近 InnoDB 的工程写法

Python 版本演示算法，真实存储引擎（InnoDB）用 C++ 实现，有几个关键工程细节：

```cpp
#include <vector>
#include <algorithm>
#include <cstdint>

// 一个磁盘页(InnoDB 默认 16KB)。这里用内存数组模拟,真实实现是 mmap 或 read/write 页。
constexpr int PAGE_SIZE = 16384;
constexpr int T = 128;   // 阶数,根据 key 大小和页大小算出:PAGE_SIZE / sizeof(Slot)

// 叶子节点 slot:value 直接存行数据(或指向溢出页)
struct LeafSlot {
    uint64_t key;
    char     value[64];   // 定长 value;变长走溢出页
};

// 内部节点 slot:只存 key + 子页号
struct InternalSlot {
    uint64_t key;
    uint32_t child_page_no;   // 子节点的磁盘页号
};

// 页头:记录页类型、slot 数量、next 页号等
struct PageHeader {
    uint8_t  page_type;       // 1=internal, 2=leaf
    uint16_t slot_count;
    uint32_t next_page_no;    // 叶子链表用
    uint32_t page_no;
};

// B+Tree 页(Pod 结构,直接序列化到磁盘)
struct Page {
    PageHeader header;
    union {
        LeafSlot     leaf_slots[0];
        InternalSlot internal_slots[0];
    };
};

class BPlusTree {
public:
    // 点查:从根页开始,二分定位子页,直到叶子
    LeafSlot* search(uint32_t root_page_no, uint64_t key) {
        Page* node = read_page(root_page_no);
        while (node->header.page_type != 2 /* leaf */) {
            int i = std::upper_bound(
                node->internal_slots,
                node->internal_slots + node->header.slot_count,
                key,
                [](uint64_t k, const InternalSlot& s) { return k < s.key; }
            ) - node->internal_slots;
            node = read_page(node->internal_slots[i].child_page_no);
        }
        // 叶子内二分
        int i = std::lower_bound(
            node->leaf_slots,
            node->leaf_slots + node->header.slot_count,
            key,
            [](const LeafSlot& s, uint64_t k) { return s.key < k; }
        ) - node->leaf_slots;
        return (i < node->header.slot_count && node->leaf_slots[i].key == key)
               ? &node->leaf_slots[i] : nullptr;
    }
private:
    Page* read_page(uint32_t page_no);   // 真实实现:buffer pool 查找,未命中则读磁盘
};
```

**Python 版和 C++ 版的区别，体现的是"算法"和"工程"的落差**：

| 维度 | Python 版（演示算法） | C++ 版（真实引擎） |
|------|---------------------|-------------------|
| 节点存储 | 内存对象，GC 管理 | 磁盘页（16KB），buffer pool 缓存 |
| key 定位 | `bisect` | `std::lower_bound` + 原生指针 |
| 分裂触发 | `len(keys) == 2t-1` | `slot_count * sizeof(Slot) > PAGE_SIZE` |
| 并发 | 无 | 临界区锁 + Latch Crabbing（从根向下加锁） |
| 事务 | 无 | redo log（WAL）+ undo log 保证 ACID |

理解这个落差，你就能明白：**算法层面 B+Tree 不复杂，但 InnoDB 的复杂性全在工程层（buffer pool、锁、WAL、崩溃恢复）**。这也是为什么"自己写个 B+Tree"和"生产级存储引擎"差距巨大。

## 3. LSM-Tree：写优化的工程奇迹

**代表**：HBase、Cassandra、RocksDB、LevelDB。

### 3.1 核心思想：把随机写变成顺序写

磁盘的物理特性是：**顺序写比随机写快 100 倍以上**（机械盘尤其明显，SSD 也有差距）。LSM-Tree 的天才之处在于：**所有写入都不去碰有序结构，而是无脑追加到内存**，把随机写彻底变成顺序写。

### 3.2 结构与工作流

```
写入流程:
  1. 数据写入 MemTable（内存，有序）+ WAL（预写日志，防宕机）
  2. MemTable 满了 → 刷成 SSTable（磁盘上的有序文件），进入 Level 0
  3. 后台 Compaction：把多层 SSTable 合并、去重、整理成更大的有序文件

读取流程:
  1. 查 MemTable（内存）
  2. 查 Level 0 SSTable（多个，可能有重叠）
  3. 查 Level 1, 2, ... N SSTable（每层有序，层间不重叠）
  4. 用布隆过滤器快速跳过不含 Key 的文件
```

```
Level 0:  [SSTable A][SSTable B]   ← 可能有 Key 重叠（同一 Key 多版本）
Level 1:  [.........有序无重叠.........]
Level 2:  [............更大更稀疏............]
```

### 3.3 为什么写得快

写入只是"内存追加 + WAL 顺序写"，完全不碰磁盘上的有序结构。写延迟≈内存写入延迟，极快。这就是 HBase、Kafka 能扛高吞吐写入的根因。

### 3.4 为什么读慢（读放大）

读一个 Key，可能要查 MemTable + 多层 SSTable。即使有布隆过滤器，最坏情况仍要查多层。这叫**读放大**（读一个 Key 实际读了多个文件）。

### 3.5 Compaction：LSM 的命门

Compaction 是 LSM 维持读取性能的关键——不合并的话，SSTable 越积越多，读放大越来越严重。但 Compaction 本身要读多层、写新层，消耗大量 IO 和 CPU，称为**写放大**（写 1 字节数据实际写多次，因为 Compaction 反复重写）。

```
权衡三角（LSM 的三难）:
  读放大  ──┐
            ├── 三者无法同时最小，Compaction 策略就是在三者间调
  写放大  ──┤
            │
  空间放大──┘  （不合并则旧版本占空间）
```

### 3.6 权衡总结

| 维度 | LSM-Tree |
|------|----------|
| 写 | 极快（顺序追加） |
| 读 | 较慢（多层查找+读放大） |
| 适合 | 写密集、日志、时序 |
| 失败模式 | Compaction 跟不上写入时，SSTable 堆积，读延迟飙升（生产事故常见根因）；点查性能弱于 B+Tree |

**第一性原理挂载**：LSM 选了矛盾 7 的"写优化"端，代价是读放大和 Compaction 开销。HBase 适合海量写入的日志/时序，不适合高频点查——这也是为什么 HBase 之上常再套 Redis 做点查缓存。

### 3.7 为什么 HBase 用 LSM 而 MySQL 用 B+Tree

回到第一性原理：HBase 面向"海量数据写入+稀疏宽表"场景（矛盾 1 的分片 + 矛盾 4 的容错），写入吞吐是第一诉求；MySQL 面向"事务点查"场景，读取延迟是第一诉求。两者的访问模式不同，所以选了矛盾 7 的不同端。**这不是谁更先进，而是场景适配。**

### 3.8 数据结构：MemTable 与 SSTable 的真实长相

LSM-Tree 不是一个单一的树结构，而是**多层有序文件 + 内存索引**的组合。核心组件两个：

#### MemTable（内存中的有序结构）

MemTable 是写入的第一站，必须支持**有序插入 + 快速点查**。工程上几乎都用**跳表（SkipList）**，原因：
- 跳表插入是 O(log N) 且**无锁并发友好**（CAS 插入），红黑树并发需要复杂锁。
- 跳表底层有序链表，刷盘时直接顺序遍历写 SSTable，天然适配。

```
跳表结构（多层索引链表，概率性建层）:

Level 3:  head ──────────────────────────► 50 ──────► nil
Level 2:  head ──────► 20 ───────────────► 50 ──────► nil
Level 1:  head ──► 10 ► 20 ──────► 30 ───► 50 ──────► nil
Level 0:  head ──► 10 ► 20 ► 25 ► 30 ► 40 ► 50 ► 60 ► nil   ← 完整有序链表

查找 40: head → (L3)跳到50太大 → 下一层 (L2)到20 → (L1)到30 → (L0)到40 ✓
每层平均跳过一半节点,O(log N)
```

#### SSTable（磁盘上的有序不可变文件）

一个 SSTable 文件由多个 block 组成，从上到下：

```
SSTable 文件布局（RocksDB/LevelDB 格式）:

┌──────────────────────────┐
│ Data Block 0             │  ← key-value 对，按 key 有序，块内可压缩
│  [key1,val1][key2,val2]… │
├──────────────────────────┤
│ Data Block 1             │
│  [key5,val5][key6,val6]… │
├──────────────────────────┤
│ ...                      │
├──────────────────────────┤
│ Meta Block (Bloom Filter)│  ← 布隆过滤器:快速判断某 key "一定不在" 本文件
├──────────────────────────┤
│ Index Block              │  ← 每个 Data Block 的首 key，二分定位用
├──────────────────────────┤
│ Footer                   │  ← 各 block 的偏移量 + 魔数，从文件尾部读
└──────────────────────────┘
```

**为什么从文件尾部读 Footer？** 打开 SSTable 时先读尾部（固定大小），拿到所有 block 偏移，再按需读 Index→Data。避免扫描整个文件。

**布隆过滤器的作用**：查 key 时，先过布隆——若布隆说"不在"，100% 不在，直接跳过该 SSTable，省一次磁盘 IO；若说"可能在"，才去 Index→Data 查。多层 SSTable 查找时，布隆能跳过 90%+ 的无关文件，是把读放大压下来的关键。

### 3.9 算法：写入、查找、Compaction

#### 写入算法

```
1. 把 key-value 写入 WAL（预写日志，顺序追加，保证宕机可恢复）
2. 把 key-value 插入 MemTable（跳表，有序）
3. 返回成功（写延迟 ≈ 顺序写 WAL + 内存插入，极快）

后台异步:
4. MemTable 达到阈值（如 64MB）→ 冻结为 Immutable MemTable
5. 后台线程把 Immutable MemTable 顺序遍历 → 写成 SSTable → 进入 Level 0
6. 后台 Compaction 按策略合并各层 SSTable
```

#### 查找算法（多层归并查找）

```
1. 查 MemTable（内存，最新写入在此）
2. 查 Immutable MemTable（正在刷盘的，也在内存）
3. 查 Level 0 SSTable（多个，key 范围可能重叠，需逐个查，从新到旧）
4. 查 Level 1, 2, ... N（每层内 SSTable key 范围不重叠，二分定位一个即可）
5. 每查一个 SSTable 前，先过布隆过滤器跳过无关文件
6. 同一 key 多版本:取最新版本（序列号最大）。若为删除标记（tombstone）则 key 不存在
```

#### Compaction 两种策略（命门中的命门）

Compaction 决定了 LSM 的读写放大和空间放大，有两种主流策略，**场景适配不同**：

**Size-Tiered（大小分级）** —— Cassandra、ScyllaDB 默认
```
触发: 某层 SSTable 数量达到阈值（如 4 个）→ 合并成一个大 SSTable 放下一层

Level 0:  [A][B][C][D]   ← 4 个相似大小，满了
              ↓ 合并
Level 1:  [......E......] ← 一个 4 倍大的文件

优点: 写放大小（每条数据只在合并时重写一次）
缺点: 空间放大大（旧文件要等合并完才删，峰值空间 ×2）
适合: 写密集（日志、时序）
```

**Leveled（层级合并）** —— RocksDB、LevelDB 默认
```
触发: Level L 的总大小超限 → 把 Level L 的一个 SSTable 合并进 Level L+1

Level 1:  [E1][E2][E3]    ← 总大小超限，选 E2
              ↓ E2 与 Level 2 重叠的文件合并
Level 2:  [F1...][F2...][F3...]   ← E2 拆分进多个，保持 L+1 有序无重叠

优点: 空间放大小（每层有序无重叠，读只需查一个文件）
缺点: 写放大大（一条数据可能被反复重写 log_N 次）
适合: 读密集、空间敏感
```

**放大效应量化**（以 LevelDB 默认 7 层为例）：

| 指标 | Size-Tiered | Leveled |
|------|-------------|---------|
| 写放大 | ~4×（每层合并一次） | ~10-30×（逐层放大） |
| 读放大 | 需查同层多个文件 | 每层最多 1 个文件 |
| 空间放大 | ~2×（峰值） | ~1.1× |

这就是为什么 RocksDB 可调 `max_bytes_for_level_multiplier`——在写放大和空间放大间找平衡点。

### 3.10 Python 实现：简易 LSM（MemTable + SSTable + 多层查找）

这段代码演示 LSM 的核心：跳表 MemTable、SSTable 刷盘、多层归并查找、布隆过滤器。省略 WAL 和真实 Compaction（用简化版）。

```python
import bisect
import hashlib
from dataclasses import dataclass, field

# ---------- 布隆过滤器 ----------
class BloomFilter:
    """简易布隆:多个哈希位图。用于"key 可能在此 SSTable"的快速判定。"""
    def __init__(self, capacity: int = 10000, n_hashes: int = 5):
        self.size = capacity * 10
        self.bits = [False] * self.size
        self.n_hashes = n_hashes

    def _hashes(self, key: str):
        h = hashlib.md5(key.encode()).digest()
        for i in range(self.n_hashes):
            yield int.from_bytes(h, 'little') % self.size

    def add(self, key: str):
        for pos in self._hashes(key):
            self.bits[pos] = True

    def might_contain(self, key: str) -> bool:
        return all(self.bits[pos] for pos in self._hashes(key))

# ---------- MemTable ----------
class MemTable:
    """有序内存表。简化版:用 dict 存,刷盘时排序。真实用跳表保有序+并发。"""
    def __init__(self):
        self._dict = {}

    def put(self, key: str, value: str):
        self._dict[key] = value

    def get(self, key: str):
        return self._dict.get(key)

    def sorted_items(self):
        return sorted(self._dict.items())

    def __len__(self):
        return len(self._dict)

# ---------- SSTable ----------
@dataclass
class SSTable:
    """磁盘上的有序文件。简化:用内存数组模拟,真实是 mmap 的 block 文件。"""
    level: int
    items: list                # [(key, value)] 有序
    bloom: BloomFilter

    @classmethod
    def from_sorted(cls, level: int, items: list):
        bloom = BloomFilter()
        for k, _ in items:
            bloom.add(k)
        return cls(level=level, items=items, bloom=bloom)

    def get(self, key: str):
        if not self.bloom.might_contain(key):
            return None         # 布隆过滤:一定不在
        keys = [k for k, _ in self.items]
        i = bisect.bisect_left(keys, key)
        if i < len(keys) and keys[i] == key:
            return self.items[i][1]
        return None

# ---------- 简易 LSM ----------
class SimpleLSM:
    def __init__(self, memtable_limit: int = 5):
        self.memtable = MemTable()
        self.memtable_limit = memtable_limit
        self.levels = [[]]      # levels[0]=L0 列表,levels[i]=Li 列表

    def put(self, key: str, value: str):
        self.memtable.put(key, value)
        if len(self.memtable) >= self.memtable_limit:
            self._flush()

    def _flush(self):
        """MemTable 满 → 刷成 SSTable 进 L0。"""
        items = self.memtable.sorted_items()
        sst = SSTable.from_sorted(level=0, items=items)
        self.levels[0].append(sst)
        self.memtable = MemTable()
        if len(self.levels[0]) >= 3:
            self._compact_l0_to_l1()

    def _compact_l0_to_l1(self):
        """L0 多个 SSTable(可能重叠) → 合并去重 → L1 一个有序 SSTable。"""
        if len(self.levels) < 2:
            self.levels.append([])
        merged = {}
        for sst in self.levels[0]:      # L0 从旧到新
            for k, v in sst.items:
                merged[k] = v           # 后写覆盖
        items = sorted(merged.items())
        self.levels[0] = []
        self.levels[1].append(SSTable.from_sorted(level=1, items=items))

    def get(self, key: str):
        """多层查找:MemTable → L0(多个,从新到旧) → L1...LN。"""
        if (v := self.memtable.get(key)) is not None:
            return v
        for level_ssts in self.levels:
            for sst in reversed(level_ssts):   # 从新到旧
                if (v := sst.get(key)) is not None:
                    return v
        return None

# ---- 验证 ----
if __name__ == "__main__":
    lsm = SimpleLSM(memtable_limit=3)
    for i in range(10):
        lsm.put(f"k{i:02d}", f"v{i}")
    print("get(k05):", lsm.get("k05"))   # v5
    print("get(k99):", lsm.get("k99"))   # None
    print("L0 文件数:", len(lsm.levels[0]), "L1 文件数:", len(lsm.levels[1]))
```

运行后能看到：写入先进 MemTable，满了刷成 L0 SSTable，L0 攒够 3 个触发 Compaction 合并到 L1。查找时多层归并 + 布隆过滤跳过。

### 3.11 C++ 实现要点：贴近 RocksDB 的工程写法

```cpp
#include <string>
#include <vector>
#include <map>
#include <fstream>
#include <cstdint>
#include <algorithm>

// SSTable 的单个 entry(key-value pair,带序列号做 MVCC)
struct KVEntry {
    std::string key;
    std::string value;
    uint64_t    seq;        // 序列号:同 key 多版本取 seq 最大
    uint8_t     type;       // 0=Put, 1=Delete(tombstone)
};

// MemTable:RocksDB 用跳表(SkipList),这里用 std::map 演示有序性
class MemTable {
    std::map<std::string, KVEntry> entries_;   // 真实:并发安全的 SkipList
public:
    void Put(const std::string& key, const std::string& value, uint64_t seq) {
        entries_[key] = {key, value, seq, 0};
    }
    void Delete(const std::string& key, uint64_t seq) {
        entries_[key] = {key, "", seq, 1};      // 墓碑标记
    }
    bool Get(const std::string& key, KVEntry* out) {
        auto it = entries_.find(key);
        if (it == entries_.end()) return false;
        *out = it->second;
        return true;
    }
    // 刷盘:顺序遍历写 SSTable 文件
    void FlushToFile(const std::string& path) {
        std::ofstream f(path, std::ios::binary);
        for (auto& [_, e] : entries_) {          // map 天然有序
            uint32_t klen = e.key.size(), vlen = e.value.size();
            f.write((char*)&klen, 4); f.write(e.key.data(), klen);
            f.write((char*)&vlen, 4); f.write(e.value.data(), vlen);
            f.write((char*)&e.seq, 8); f.write((char*)&e.type, 1);
        }
    }
};

// SSTable 读取:用布隆过滤器 + 稀疏索引加速点查
class SSTableReader {
    std::vector<KVEntry> entries_;              // 简化:全加载。真实:按 block mmap 按需读
    std::vector<std::string> index_keys_;        // 稀疏索引:每 block 首 key
public:
    bool Get(const std::string& key, KVEntry* out) {
        auto eit = std::lower_bound(entries_.begin(), entries_.end(), key,
            [](const KVEntry& e, const std::string& k){ return e.key < k; });
        if (eit != entries_.end() && eit->key == key) {
            *out = *eit;
            return true;
        }
        return false;
    }
};
```

**LSM 工程化的关键复杂点**（Python 简化版都没体现）：

| 维度 | Python 演示版 | RocksDB 真实实现 |
|------|--------------|-----------------|
| MemTable | `dict` + 排序 | 无锁跳表，并发 CAS 插入 |
| WAL | 无 | 顺序写 log，group commit 批量刷盘 |
| 布隆过滤器 | 全内存位图 | 分 block 布隆，可持久化到 SSTable |
| Compaction | 同步阻塞 | 后台多线程，rate limit 限速避免影响前台 IO |
| 删除 | 直接删 | 写 tombstone（墓碑），等 Compaction 才真删 |
| 并发 | 无 | MemTable 无锁读 + SSTable 不可变（天然读无锁） |

**删除为什么是写墓碑而不是直接删？** 因为 SSTable 不可变，无法原地删除。写一个 `type=Delete` 的 entry，查找时遇到墓碑就返回"不存在"，等 Compaction 合并时才物理丢弃。这就是 LSM 删除有延迟的根因。

## 4. 列式存储：分析查询的加速器

**代表**：Parquet、ORC（文件格式）；ClickHouse、Doris、Druid（存储引擎）。

### 4.1 核心思想：按列而非按行存储

行存（B+Tree/LSM 存的是整行）：一条记录的字段连续存储。
列存：同一列的所有值连续存储，不同列分开放。

```
行存（适合取整行）:            列存（适合按列聚合）:
  行1: [id=1, name=张三, age=20, city=北京]
  行2: [id=2, name=李四, age=25, city=上海]    id列:   [1,2,3,4]
  行3: [id=3, name=王五, age=30, city=广州]    name列: [张三,李四,王五,赵六]
  行4: [id=4, name=赵六, age=28, city=深圳]    age列:  [20,25,30,28]
                                              city列: [北京,上海,广州,深圳]
```

### 4.2 为什么分析查询快——三个层次的加速

**第一层：减少 IO（只读需要的列）**
分析查询通常只涉及少数列。如 `SELECT city, AVG(age) FROM users GROUP BY city` 只需 city 和 age 两列。行存要把整行读出来再丢弃无用列；列存只读这两列，IO 量可能减少 90%+。

**第二层：列内压缩率极高**
同一列的数据类型相同（都是整数、都是字符串），编码后压缩率远高于行存混合数据。例如 age 列全是小整数，可用 delta 编码压到极致。**压缩不仅省空间，更减少了磁盘 IO——读的字节少了，查询就快了。**

**第三层：向量化执行（关键！）**
列存天然适配向量化：一次取出一列的一批值（如 1024 个 age），用一个紧凑循环批量处理，利用 CPU 的三个特性：
- **CPU 缓存友好**：连续内存，缓存命中率高
- **SIMD 指令**：一条指令同时处理多个数据（如一次算 8 个整数的和）
- **无分支预测失败**：紧凑循环没有 if/else 分支，CPU 流水线不断

这就是 ClickHouse 单表查询快到极致的根因——列存 + 向量化 + 压缩，三位一体把分析查询的每个环节都压榨到极限。

### 4.3 为什么更新/删除慢

列存按列分文件，更新一行意味着要改多个列文件、重写整个列块。所以列存几乎不支持高效的单行更新。ClickHouse 用 `ReplacingMergeTree` 异步合并去重来"模拟"更新，代价是更新有延迟、且查询时需注意合并语义。

### 4.4 权衡总结

| 维度 | 列存 |
|------|------|
| 分析查询 | 极快（少 IO + 高压缩 + 向量化） |
| 点查/更新 | 很慢 |
| 适合 | OLAP、数仓、BI |
| 失败模式 | 点查、频繁更新场景性能差；小文件多时压缩优势丧失 |

**第一性原理挂载**：列存选了矛盾 7 的"分析优化"端。Hive 数仓用 Parquet/ORC 列存、ClickHouse 用列存+向量化，都是为了分析查询的吞吐；代价是放弃了事务型点查能力。

### 4.5 数据结构：列存文件长什么样（Parquet/ORC 格式）

列存不是简单"把列分开存"，而是有层级组织，兼顾 IO 效率和压缩：

```
Parquet 文件层级结构:

File
├── Row Group 0          ← 水平切分,每个 RG 约 128MB(并行扫描单位)
│   ├── Column Chunk (id)     ← 垂直切分,每列一个 chunk(列存核心)
│   │   ├── Page 0            ← 页,压缩+编码的基本单位(~1MB)
│   │   │   [1,2,3,4,5...]    ← 该页的列数据(已编码压缩)
│   │   ├── Page 1
│   │   └── Page statistics   ← min/max/null_count(谓词下推跳过页)
│   ├── Column Chunk (name)
│   ├── Column Chunk (age)
│   └── Column Chunk (city)
├── Row Group 1
│   └── ...
└── Footer               ← schema + 所有 chunk 偏移 + row group 元数据
```

**三层切分各自解决什么问题**：

| 层级 | 大小 | 作用 |
|------|------|------|
| Row Group | ~128MB | 水平并行单位，Spark/Trino 一个 task 读一个 RG |
| Column Chunk | = RG × 列宽 | 垂直切分，只读查询涉及的列，跳过无关列 |
| Page | ~1MB | 压缩+编码单位，页内统计(min/max)支持谓词下推跳页 |

**为什么有 Page statistics？** 查询 `WHERE age > 50` 时，若某页的 max=30，整页直接跳过，不读不解压。这就是列存能把扫描量再砍一刀的关键。

### 4.6 算法：列编码与向量化执行

#### 三种核心列编码（把列数据压到更小）

```
1. Dictionary Encoding（字典编码）—— 适合低基数列(如 city)
   原始: ["北京","上海","北京","广州","北京","上海"]
   编码: dictionary=[北京,上海,广州]  values=[0,1,0,2,0,1]
   效果: 字符串变整数,整数再用 bit-packing 压缩(3 个值只需 2 bit)

2. Run-Length Encoding（游程编码）—— 适合排序列(如日期)
   原始: [2024-01,2024-01,2024-01,2024-02,2024-02]
   编码: [(2024-01,3),(2024-02,2)]   ← (值,连续次数)
   效果: 排序后重复值压成 (值,次数) 对

3. Delta Encoding（差值编码）—— 适合递增数值(如 id、时间戳)
   原始: [1000,1001,1002,1003,1004]
   编码: base=1000  deltas=[0,1,2,3,4]  → 再 bit-pack 成 3bit/值
   效果: 大整数变小差值,bit-packing 极致压缩
```

**编码和压缩是两步**：编码把数据变得有规律（同类型、小数值），通用压缩（Snappy/ZSTD）再压一遍。列存的压缩率远高于行存，根因就是编码后的数据高度规整。

#### 向量化执行算法（火山模型 vs 向量化）

```
火山模型（一次一行，传统数据库）:
  Scan.next() → row1 → Filter.next() → Agg.next() → 输出
  Scan.next() → row2 → Filter.next() → Agg.next() → 输出
  问题:每行一次虚函数调用,分支预测差,CPU 流水线断

向量化模型（一次一批，ClickHouse/Doris）:
  Scan.next(1024行) → batch → Filter.next(batch) → Agg.next(batch) → 输出
  优势:紧凑循环 + SIMD + 缓存命中,CPU 利用率提升 5-10 倍
```

**向量化 Filter 的内部逻辑**（批量过滤）：

```
输入: batch = [20,25,30,18,35,22]  谓词: age > 21
步骤:
1. 生成 mask 向量:  [F,T,T,F,T,T]   ← 逐元素比较,SIMD 一次算 8 个
2. 用 mask 压缩 batch: [25,30,35,22]  ← 只保留 true 的
3. 输出压缩后的 batch 给下游算子
```

### 4.7 Python 实现：列存储 + 向量化聚合

这段代码演示列存的核心：按列存储、列编码、向量化聚合（用 NumPy 模拟 SIMD 批量计算）。

```python
import numpy as np
from dataclasses import dataclass, field

# ---------- 列存表 ----------
@dataclass
class ColumnChunk:
    """一列的存储 chunk。演示字典编码 + bit-packing。"""
    name: str
    dictionary: list           # 字典:值 → 下标
    codes: np.ndarray          # 编码后的整数数组(真实是 bit-packed)

    @classmethod
    def encode(cls, name: str, values: list):
        """字典编码:适合低基数列(如 city)。字符串变整数下标。"""
        uniq = list(dict.fromkeys(values))   # 保序去重
        idx = {v: i for i, v in enumerate(uniq)}
        codes = np.array([idx[v] for v in values], dtype=np.int32)
        return cls(name, uniq, codes)

    @classmethod
    def from_numeric(cls, name: str, values: list):
        """数值列直接存原值(真实用 delta/bit-packing,这里简化)。"""
        return cls(name, None, np.array(values, dtype=np.int32))

    def scan(self):
        """解码回原值。真实引擎尽量不解码,直接对 codes 操作。"""
        if self.dictionary is None:
            return self.codes.tolist()
        return [self.dictionary[c] for c in self.codes]

class ColumnarTable:
    """列存表:每列独立存储。"""
    def __init__(self):
        self.columns = {}
        self.num_rows = 0

    def add_column(self, chunk: ColumnChunk):
        self.columns[chunk.name] = chunk
        self.num_rows = len(chunk.codes)

    def column(self, name: str) -> ColumnChunk:
        return self.columns[name]

# ---------- 向量化算子 ----------
def vectorized_filter(codes: np.ndarray, predicate) -> np.ndarray:
    """向量化过滤:返回满足谓词的下标。codes 是已解码的数值列。"""
    mask = predicate(codes)            # SIMD 批量比较,生成 bool 数组
    return np.where(mask)[0]           # 取出 true 的下标

def vectorized_sum(values: np.ndarray) -> float:
    """向量化聚合:NumPy 底层用 SIMD 一次算一批。"""
    return float(np.sum(values))

def vectorized_groupby_avg(keys: np.ndarray, values: np.ndarray):
    """向量化 group-by 聚合:按 key 分组求均值。"""
    uniq_keys = np.unique(keys)
    result = {}
    for k in uniq_keys:
        mask = keys == k               # 向量化比较
        result[k] = float(np.mean(values[mask]))   # 向量化求均值
    return result

# ---------- 演示:列存查询 ----------
if __name__ == "__main__":
    # 模拟 6 行数据
    cities = ["北京","上海","北京","广州","北京","上海"]
    ages   = [20, 25, 30, 18, 35, 22]
    table = ColumnarTable()
    table.add_column(ColumnChunk.encode("city", cities))      # 字符串列:字典编码
    table.add_column(ColumnChunk.from_numeric("age", ages))   # 数值列:直接存原值

    # 查询:SELECT city, AVG(age) FROM t GROUP BY city
    # 传统行存:逐行读、逐行聚合。列存:只读 city+age 两列,向量化聚合。
    city_codes = table.column("city").codes
    age_codes  = table.column("age").codes

    print("字典编码 city:", table.column("city").dictionary, city_codes)
    # 字典编码 city: ['北京','上海','广州'] [0 1 0 2 0 1]

    avg_by_city = vectorized_groupby_avg(city_codes, age_codes)
    for k, v in avg_by_city.items():
        print(f"{table.column('city').dictionary[k]}: avg_age={v:.1f}")
    # 北京: avg_age=28.3   上海: avg_age=23.5   广州: avg_age=18.0

    # 查询:SELECT AVG(age) FROM t WHERE age > 21
    idx = vectorized_filter(age_codes, lambda a: a > 21)
    print("age>21 的均值:", vectorized_sum(age_codes[idx]) / len(idx))
    # age>21 的均值: 28.0
```

运行后能看到：列存只读涉及的列、字典编码压缩、聚合用 NumPy 向量化（底层 SIMD）。

### 4.8 C++ 实现要点：SIMD 向量化聚合

真实列存引擎（ClickHouse/Doris）用 C++ + SIMD 指令手动优化批计算。下面是向量化 SUM 的核心写法：

```cpp
#include <immintrin.h>    // AVX2 intrinsics
#include <vector>
#include <cstdint>

// 标量版 SUM(一次一个,传统方式)
int64_t sum_scalar(const int32_t* data, size_t n) {
    int64_t sum = 0;
    for (size_t i = 0; i < n; ++i) sum += data[i];
    return sum;
}

// SIMD 版 SUM(一次 8 个,AVX2)
int64_t sum_avx2(const int32_t* data, size_t n) {
    __m256i vsum = _mm256_setzero_si256();   // 8 个 int32 累加器(256bit)
    size_t i = 0;
    // 主循环:每次加载 8 个 int32,一条指令 8 路并行加
    for (; i + 8 <= n; i += 8) {
        __m256i v = _mm256_loadu_si256((const __m256i*)(data + i));
        vsum = _mm256_add_epi32(vsum, v);    // 8 路 int32 并行累加
    }
    // 水平求和:8 个 int32 lane 加到一起(转 int64 防溢出)
    int32_t tmp[8];
    _mm256_storeu_si256((__m256i*)tmp, vsum);
    int64_t sum = 0;
    for (int j = 0; j < 8; ++j) sum += tmp[j];
    // 处理尾部不足 8 个的剩余元素
    for (; i < n; ++i) sum += data[i];
    return sum;
    // 注:教学版用 int32 累加(假设单批总和不溢出);生产版用 int64 lane 防溢出
}

// 向量化 Filter + SUM(age>21 的求和):mask 压缩 + SIMD
int64_t filtered_sum_avx2(const int32_t* ages, size_t n, int32_t threshold) {
    __m256i vthresh = _mm256_set1_epi32(threshold);
    __m256i vsum = _mm256_setzero_si256();   // 8 路 int32 累加
    size_t i = 0;
    for (; i + 8 <= n; i += 8) {
        __m256i v = _mm256_loadu_si256((const __m256i*)(ages + i));
        // 逐元素比较:age > threshold 生成 mask(全 1 或全 0 的 int32)
        __m256i mask = _mm256_cmpgt_epi32(v, vthresh);
        // mask 与原值按位与:不满足的清零,满足的保留(无分支!)
        __m256i masked = _mm256_and_si256(v, mask);
        vsum = _mm256_add_epi32(vsum, masked);
    }
    int32_t tmp[8]; _mm256_storeu_si256((__m256i*)tmp, vsum);
    int64_t sum = 0;
    for (int j = 0; j < 8; ++j) sum += tmp[j];
    for (; i < n; ++i) if (ages[i] > threshold) sum += ages[i];
    return sum;
}
```

**SIMD 为什么快——三个 CPU 特性的叠加**：

| 特性 | 标量版 | SIMD 版 | 收益 |
|------|--------|---------|------|
| 指令并行 | 1 条 add 算 1 个 | 1 条 `vpadd` 算 8 个 | 8× 吞吐 |
| 缓存 | 跳行访问 miss 多 | 连续列数据预取友好 | L1 命中率高 |
| 分支 | 有 if 判断 | 无分支（mask 按位与） | 流水线不断 |

**向量化 Filter 用 mask 而非 if 的精妙**：`age > 21 ? age : 0` 写成 `age & mask`，避免分支预测失败。8 个值同时算，CPU 流水线满载。这是 ClickHouse 单表查询比 MySQL 快 100× 的底层根因之一。

**Python 版和 C++ 版的对应关系**：

| 概念 | Python 演示版 | C++ SIMD 版 |
|------|--------------|-------------|
| 列存储 | `ColumnChunk` + dict 编码 | Parquet/ORC 的 Column Chunk |
| 批量计算 | `np.sum` / `np.where` | `_mm256_add_epi64` / `_mm256_cmpgt` |
| 向量化过滤 | `mask = predicate(codes)` | `_mm256_cmpgt_epi32` 生成 mask |
| 分组聚合 | `np.unique` + 循环 | Hash 表 + SIMD 聚合 |

NumPy 的底层就是 C + SIMD，所以 Python 版能直接享受向量化收益——这也是为什么数据科学用 NumPy/Pandas 而非原生 Python 列表。

## 5. 三种结构的对比与选型

| 维度 | B+Tree | LSM-Tree | 列存 |
|------|--------|----------|------|
| 写 | 慢（页分裂+锁） | 极快（顺序追加） | 慢（重写列块） |
| 点查 | 极快 | 较慢（读放大） | 慢 |
| 范围扫描 | 快 | 中 | 中 |
| 分析聚合 | 慢（读整行） | 慢 | 极快（向量化） |
| 压缩率 | 低 | 中 | 高 |
| 典型 | MySQL | HBase/RocksDB | ClickHouse/Parquet |
| 解的矛盾端 | 读优化 | 写优化 | 分析优化 |

**选型决策**（用第一性原理 5 步法）：
1. 业务是 OLTP（点查事务）→ B+Tree（MySQL）。
2. 业务是写密集日志/时序 → LSM（HBase/Cassandra）。
3. 业务是 OLAP 分析 → 列存（ClickHouse/Doris）。
4. 离线数仓存储格式 → Parquet/ORC 列存（配合 Spark/Trino）。

## 6. 向量化执行：为什么是列存的"第二增长曲线"

向量化是 ClickHouse、Doris、Photon 等 OLAP 引擎性能的核心，值得单独讲透。

### 6.1 火山模型 vs 向量化模型

传统数据库用**火山模型**（Volcano）：每个算子一次 `next()` 吐一行，行行传递。问题是每次只处理一行，虚函数调用、分支判断开销巨大，CPU 利用率很低。

```
火山模型（一次一行）:          向量化模型（一次一批）:
  Scan → next(行1) → Filter → Agg    Scan → next(1024行) → Filter → Agg
  Scan → next(行2) → Filter → Agg    （一批一起处理，紧凑循环）
  ... 每行都有函数调用开销
```

向量化模型一次处理一批（如 1024 行），算子间传递列向量，用紧凑循环+SIMD 批量计算。

### 6.2 为什么快——CPU 视角

- **缓存命中**：列数据连续，预取友好，L1/L2 缓存命中率高。
- **SIMD**：一条 AVX2 指令同时算 8 个 int 或 16 个 short，相当于免费并行。
- **无分支**：紧凑循环没有 if，CPU 流水线不中断，避免分支预测惩罚。
- **少虚函数调用**：一批一次调用，摊薄开销。

### 6.3 代价

向量化要求数据按列组织（列存），且算子要改写成批处理逻辑。它和列存是**共生关系**——列存提供按列数据，向量化提供按列计算。这就是为什么 ClickHouse 必须是列存引擎，不能在行存上加向量化。

> **存储引擎的本质是"读写权衡"：B+Tree 用有序换读快，LSM 用追加换写快，列存用按列换分析快。没有银弹，只有场景适配。理解了这一点，你就能解释为什么 MySQL 不适合做数仓、为什么 ClickHouse 不能当业务库、为什么 HBase 写入快但点查要套 Redis——这些都是矛盾 7 的必然推论，而非偶然。**
