# 原理深潜 1：存储引擎——为什么 B-Tree、LSM、列存各快各的

> **本文定位**：对应第一性原理**矛盾 7（读优化 vs 写优化）**。课程里课时13（Hive 文件格式）、课时16.5（OLAP 引擎）、DDIA 第 3 章都涉及存储引擎，但散落在各处、停在"是什么"。本文把这些碎片串成一条原理主线，回答一个核心问题：**为什么没有一种存储结构能通吃所有场景？ClickHouse 凭什么单表查询快到极致？HBase 凭什么写入快？MySQL 凭什么点查快？**
>
> **前置阅读**：`大数据第一性原理.md` 第 2 章矛盾 7。

---

## 1. 问题的起点：访问模式决定存储结构

存储引擎的选择，不取决于"数据长什么样"，而取决于**数据怎么被访问**。访问模式分两大类：

| 访问模式 | 特征 | 典型场景 | 偏好的存储结构 |
|---------|------|---------|--------------|
| 事务型（OLTP） | 高频小量读写，按主键点查/范围查，要低延迟 | MySQL 业务库、订单系统 | B-Tree |
| 分析型（OLAP） | 大批量扫描，按列聚合，要高吞吐 | 数仓报表、BI 分析 | 列存 + 向量化 |
| 写密集型 | 海量写入，少量读取 | 日志、IoT、时序 | LSM-Tree |

**为什么没有通吃的结构？** 因为读和写在物理上是矛盾的：

- **要读得快**，数据就得有序、紧凑、有索引——但写入时要维护这个有序结构，就得移动数据、加锁，写就慢。
- **要写得快**，数据就该无序追加（append）——但读时就要在无序数据里翻找，读就慢。

这是一个物理层面的权衡，无法靠工程技巧消除。所有存储引擎都是在"读快"和"写快"之间选一个点。下面三种结构，就是三个不同的选择点。

---

## 2. B-Tree：读优化的经典

**代表**：MySQL InnoDB、PostgreSQL。

### 2.1 结构与原理

B-Tree 是一棵平衡多路查找树。数据按主键有序存储在叶子节点，叶子节点间用链表串起来（B+Tree 变种）。

```
              [10 | 20 | 30]            ← 内部节点（索引，指引搜索方向）
             /      |      |     \
       [1,3,7] [10,12,15] [20,22] [30,35,40]  ← 叶子节点（存数据，有序+链表）
         ↔        ↔          ↔        ↔
```

**为什么读快**：
- 点查：从根到叶走 O(log N) 次，每次一个磁盘页（16KB），3-4 层就能索引千万级数据——意味着点查只需 3-4 次磁盘 IO。
- 范围查：找到起点叶子后，沿链表顺序扫描，局部性好。

### 2.2 为什么写得慢

B-Tree 要保持有序，每次写入可能触发**页分裂**（一个页满了要拆成两个）和**索引维护**。页分裂要移动数据、更新父节点指针，还要加锁保证并发安全。所以 B-Tree 的写是"原地更新 + 加锁维护"，开销大。

### 2.3 权衡总结

| 维度 | B-Tree |
|------|--------|
| 读 | 极快（点查、范围查都优） |
| 写 | 慢（页分裂+锁） |
| 空间 | 有填充因子浪费（页不满） |
| 适合 | OLTP、事务、强一致点查 |
| 失败模式 | 大量随机写时性能急剧下降；不适合全表扫描分析 |

**第一性原理挂载**：B-Tree 选了矛盾 7 的"读优化"端，代价是写慢。MySQL 适合业务库而不适合数仓分析，根因在此。

## 3. LSM-Tree：写优化的工程奇迹

**代表**：HBase、Cassandra、RocksDB、LevelDB。

### 3.1 核心思想：把随机写变成顺序写

磁盘的物理特性是：**顺序写比随机写快 100 倍以上**（机械盘尤其明显，SSD 也有差距）。LSM-Tree 的天才之处在于：**所有写入都不去碰有序结构，而是无脑追加到内存**，把随机写彻底变成顺序写。

### 3.2 结构与工作流

```
写入流程:
  1. 数据写入 MemTable（内存，有序）+ WAL（预写日志，防宕机）
  2. MemTable 满了 → 刷成 SSTable（磁盘上的有序文件），进入 Level 0
  3. 后台 Compaction：把多层 SSTable 合并、去重、整理成更大的有序文件

读取流程:
  1. 查 MemTable（内存）
  2. 查 Level 0 SSTable（多个，可能有重叠）
  3. 查 Level 1, 2, ... N SSTable（每层有序，层间不重叠）
  4. 用布隆过滤器快速跳过不含 Key 的文件
```

```
Level 0:  [SSTable A][SSTable B]   ← 可能有 Key 重叠（同一 Key 多版本）
Level 1:  [.........有序无重叠.........]
Level 2:  [............更大更稀疏............]
```

### 3.3 为什么写得快

写入只是"内存追加 + WAL 顺序写"，完全不碰磁盘上的有序结构。写延迟≈内存写入延迟，极快。这就是 HBase、Kafka 能扛高吞吐写入的根因。

### 3.4 为什么读慢（读放大）

读一个 Key，可能要查 MemTable + 多层 SSTable。即使有布隆过滤器，最坏情况仍要查多层。这叫**读放大**（读一个 Key 实际读了多个文件）。

### 3.5 Compaction：LSM 的命门

Compaction 是 LSM 维持读取性能的关键——不合并的话，SSTable 越积越多，读放大越来越严重。但 Compaction 本身要读多层、写新层，消耗大量 IO 和 CPU，称为**写放大**（写 1 字节数据实际写多次，因为 Compaction 反复重写）。

```
权衡三角（LSM 的三难）:
  读放大  ──┐
            ├── 三者无法同时最小，Compaction 策略就是在三者间调
  写放大  ──┤
            │
  空间放大──┘  （不合并则旧版本占空间）
```

### 3.6 权衡总结

| 维度 | LSM-Tree |
|------|----------|
| 写 | 极快（顺序追加） |
| 读 | 较慢（多层查找+读放大） |
| 适合 | 写密集、日志、时序 |
| 失败模式 | Compaction 跟不上写入时，SSTable 堆积，读延迟飙升（生产事故常见根因）；点查性能弱于 B-Tree |

**第一性原理挂载**：LSM 选了矛盾 7 的"写优化"端，代价是读放大和 Compaction 开销。HBase 适合海量写入的日志/时序，不适合高频点查——这也是为什么 HBase 之上常再套 Redis 做点查缓存。

### 3.7 为什么 HBase 用 LSM 而 MySQL 用 B-Tree

回到第一性原理：HBase 面向"海量数据写入+稀疏宽表"场景（矛盾 1 的分片 + 矛盾 4 的容错），写入吞吐是第一诉求；MySQL 面向"事务点查"场景，读取延迟是第一诉求。两者的访问模式不同，所以选了矛盾 7 的不同端。**这不是谁更先进，而是场景适配。**

## 4. 列式存储：分析查询的加速器

**代表**：Parquet、ORC（文件格式）；ClickHouse、Doris、Druid（存储引擎）。

### 4.1 核心思想：按列而非按行存储

行存（B-Tree/LSM 存的是整行）：一条记录的字段连续存储。
列存：同一列的所有值连续存储，不同列分开放。

```
行存（适合取整行）:            列存（适合按列聚合）:
  行1: [id=1, name=张三, age=20, city=北京]
  行2: [id=2, name=李四, age=25, city=上海]    id列:   [1,2,3,4]
  行3: [id=3, name=王五, age=30, city=广州]    name列: [张三,李四,王五,赵六]
  行4: [id=4, name=赵六, age=28, city=深圳]    age列:  [20,25,30,28]
                                              city列: [北京,上海,广州,深圳]
```

### 4.2 为什么分析查询快——三个层次的加速

**第一层：减少 IO（只读需要的列）**
分析查询通常只涉及少数列。如 `SELECT city, AVG(age) FROM users GROUP BY city` 只需 city 和 age 两列。行存要把整行读出来再丢弃无用列；列存只读这两列，IO 量可能减少 90%+。

**第二层：列内压缩率极高**
同一列的数据类型相同（都是整数、都是字符串），编码后压缩率远高于行存混合数据。例如 age 列全是小整数，可用 delta 编码压到极致。**压缩不仅省空间，更减少了磁盘 IO——读的字节少了，查询就快了。**

**第三层：向量化执行（关键！）**
列存天然适配向量化：一次取出一列的一批值（如 1024 个 age），用一个紧凑循环批量处理，利用 CPU 的三个特性：
- **CPU 缓存友好**：连续内存，缓存命中率高
- **SIMD 指令**：一条指令同时处理多个数据（如一次算 8 个整数的和）
- **无分支预测失败**：紧凑循环没有 if/else 分支，CPU 流水线不断

这就是 ClickHouse 单表查询快到极致的根因——列存 + 向量化 + 压缩，三位一体把分析查询的每个环节都压榨到极限。

### 4.3 为什么更新/删除慢

列存按列分文件，更新一行意味着要改多个列文件、重写整个列块。所以列存几乎不支持高效的单行更新。ClickHouse 用 `ReplacingMergeTree` 异步合并去重来"模拟"更新，代价是更新有延迟、且查询时需注意合并语义。

### 4.4 权衡总结

| 维度 | 列存 |
|------|------|
| 分析查询 | 极快（少 IO + 高压缩 + 向量化） |
| 点查/更新 | 很慢 |
| 适合 | OLAP、数仓、BI |
| 失败模式 | 点查、频繁更新场景性能差；小文件多时压缩优势丧失 |

**第一性原理挂载**：列存选了矛盾 7 的"分析优化"端。Hive 数仓用 Parquet/ORC 列存、ClickHouse 用列存+向量化，都是为了分析查询的吞吐；代价是放弃了事务型点查能力。

## 5. 三种结构的对比与选型

| 维度 | B-Tree | LSM-Tree | 列存 |
|------|--------|----------|------|
| 写 | 慢（页分裂+锁） | 极快（顺序追加） | 慢（重写列块） |
| 点查 | 极快 | 较慢（读放大） | 慢 |
| 范围扫描 | 快 | 中 | 中 |
| 分析聚合 | 慢（读整行） | 慢 | 极快（向量化） |
| 压缩率 | 低 | 中 | 高 |
| 典型 | MySQL | HBase/RocksDB | ClickHouse/Parquet |
| 解的矛盾端 | 读优化 | 写优化 | 分析优化 |

**选型决策**（用第一性原理 5 步法）：
1. 业务是 OLTP（点查事务）→ B-Tree（MySQL）。
2. 业务是写密集日志/时序 → LSM（HBase/Cassandra）。
3. 业务是 OLAP 分析 → 列存（ClickHouse/Doris）。
4. 离线数仓存储格式 → Parquet/ORC 列存（配合 Spark/Trino）。

## 6. 向量化执行：为什么是列存的"第二增长曲线"

向量化是 ClickHouse、Doris、Photon 等 OLAP 引擎性能的核心，值得单独讲透。

### 6.1 火山模型 vs 向量化模型

传统数据库用**火山模型**（Volcano）：每个算子一次 `next()` 吐一行，行行传递。问题是每次只处理一行，虚函数调用、分支判断开销巨大，CPU 利用率很低。

```
火山模型（一次一行）:          向量化模型（一次一批）:
  Scan → next(行1) → Filter → Agg    Scan → next(1024行) → Filter → Agg
  Scan → next(行2) → Filter → Agg    （一批一起处理，紧凑循环）
  ... 每行都有函数调用开销
```

向量化模型一次处理一批（如 1024 行），算子间传递列向量，用紧凑循环+SIMD 批量计算。

### 6.2 为什么快——CPU 视角

- **缓存命中**：列数据连续，预取友好，L1/L2 缓存命中率高。
- **SIMD**：一条 AVX2 指令同时算 8 个 int 或 16 个 short，相当于免费并行。
- **无分支**：紧凑循环没有 if，CPU 流水线不中断，避免分支预测惩罚。
- **少虚函数调用**：一批一次调用，摊薄开销。

### 6.3 代价

向量化要求数据按列组织（列存），且算子要改写成批处理逻辑。它和列存是**共生关系**——列存提供按列数据，向量化提供按列计算。这就是为什么 ClickHouse 必须是列存引擎，不能在行存上加向量化。

## 7. 串到课程其他知识点

把存储引擎原理挂回课程其他地方，形成知识网络：

- **课时13 Hive 文件格式**：为什么 Hive 选 Parquet/ORC 而非 TextFile？因为数仓是 OLAP（矛盾 7 的分析端），列存让聚合查询快。TextFile 只适合调试。
- **课时16.5 OLAP 引擎**：ClickHouse 用 MergeTree（LSM 思想管理列存数据）+ 向量化，本质是"列存的读优化 + LSM 的写管理"的混合体。
- **课时22 Iceberg**：Iceberg 表底层存 Parquet 列存文件，再用元数据层管理——把列存的分析性能和湖仓的灵活性结合。
- **DDIA Ch3**：读书会里讲 LSM vs B-Tree，本文是它的系统化展开。
- **论文3 BigTable**：BigTable 是 LSM 思想的源头（SSTable + MemTable），HBase 是其开源实现。
- **论文4 Dremel**：Dremel 是列式存储嵌套数据的源头，Parquet/ORC 继承其思想。

## 8. 一句话总结

> **存储引擎的本质是"读写权衡"：B-Tree 用有序换读快，LSM 用追加换写快，列存用按列换分析快。没有银弹，只有场景适配。理解了这一点，你就能解释为什么 MySQL 不适合做数仓、为什么 ClickHouse 不能当业务库、为什么 HBase 写入快但点查要套 Redis——这些都是矛盾 7 的必然推论，而非偶然。**
