# 原理深潜 2：一致性与容错——为什么分布式系统不能既要、又要、还要

## 1. 问题的起点：容错和一致性是一个问题，不是两个

很多人把"容错"和"一致性"当作两个独立话题。这是错觉。它们是**同一个问题的两面**，根源在于矛盾 1（分片+副本）。

**推导链**：

```
矛盾1：数据太多单机装不下 → 必须分片到多台机器
                          → 机器会坏，数据会丢 → 必须存副本
                          → 副本之间可能不一致（写入时某个副本还没同步）
                          → 矛盾4：故障是常态，必须能从故障恢复
                          → 矛盾5：分区时，要么拒绝服务保一致(C)，要么继续服务丢一致(A)
```

**关键洞察**：如果只有一台机器（单机），容错和一致性几乎不是问题——数据只有一份，没有"副本不一致"这回事。一致性问题是**多副本**带来的，而多副本是为了**容错**。所以容错和一致性是因果相连的：**你为了容错引入了副本，副本带来了一致性问题。**

这就是为什么本文把矛盾 4 和矛盾 5 放在一起讲——它们是同一根链条上的两个环节。

## 2. CAP 定理：为什么三选二

### 2.1 三个字母的精确含义

CAP 不是三个特性的简单罗列，而是**一个约束关系**：

- **C（一致性，Consistency）**：这里特指**线性一致性**（Linearizability）——读操作一定返回最新写入的值。对外看起来就像只有一个数据副本。
- **A（可用性，Availability）**：每个请求都能收到**非错误响应**（不保证是最新数据），且延迟在有限时间内。
- **P（分区容忍，Partition Tolerance）**：网络分区（部分机器间通信中断）时，系统仍能运转。

### 2.2 为什么 P 不可放弃

很多人问"能不能选 CA 放弃 P"。答案是：**在分布式系统中，P 不是你能选放弃的——网络分区是物理现实。**

网络交换机会故障、网线会被挖断、GC 停顿会让节点"看似"下线。你不能假设网络永远不分区。所以 CAP 的真实含义不是"三选二"，而是：

> **当分区发生时，你只能在 C 和 A 之间二选一。**

- 选 C（CP）：分区时，未同步的副本**拒绝服务**，保证不返回旧数据。代价是可用性下降。
- 选 A（AP）：分区时，副本**继续服务**，可能返回旧数据。代价是一致性被破坏。

**不分区时**，C 和 A 可以同时满足——这正是你平时的状态。CAP 的约束只在分区那一刻生效。

### 2.3 常见误解澄清

| 误解 | 事实 |
|------|------|
| "我选 CA，不要 P" | 分布式系统无法放弃 P，网络分区不可预测 |
| "Kafka 是 AP 系统" | 不准确。Kafka 对不同操作有不同选择：元数据管理用 ZK（CP），消息副本用 ISR（可调） |
| "最终一致就是没有一致性" | 最终一致是一致性谱系的一端，不是"无一致性"。它保证"最终"会一致，只是中间可能不一致 |
| "CAP 是静态选择" | 不是。同一系统在不同操作上可以做不同选择（如 Cassandra 的可调一致性） |

### 2.4 CP vs AP 的工程选择

| 维度 | CP 系统 | AP 系统 |
|------|---------|---------|
| 分区时行为 | 拒绝服务 | 继续服务 |
| 代表 | ZooKeeper、Spanner、etcd | Dynamo、Cassandra、Kafka（默认） |
| 适用场景 | 金融交易、配置管理、锁 | 互联网高并发、社交feed、推荐 |
| 代价 | 分区时不可用 | 分区后需修复冲突 |

**第一性原理挂载**：CP 和 AP 不是"谁更好"，而是场景适配。金融场景宁可拒绝服务也不能错（选 C）；社交 feed 宁可看到旧数据也不能停（选 A）。

## 3. 一致性级别谱系：从线性一致到最终一致

CAP 里的"C"是线性一致——最强的一致性。但现实中有一整条谱系，越往左越强、越贵：

```
线性一致  >  顺序一致  >  因果一致  >  读己之写  >  最终一致
  (最强)                                              (最弱)
```

### 3.1 各级别的含义

| 级别 | 含义 | 代价 |
|------|------|------|
| 线性一致 | 读一定返回最新写。所有操作看起来在一个全局时间线上排序 | 最高延迟（需同步多数派） |
| 顺序一致 | 所有客户端看到的操作顺序相同，但不一定是真实时间顺序 | 中等延迟 |
| 因果一致 | 有因果关系的操作保序，无因果的可重排 | 较低延迟 |
| 读己之写 | 你一定能看到自己的写 | 低延迟（需会话粘性） |
| 最终一致 | 不读时最终所有副本会一致 | 最低延迟 |

### 3.2 为什么越强越贵

**线性一致为什么贵**：一次写入要同步到**多数派副本**才算成功（否则分区时可能丢失）。这意味着每次写都要等多数派确认，延迟 = 网络往返时间 × 1。读也要走多数派（否则可能读到旧副本），延迟同样高。

**最终一致为什么便宜**：写入只需写入**一个副本**就返回，其他副本异步同步。延迟≈本地写延迟，极快。代价是短时间内读到的可能是旧数据。

**工程智慧**：多数系统不追求线性一致，而是在谱系上找一个"够用"的点。Cassandra 让用户选 `ONE/QUORUM/ALL`——选 ONE 快但可能不一致，选 ALL 一致但慢，选 QUORUM（多数派）是折中。这就是"可调一致性"。

## 4. 共识协议为什么必要

### 4.1 什么是共识

**共识（Consensus）**：多个节点对一个值达成一致。

听起来简单，实则是分布式系统最核心、最难的问题之一。为什么难？因为：

- 节点可能故障（崩溃、重启）
- 网络可能分区（消息丢失、延迟）
- 没有一个"全局时钟"来判断哪个操作先发生

**共识的典型场景**：
- Leader 选举：谁是当前 Leader？
- 日志复制：所有副本按什么顺序应用写入？
- 分布式锁：谁拿到了锁？

### 4.2 Paxos：学术源头

**Paxos**（Lamport, 1998）是共识协议的理论源头。它的核心思想：

1. **Prepare 阶段**：提议者向多数派承诺"不接受比编号 N 更小的提案"
2. **Accept 阶段**：提议者向多数派发送提案，多数派接受后提案通过

**为什么 Paxos 难懂**：它证明了"在多数派达成一致"是可行的，但论文用的是数学证明而非工程描述。它没有清晰的 Leader 概念，多个提议者可以同时提议，导致活锁。**Paxos 证明了"能做"，但没有告诉你"怎么做才好用"。**

### 4.3 Raft：工程化的共识

**Raft**（2014）的设计目标就是"可理解性"——先让人类能懂，再让机器能用。它的核心简化：

1. **强 Leader**：只有一个 Leader 处理所有写入，其他节点是 Follower。这消除了 Paxos 的多提议者活锁问题。
2. **日志复制**：Leader 把写入追加到自己的日志，然后复制到所有 Follower。多数派确认后提交。
3. **Leader 选举**：Leader 挂了，Follower 通过任期号（Term）和心跳超时发起选举，多数派投票选出新 Leader。

```
Raft 的写入流程:
  Client → Leader: 写入 X=1
  Leader: 追加日志 (Term=5, Index=10, X=1)
  Leader → Followers: 复制日志
  Followers: 追加日志，回复 ACK
  Leader: 收到多数派 ACK → 提交（标记为已应用）
  Leader → Client: 写入成功
  Leader → Followers: 通知提交（Follower 也应用到状态机）
```

**为什么 Raft 能保证一致性**：
- 已提交的日志一定在多数派上（否则不会提交）
- 新 Leader 一定包含所有已提交的日志（因为它获得了多数派投票，而已提交的日志也在多数派上，两个多数派必有交集）
- 所以新 Leader 不会丢失已提交的数据

### 4.4 Zab：ZooKeeper 的变种

**Zab**（ZooKeeper Atomic Broadcast）和 Raft 类似，也是 Leader-based 的日志复制协议。区别在于：
- Zab 的 Leader 选举考虑了数据的完整性（拥有最新数据的节点优先）
- Zab 用"原子广播"而非"日志复制"来描述，但本质相似

**为什么 ZooKeeper 用 Zab 而非 Raft**：历史原因。ZooKeeper（2008）比 Raft（2014）早，当时 Raft 还没出来。Zab 是 ZooKeeper 团队自己设计的。

### 4.5 共识协议的第一性原理

所有共识协议的本质都是：**通过多数派投票，在故障和分区下达成一致。**

- **为什么是多数派**：两个多数派必有交集，所以不会出现"两个不同值都获多数派同意"的分裂情况。
- **为什么需要 Leader**：简化协议——所有写入走 Leader，避免多提议者的冲突和活锁。
- **为什么有 Term/Epoch**：防止旧 Leader（已分区或重启）用过期身份干扰新 Leader。

**代价**：共识协议要求多数派确认，所以：
- 写延迟 ≥ 一次多数派往返
- 可用性要求多数派存活（3 节点容忍 1 个故障，5 节点容忍 2 个）
- 不能无限扩展——节点越多，多数派越大，延迟越高

## 5. 副本与 ISR：Kafka 的工程智慧

### 5.1 三种复制策略的权衡

| 策略 | 机制 | 优点 | 缺点 |
|------|------|------|------|
| 同步复制 | 写入所有副本后才返回 | 强一致 | 慢（等最慢副本），一个副本慢拖垮全部 |
| 纯异步复制 | 写入一个副本就返回 | 极快 | 可能丢数据（副本还没同步就挂了） |
| ISR（折中） | 写入ISR中所有副本后返回 | 一致性与性能平衡 | 需要动态维护ISR |

### 5.2 ISR 的核心思想

**ISR（In-Sync Replicas，同步副本集合）**：Kafka 的折中方案。不是"所有副本"也不是"一个副本"，而是"跟得上的副本"。

```
所有副本:  [Replica 0(Leader), Replica 1, Replica 2, Replica 3, Replica 4]
ISR:      [Replica 0(Leader), Replica 1, Replica 2]  ← 跟得上的
OSR:      [Replica 3, Replica 4]                     ← 落后太多的

写入流程:
  Producer → Leader: 写入消息
  Leader: 追加到本地日志
  Leader → ISR中的Follower: 复制
  ISR中的Follower: 追加并ACK
  Leader: 收到ISR全部ACK → 提交 → 回复Producer
```

**ISR 的动态维护**：
- Follower 落后超过阈值（时间或条数）→ 移出 ISR，进入 OSR
- Follower 追上 → 加回 ISR
- ISR 缩小到 0 → 触发告警（无可用副本）

### 5.3 acks 参数：让用户选一致性级别

Kafka 的 `acks` 参数体现了"可调一致性"思想：

| acks | 含义 | 一致性 | 性能 | 适用场景 |
|------|------|--------|------|---------|
| 0 | 不等任何确认 | 最弱 | 最快 | 日志采集（丢一点没关系） |
| 1 | 等Leader确认 | 中 | 快 | 一般业务 |
| all/-1 | 等ISR全部确认 | 最强 | 慢 | 金融、交易 |

**配合 `min.insync.replicas`**：
- `acks=all` + `min.insync.replicas=2`：至少 2 个副本确认才算成功
- 如果 ISR 缩小到 1（只有 Leader），写入会失败——宁可拒绝也不丢数据

**第一性原理挂载**：ISR 是矛盾 4（容错）和矛盾 5（一致性）的工程折中。它用"动态集合"避免了同步复制的慢和异步复制的丢，让用户通过 `acks` 自己选 C 和 A 的平衡点。

## 6. 强一致为什么贵

### 6.1 两阶段提交（2PC）的代价

**2PC** 是实现跨节点强一致的经典协议，也是** Exactly-Once** 的基础之一。

```
2PC 流程:
  阶段1（Prepare）:
    协调者 → 所有参与者: "准备提交?"
    参与者: 锁定资源，回复 YES/NO
  
  阶段2（Commit/Rollback）:
    如果全部YES → 协调者: "提交!"
    如果有NO → 协调者: "回滚!"
    参与者: 执行并释放锁
```

**2PC 的代价**：
1. **阻塞**：参与者在 Prepare 后锁定资源，直到 Commit/Rollback。期间不能做其他事。
2. **协调者单点**：协调者挂了，参与者会一直阻塞（不知道该提交还是回滚）。
3. **性能差**：两次网络往返 + 资源锁定，延迟高。

**为什么 2PC 贵但必须用**：跨节点事务（如 Kafka 事务、分布式数据库）需要原子性——要么全成功，要么全失败。没有 2PC 或类似机制，无法保证跨节点一致性。

### 6.2 Spanner：用原子钟换全局强一致

**Spanner**（Google, 2012）是强一致的极致方案。它的核心创新是 **TrueTime**：

- 用**原子钟 + GPS** 让全球数据中心的时间误差 < 7ms
- 给每个事务打上**全局唯一的时间戳**
- 用时间戳确定事务顺序，实现全局线性一致

**为什么这么贵**：
- 需要原子钟硬件（数据中心配备 GPS 和原子钟）
- 写入要等待"时间确定"（commit wait），增加延迟
- 工程复杂度极高

**为什么 Google 要做**：Google 的广告计费等场景要求全球强一致，宁可花大代价也要做。这说明：**强一致不是做不到，而是代价大。多数场景不值得。**

### 6.3 为什么多数场景选择最终一致

| 场景 | 一致性需求 | 选择 |
|------|----------|------|
| 银行转账 | 不能错 | 强一致（2PC） |
| 电商库存 | 超卖有损失 | 强一致（但可用性可降级） |
| 社交feed | 看到旧动态无所谓 | 最终一致 |
| 搜索索引 | 短暂不一致可接受 | 最终一致 |
| 缓存 | 本就是临时数据 | 最终一致 |

**工程智慧**：不是所有数据都需要强一致。识别出你的业务哪些数据需要强一致（通常 < 20%），对这些走强一致路径；其余走最终一致，换取高可用和高性能。

## 7. Exactly-Once 语义：为什么这么难

### 7.1 三种交付语义

| 语义 | 含义 | 实现难度 |
|------|------|---------|
| At-Most-Once | 最多一次，可能丢 | 最简单（发完不管） |
| At-Least-Once | 至少一次，可能重复 | 中等（失败重试） |
| Exactly-Once | 恰好一次，不丢不重 | 最难 |

### 7.2 为什么 Exactly-Once 难

**表面问题**：网络不可靠，消息可能丢失或重复。重试解决丢失但引入重复，不重试解决重复但引入丢失。

**深层问题**：Exactly-Once 不是"消息只发一次"，而是"**效果上只执行一次**"——即使消息被重试多次，最终结果也像只执行了一次。这要求：

1. **幂等性**：同一操作执行多次，效果等同执行一次。如"设置 X=1"是幂等的，"X 加 1"不是。
2. **事务性**：消费+处理+下游写入必须原子——要么全成功，要么全回滚。

### 7.3 两种实现路径

**路径一：At-Least-Once + 幂等去重**

```
Producer: 开启幂等（用序列号去重）
  → Broker: 收到重复消息时去重
Consumer: At-Least-Once 消费（可能重复读）
  → 下游: 幂等写入（用主键去重）

优点: 简单，不需要 2PC
缺点: 要求下游支持幂等（不是所有下游都能）
```

**路径二：两阶段提交（2PC）**

```
Kafka 事务:
  1. Producer 发起事务
  2. 消费→处理→写入下游→写入Kafka（全部在事务内）
  3. 提交事务（2PC）→ 下游可见

优点: 端到端 Exactly-Once，不依赖下游幂等
缺点: 2PC 的代价（阻塞、延迟、复杂）
```

### 7.4 Kafka 的事务机制

Kafka 的事务实现了"消费-处理-生产"的端到端 EOS：

```
1. Producer 用 transactional.id 注册（防止重启后产生新的事务实例）
2. Producer 发起事务
3. 消费输入topic → 处理 → 写入输出topic + 写入__transaction_state
4. 提交事务：Coordinator 写"commit"标记到 __transaction_state
5. Consumer 读取输出topic时：只读取已提交的事务消息（read_committed 隔离级别）
```

**关键设计**：
- `transactional.id`：保证 Producer 重启后能恢复之前的事务状态（abort 或 commit）
- `__transaction_state`：内部 topic，记录事务状态
- `isolation.level=read_committed`：Consumer 只读已提交的消息

### 7.5 Flink 的端到端 EOS

Flink 的 Exactly-Once 需要 Source + Checkpoint + Sink 三者配合：

```
Source: 可重放的源（如 Kafka，记录消费位移）
  → 失败后从Checkpoint恢复，重新消费

Checkpoint: Chandy-Lamport 分布式快照
  → 周期性保存状态和位移（见原理深潜4）

Sink: 支持事务的下游
  → 方式A: 事务写入（2PC，如 Kafka 事务）
  → 方式B: 幂等写入（如 MySQL 用主键去重）
```

**为什么需要三者配合**：任何一个环节不支持，EOS 都会断裂。Source 不可重放 → 失败会丢数据；Checkpoint 不一致 → 状态会错乱；Sink 不支持事务/幂等 → 会产生重复。

**第一性原理挂载**：Exactly-Once 是矛盾 4（容错）的极致追求——故障后不仅不丢数据，还不重复。代价是巨大的工程复杂度（2PC + Checkpoint + 事务性 Sink）。**多数场景下，At-Least-Once + 幂等已经够用，不值得为 EOS 承受全部复杂度。**

## 8. 权衡总结

| 维度 | 强一致（CP） | 最终一致（AP） | 可调一致 |
|------|------------|--------------|---------|
| 分区时 | 拒绝服务 | 继续服务 | 用户选择 |
| 写延迟 | 高（同步多数派） | 低（写一个副本） | 取决于配置 |
| 可用性 | 多数派存活才可用 | 任何副本可服务 | 取决于配置 |
| 复杂度 | 高（共识协议） | 中（冲突修复） | 中（可调参数） |
| 代表系统 | ZooKeeper、Spanner | Dynamo、Cassandra | Kafka(ISR)、Cassandra |
| 典型场景 | 金融、配置 | 社交、搜索 | 通用 |

**共识协议对比**：

| 协议 | 设计目标 | Leader模型 | 可理解性 | 代表实现 |
|------|---------|-----------|---------|---------|
| Paxos | 理论证明 | 无Leader（多提议者） | 极难懂 | 理论基础 |
| Raft | 可理解性 | 强Leader | 易懂 | etcd、Consul |
| Zab | ZooKeeper专用 | 强Leader | 中等 | ZooKeeper |

## 9. 串到课程知识点

- **课时17 Kafka 架构**：ISR 是矛盾 4/5 的工程折中。`acks` 参数让用户选一致性级别。Kafka 用追加日志+副本解矛盾 1（分片）+ 矛盾 6（高吞吐）。
- **课时18 Kafka EOS**：事务性 Producer + `__transaction_state` + `read_committed` 隔离级别。这是 2PC 思想在消息系统的应用。
- **课时20 Flink Checkpoint**：Chandy-Lamport 算法做分布式快照。Checkpoint 是矛盾 4（容错）的解法，也是 EOS 的基础。详见原理深潜4。
- **论文9 Raft**：Raft 论文是共识协议的工程化典范。读论文时重点理解：Leader 选举的 Term 机制、日志复制的安全性证明、日志不一致时的修复。
- **论文8 Dynamo**：Dynamo 论文是 AP 系统的代表。它用向量时钟解决冲突、用 hinted handoff 处理故障、用一致性哈希做分片。对比 Kafka ISR 理解"可调一致性"。
- **DDIA Ch5/Ch9**：DDIA 对一致性和共识有系统讲解。本文是它的课程化精简版。

## 10. 一句话总结

> **一致性和容错是一枚硬币的两面：你为了容错引入了副本，副本带来了一致性问题。CAP 说分区时你只能在 C 和 A 间选一个，共识协议（Paxos/Raft）是多数派达成一致的数学保证，ISR 是 Kafka 的可调一致性折中，Exactly-Once 是容错的极致追求但代价巨大。没有"最好"的一致性，只有"最适合场景"的一致性。理解了这一点，你就能解释为什么 ZooKeeper 不能当消息队列用、为什么 Kafka 默认不是强一致、为什么银行系统宁可慢也要 2PC——这些都是矛盾 4/5 的必然推论。**

## 课后思考

1. 为什么共识协议都用"多数派"而非"全票通过"？多数派能容忍多少个节点故障？（提示：N 个节点中多数派 = ⌊N/2⌋+1，容忍 N−多数派 个故障）
2. 如果你要设计一个"既要强一致、又要高可用"的系统，你会怎么做？（提示：单机可以做到，分布式不行。或者用 Spanner 的思路——用原子钟把"分布式"变成"看起来像单机"）
3. Kafka 的 `acks=all` + `min.insync.replicas=1` 配置有什么风险？（提示：ISR 缩小到 1 时，写入仍会成功，但此时故障会丢数据——这实际上退化成了 At-Least-Once）
4. 用第一性原理 5 步法分析 Cassandra 的可调一致性：它解决哪个矛盾？做了什么取舍？假设前提是什么？失败模式是什么？
